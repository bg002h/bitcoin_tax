# 3. BLOCKING FINDINGS

### I-1 — §6's rounding rule contradicts §8's cent-precise vectors and §4's absolute chain; T2's KAT list is unexecutable as written
*(§2 "Rounding" vs §8 vs §4 Tier-2 vs T2)*

**Problem.** §2 states an unambiguous rule about the *computation*: "whole dollars **per line** … each band's tax is rounded at its own line." §8 pins the same quantities to the cent (line 9 = 447,200.50 / 113,654.50; AMT = 15,818.50 / 1,722.50), and §4's Tier-2 row requires AMT to thread into `AbsoluteReturn.total_tax`/`amount_owed`, which is verified exact-cents (`return_1040.rs:910,935,954` are `Usd`; `ar.regular_tax` = 420,929.50). Both cannot hold, so T2's "KATs: every §8 vector" cannot be written against a whole-dollar struct. `round_dollar` is half-up (`conventions.rs:37`, `DOLLAR_ROUNDING`), so rounding Part III's intermediate lines (L31 = 54,442.50 on V5) moves L38 and hence §1's own headline exemplar by a dollar. It also silently decides V9, whose acceptance window `(L16 − FTC, L16]` is ≤ $600 wide — whether lines 7 and 10 are compared rounded or exact changes whether an attachment triggers on a tie.

**Fix.** State which layer `Form6251` is, matching the architecture already in-tree (`printed.rs:1-14`, `design/full-return/ROUNDING_AUTHORITY.md` Reading A): `Form6251` carries **exact cents** and lives in the absolute chain beside `AbsoluteReturn`; §8's figures are that layer and T2's KATs pin them to the cent; the **printed** Form 6251 rounds per line and cross-foots per `printed.rs`'s existing discipline, pinned by T7's byte-reproducible V5 golden. Say explicitly that the Who-Must-File line-7-vs-line-10 comparison uses the **exact** values, so attachment cannot flip on a rounding tie. Re-scope §2's "two orders differ by $1" KAT to the printed layer.

### I-2 — §11's `#[non_exhaustive]` instruction hard-errors one crate and dissolves the no-wildcard guarantee §4 leans on
*(§11 SemVer)*

**Problem.** §11 says "Mark all three `#[non_exhaustive]` in the Tier-1 commit (cheap; `no-users-yet`)". Verified: it is neither cheap nor safe for two of the three. (a) `Schedule2Lines` is built by **struct literal in another crate** — `crates/btctax-forms/tests/full_return_forms.rs:430` (imported from `btctax_core::tax::printed` at `:13`); `#[non_exhaustive]` makes that E0639, a hard compile error, against §6's "`make check` green from the first commit." (b) `RefuseReason` is matched **exhaustively from another crate** at `crates/btctax-input-form/src/attribute.rs:22-26`, whose own header states the guarantee: *"An EXHAUSTIVE `match` — no `_` arm — so a new `RefuseReason` fails to compile until it is placed."* `#[non_exhaustive]` forces a wildcard arm there, converting the compile-time totality that §4 cites as its reason for putting `attribute.rs` in the blast radius into a silent catch-all, leaving only the hand-written list at `:348` — which by construction cannot notice a new variant. That trades a structural guarantee for a SemVer label in the one repo whose named architectural fault line is "held by convention, not construction."

**Fix.** Take the branch §11 already names: **Tier 1 is MAJOR for `btctax-core`**, all three stay plain derives — `no-users-yet` makes the major bump free. If a `#[non_exhaustive]` is still wanted, restrict it to `AbsoluteReturn` (verified: every literal is in-crate — `return_1040.rs:1287,3760`, `printed.rs:1270,2132,2358`) and add one sentence recording that `RefuseReason` stays exhaustive because `attribute.rs`'s no-wildcard match is load-bearing, and `Schedule2Lines` stays plain because `btctax-forms` constructs it by literal.

### I-3 — §6's input-surface guard cites a mechanism that structurally cannot assert absence
*(§6 exhaustiveness bullet (ii) / T2's "the two §6 exhaustiveness guards")*

**Problem.** §6 says the eleven uncapturable items "still have no `ReturnInputs` leaf, via `spec/coverage.rs`'s existing mutate-and-diff mechanism." Verified against `crates/btctax-input-form/src/spec/coverage.rs`: the mechanism serializes a maximally-populated `ReturnInputs`, walks every **existing** leaf (`leaf_map`, `:67-75`), and asserts `{in-scope leaves} == {covered} ∪ {exempt}`. A concept never given a struct field never appears in `leaf_map`'s output — there is nothing to observe, so the KAT cannot assert non-existence. It is weaker still than "cannot": if someone *did* add an `iso_exercise` leaf **and** gave it a form `Field`, coverage stays green and says nothing. The EXEMPT-list workaround is foreclosed too — `:262-279` asserts every `EXEMPT_LEAVES`/`EXEMPT_PREFIXES` entry matches a real fixture leaf and panics on "stale exemption." This is r2 I-6 recurring inside its own fix (the same shape as r2 C-A: an existing mechanism cited for a guarantee it cannot carry), and r2's fix text asked this exact question ("say whether this extends `spec/coverage.rs`'s mutate-and-diff KAT … or stands alone") without the plan answering it.

**Fix.** Point (ii) at a mechanism that can observe absence — e.g. a KAT that reuses `leaf_map` on the maximal fixture and asserts no key matches a literal blocklist of the uncapturable items' field-name patterns — **or** state plainly that (ii) is a documentation/code-review guarantee, not an automated KAT, and drop the `coverage.rs` citation. Give it its own T2 sub-bullet so the mechanism is named rather than gestured at. While there: re-key the guard to the form's numbering ("every Part I line 2c–2t and line 3 either refuses or has no `ReturnInputs` leaf", enumerated from `PART_III.md`) and drop the count "eleven" — §1's prose list omits 2m, 2n, 2o, 2q and 2r, and under §0's own thesis an exhaustiveness guard is the last place a prose list should stand in for numbered lines.

### I-4 — T3's `EXPECTED_REFUSED` instruction picked the one branch of r2 I-7 the tree makes impossible
*(T3 bullet 5)*

**Problem.** r2 offered "`EXPECTED_REFUSED` becomes empty **or** is retargeted to a household that still trips line 7 > line 10"; the fold kept only the retarget. No retarget target can exist, by construction rather than by accident: `gen_goldens.py:259`'s `if amt or credits` rejects any candidate with `c09600 != 0` and its own comment (`:256-258`) says the substance check "applies to EVERYONE (anchors included)" — the anchor exemption at `:266-276` bypasses only the *harness refusal* gate. With FTC = 0, line 7 = line 9 and line 10 = regular tax, so AMT = 0 ⟺ line 7 ≤ line 10 — and no corpus household can carry an FTC (verified: no `foreign`/`e07300` field anywhere in `gen_goldens.py` or `corpus.py`). So every bakeable household proceeds after T3, including the sole current anchor (`smoke.rs:93-97` says both oracles compute zero actual AMT on it). Nor can the constant merely be emptied as written: `the_amt_screen_anchor_is_reported_refused_in_default_mode` indexes `EXPECTED_REFUSED[0]` (`smoke.rs:101`) and would panic on an empty slice.

**Fix.** Replace the bullet with the actual work: `EXPECTED_REFUSED = &[]`; **invert** `the_amt_screen_anchor_is_reported_refused_in_default_mode` so it asserts the anchor now *proceeds* and reconciles on every compared line — that inversion is the end-to-end proof that T3 un-refused the target population and is worth strictly more than the test it replaces; `sweep_check_reconciliation`'s `refused == EXPECTED_REFUSED` then asserts emptiness, and `admitted >= 10` moves by one. Attach r2's "do not delete" to the *test function*, not to the constant. (T5 already owns the now-dead `gen_goldens.py:266-276` branch.)

## Findings

**1. [Critical] §2.4 step 3 makes `execute_defensive_export` unreachable while the stale latch is armed, revoking D-7 and removing the design's only named mitigation for the reopen-bounce.**
`x` is dispatched from exactly one place: `main.rs:511-513`, inside the `EditorScreen::DefensiveFiling` arm (`:493`). That screen is entered from exactly one place: `KeyCode::Char('w') => app.open_defensive_filing()` (`main.rs:478`), which sets `self.screen = EditorScreen::DefensiveFiling` at `editor.rs:514`. `open_defensive_filing` opens with `if let Some(s) = self.residue_latch_status() { … return; }` (`editor.rs:474`) — and it is one of the "~27 opener sites" §2.4 step 3 switches to `stale_or_residue_latch_status()`: I counted the call sites and there are exactly 26 in `main.rs` (`:775 … :10107`) plus `editor.rs:474` = 27. So while armed, `w` refuses, DefensiveFiling is never entered, and `x` is never dispatched. D-7's premise ("it is the filer's route to the 8949/8275 packet") and §2.6's "D-7 is the primary mitigation — `x` still works while armed, so the packet is reachable *before* quitting" are both false.
The exemption survives only for the 2 tails that arm while the filer is already on that screen — the declare tail (`:4217`) and the promote tail (`:4498`) — because `close_all_mutation_surfaces` (`main.rs:719-764`) does **not** null `defensive_dashboard` and does not change `screen`. For the other 25 tails the filer is on Browse and has no route to the export. And §3.5(a)'s guard ("`handle_key`'s dispatch set ⊆ `close_all`'s clear set", with the extraction rule *left unstated*) would, on the reading that includes `defensive_dashboard` — dispatched via `as_mut()` at `main.rs:501` — force it into `close_all` and kill the last 2 as well.
**Filing scenario:** the filer voids a decision from Browse (tail `main.rs:4809`); the append lands; `build_snapshot` fails on a corrupt local price cache (`unlock.rs:203-205`, deterministic in on-disk content); the latch arms. `w` refuses. They quit as instructed (fact 3), and `open_session` bounces at `unlock.rs:135` with "failed to load vault data" — the same deterministic arm. They now have no in-app route to their Form 8949 / Schedule D / Form 8275 packet, in the exact scenario the design cites D-7 to cover.
**Fix:** exempt `open_defensive_filing` from the stale branch too (gate the dashboard's *write* intents — `DashboardIntent::Declare`/`Promote` at `main.rs:505-510` — instead of its entry, since the dashboard itself is read-only), state the extraction rule for §3.5(a) so `defensive_dashboard` is excluded, and add a KAT that `w`-then-`x` completes while `stale_after_write` is armed from a Browse tail.

**2. [Important] §2.5's replacement marker is specified against a construction that exists only on the DefensiveFiling screen, so D-2 is still undelivered on Browse — where the stale Form 8949 / Schedule D figures are read.**
§2.5 says "reserve the notice rows when `stale_after_write.is_some()` … Today `draw_edit.rs:108-119` allocates them on `status.is_some()` alone". Those lines are inside `draw_defensive_filing` (`draw_edit.rs:99-164`); `DEFENSIVE_NOTICE_LINES = 3` is declared at `:169` and used nowhere else. `draw_browse` (`:173`) builds `constraints = [Length(3) tab bar, (Length(1) pseudo banner), Min(0) content, Length(1) footer]` (`:183-195`) and renders the status into that one footer row (`:279-294`), which reverts to the keybinding hint the moment `main.rs:414` clears the status. There is no notice-row mechanism on Browse to make state-conditional. §3.12 nonetheless demands "New goldens cover the armed state, including Browse at 80 columns" — a golden for a marker the architecture never specifies. (Distinct from arch-r2 I-3: that was the *title* construction, which this fold withdrew; this is the replacement.)
**Filing scenario:** armed by any Browse-screen tail, the filer Tabs to Forms/Tax — `btctax_tui::tabs::forms::render(frame, content_area, snap, year)` etc. at `draw_edit.rs:229-271` renders straight off the pre-write `snap` — and transcribes Form 8949 column (d)/(e) and Schedule D totals that predate the write they just made, with nothing on screen saying so.
**Fix:** specify a Browse row keyed on `stale_after_write.is_some()`, inserted the way the PSEUDO banner already is (`draw_edit.rs:184-186`, `:213-225` — a state-conditional `Constraint::Length(1)` with index bookkeeping at `:194-195`), and say explicitly that the DefensiveFiling notice rows carry the §2.6 facts while the Browse row carries the short marker.

**3. [Important] `declare_flow_confirm` derives a decision payload from `app.snapshot` and writes it, and the fold's remedy, KATs and site table all exclude it; the bulk-income exposure §0.1 substitutes for it is not real.**
`main.rs:4172-4188` plans off `&snap.events`/`&snap.prices`; `:4210` writes it; `apply_declare` (`chokepoint/mod.rs:601-609`) appends verbatim with no re-check. Critically, `plan_declare`'s **gates** run against the stale image: `guard_tranche_vs_allocation(events, window_end)` (`chokepoint/mod.rs:537`) and the DFW-D5.2 clearance shadow, which re-projects `events + candidate` and asserts no `UncoveredDisposal` remains (`:559-591`). A stale `events` therefore lets a tranche through that the current ledger would refuse.
Meanwhile §0.1's substitute claim — "`open_bulk_income_modal` (`:8612-8627`) freezes each row's `fmv` into the payload" as a stale-image exposure — is wrong. `i.fmv` comes from `bulk_income_recompute_preview` (`main.rs:8504-8550`), which calls `session.bulk_classify_income_plan(filter)` (`:8517`), whose first statement is `let (events, state, _cfg) = self.load_events_and_project()?` (`session.rs:947`) — a fresh read off the session. Only the opener's wallet/year *filter choices* come from `snap` (`:8352-8409`), and a stale choice yields an empty plan, not a wrong dollar amount. So §3.3 spends one of its two filing-correctness KATs on a non-exposure while the real one is unnamed.
**Filing scenario:** a safe-harbor allocation is appended and its re-projection fails; the filer (pre-`close_all`, or in any future arrangement where the declare flow survives) confirms a declare whose `window_end` overlaps that allocation. `guard_tranche_vs_allocation` sees the pre-write image, passes, and a `DeclareTranche` lands that corrupts the allocation's conservation — the year then will not compute, and the tranche's synthetic acquisition feeds the Form 8949 basis for the covered disposal.
**Fix:** add `main.rs:4172-4188` to §2.2's table as a *fifth* site whose remedy is "calls `live_snapshot()` and refuses" (no migration needed — the borrow ends at `:4188`), extend §3.3's KAT set to "no `DeclarePlan` can be constructed while armed", and correct §0.1's bulk-income paragraph to say the fmv is session-derived.

**4. [Important] §2.4 step 1's flush-first obligation puts a `Vault::save` inside `on_persist_error`'s `ResidueLive` handler, whose own copy promises the opposite.**
`close_all_mutation_surfaces()` is called at `main.rs:712`, immediately after the status that reads "*the vault on disk is unchanged; no in-editor action will save until you quit*" (`:707-711`). `ResidueLive` means `session.restore(pre)` **failed** after a failed `session.save()` (`edit/persist.rs:214-223`) — the in-memory DB still carries the un-reverted decision. §2.4 step 1 mandates that `close_all` now flush the tax-inputs draft, i.e. `form_save_draft` → `input_form_store::save_draft` → **`sess.save()`** (`input_form_store.rs:129`), which writes the whole in-memory image, residue included. Today this is blocked only by `handle_key`'s dispatch ordering (`main.rs:377` returns while `tax_inputs_form` is open, so no other surface can raise a `ResidueLive` while the form is live) — a convention, and precisely the "armed ⇒ unreachable" two-mechanism reasoning §2.2's ★ rejects two paragraphs earlier. The same unguarded write already exists on the idle tick (`main.rs:10658` calls `flush_tax_inputs_draft` with no latch check at all), which §3.5 asks only to *enumerate in tests*, never to gate.
**Filing scenario:** if the precondition is ever met, an unconfirmed, unreverted decision event is persisted to the vault under a banner telling the filer their vault is untouched — a decision they never confirmed then feeds every downstream 8949/Schedule D figure.
**Fix:** make the write-side gate structural rather than surface-based: have `flush_tax_inputs_draft` itself refuse when `attest_save_failed || rollback_failed` (this also covers the idle tick and `q`), and specify that `close_all`'s flush runs only on the `apply_reprojection` `Err` path, never on the `ResidueLive` path. KAT the mutation.

**5. [Important] A successful `x` while armed installs a *fresh* snapshot but leaves the latch and the marker asserting staleness, and every payload derivation still refused.**
`execute_defensive_export` re-projects at `main.rs:4626`, and on success assigns `app.snapshot = Some(snap)` (`:4630`) and refreshes the dashboard (`:4631`) — unconditionally, with no reference to `stale_after_write`. D-4 gives the latch zero clear sites. So after the export the rendered image is demonstrably current, the dashboard rows have silently changed under the filer, and yet §2.6 fact 1 still tells them "whether it had the intended effect could not be verified", the §2.5 marker still says stale, and `live_snapshot()` still returns `Err` for every write action.
**Filing scenario:** the filer promotes a tranche, re-projection blips, latch arms, they press `x`; the packet is written off the fresh image and is *correct*; the dashboard now shows the tranche as promoted; but the persistent marker says the last write's effect is unverified and every action refuses. §2.6's own stated risk — "the filer redoing a write that already succeeded" — fires: they quit, reopen (or bounce), and re-promote, which `apply_promote`'s `would_conflict` pre-check (`chokepoint/mod.rs:470-476`) refuses with "cannot record this promote — a decision conflict", leaving them believing the promote never landed.
**Fix:** decide explicitly. Either the export's successful rebuild is routed through `apply_reprojection`'s `Ok` arm and is the one sanctioned clear site (amending D-4 with its rationale), or `execute_defensive_export` must plan off a *local* rebuilt snapshot and not install it while armed, so the marked image stays consistent. Silently refreshing behind a stale marker is not an option; whichever is chosen needs a KAT on the post-export marker text.

**6. [Important] §2.6 fact 2's conditional rests on a premise that is false in source: the tails null their surfaces *below* the inner match, so the "something was closed" condition fires at essentially all 27 — and at the one tail the design says it fires, the claim is false.**
§2.3 and §2.6 both assert "26 of 27 tails null their own surface **above** the match". They do not. Reading the tails directly: the select-lots tail nulls at `main.rs:4830-4831`, *after* the `match new_snap` block that ends at `:4826`; classify-inbound at `:1681-1682` after the block ending `:1680`; bulk-income at `:8693-8694` after `:8692`; pseudo-approve at `:8271` after `:8265`. (The only pre-match `= None` in each region is the `None => { app.X_modal = None; return; }` guard inside the session-extraction block, e.g. `:1649-1650`.) The genuine above-the-match nulls are the declare tail (`:4219`), the promote tail (`:4500`), the commit tail (`:1340`) and the attest tail (`:7026`) — four, not twenty-six. So `close_all_mutation_surfaces()`, invoked from the `Err` arm, really does close a live surface at most tails, and the conditional emits "any in-progress flow entry was discarded" almost everywhere.
Worse, at the park tail — the one the design says is the exception — the condition fires and the sentence is **false**: `confirm_park_to_profile` sets `form.dirty = false` at `main.rs:1536` *before* the `match new_snap` at `:1538`, and `form_park_to_profile` has already written the parked draft, so nothing is discarded.
**Filing scenario:** the filer parks their full return for a year (the entire `ReturnInputs` 1040 input set), re-projection fails, and they read that their in-progress entry was discarded. It is on disk as a `parked = 1` draft (`input_form_store.rs:66-84`). They re-author the return, or re-park — and `park_to_profile` refuses when a WIP draft occupies the slot (`main.rs:1511`), leaving them convinced the park never happened.
**Fix:** compute the condition from an actual pre-close survey (`let closed_any = self.any_mutation_surface_open()` before the call), correct the "26 of 27 / above the match" premise in both §2.3 and §2.6, and word fact 2 as "the open entry screen was closed; nothing you had typed was written" — with an explicit park-tail carve-out saying the parked draft is on disk.

**Minor 1.** "Attested but re-projection failed" (`main.rs:7042`) is the one surviving prefix that claims an *effect*, not just a landing: `derive_attest_status`'s arm 1 (`:7074-7078`) exists precisely to say "ATTEST FAILED: allocation fires SafeHarborUnconservable". Fact 1 disclaims it generically, but "Attested" is the word the filer will carry. Prefer "the safe-harbor attest write landed, but…".

**Minor 2.** §0.1 names `shown_terms` and the `promote_prior_year_advisory` year set as the stale-derived record but omits the number that actually reaches a filed form: `filed_basis`/`coverage`, computed in `plan_promote` from `conservative_promote::filed_basis_for(prices, …)` (`chokepoint/mod.rs:348-354`) and written into the payload at `:409-410` — that becomes the promoted lot's basis, i.e. Form 8949 column (e). Conversely, `shown_terms` never reaches a filed form: Form 8275 renders `part_ii_narrative` (`btctax-core/src/tax/form8275.rs:86-96` → `btctax-forms/src/form8275.rs:123`), which is filer-authored. Correcting both makes §0.1's withdrawal of the §4 non-goal stronger, not weaker.

**Minor 3.** Under D-5 the field is private to the `editor` module, but `execute_defensive_export` writes it from `main.rs:4630` and §2.2 specifies only three read accessors plus a `#[cfg(test)]` setter. **Minor 4.** The design never says what happens to a promote whose `Acknowledgment`/`filed_basis` was already recorded off a stale image in an existing vault: nothing detects it, nothing surfaces it, and the export renders the year normally. ## Verified sound

- **Fact 1 is true at all 27.** Every `Err` re-projection arm is nested inside an `Ok(...)` persist result, and every one of those wrappers reaches disk (`edit/persist.rs:227-232`; `input_form_store.rs:129`).
- **The refusal is sufficient; the derivation source does not need to change.** When the latch is not armed, `app.snapshot` equals the last successful re-projection, and the editor holds the vault's exclusive lock for its whole lifetime with no concurrent-writer case (`edit/persist.rs:8-11`, `session.rs:662`) — so `live_snapshot()` returning `Err` while armed is a complete fix for the promote path, and §4's withdrawal does not oblige a new derivation source.
- **The flush cannot produce a partial 1040 input set.** `save_draft` (`input_form_store.rs:126-131`) → `set_draft_row` (`:66-84`) is one serialized blob, one upsert, one atomic `sess.save()`.
- **Neither tax-inputs tail can lose work to the new `close_all`.** The commit tail sets `app.tax_inputs_form = None` at `main.rs:1340` before its `build_snapshot` at `:1347`; the park tail sets `form.dirty = false` at `:1536` before its match at `:1538`, with the draft already on disk — so `tax_inputs_flush_left_unsaved` (`:993-997`) is false at both.
- **`PromotePlan` has exactly one payload-bearing constructor** (`edit/promote_flow.rs:210`), reached only from `main.rs:4367-4376`, so §2.2's ★ genuinely covers the §6664(c) `Acknowledgment` on the promote path.
- **The export packet cannot disagree with the dashboard the filer is left looking at.** `execute_defensive_export` refreshes the snapshot and the dashboard at `main.rs:4630-4631` *before* `plan_export` at `:4656`, so the DFW-D11 year set, the written packets and the post-export dashboard all come from one image; and `plan_export` re-derives `flagged_years` on every call and persists no "already exported" marker, so a year dropped from one export reappears in the next.
- **D-7's carve-out itself is correct where it is reachable:** `execute_defensive_export` refuses on its own re-projection failure (`main.rs:4633-4640`) before touching `plan_export`, so it provably cannot export a short year set off a stale image.
- **§2.4 step 3's precedence ordering is behaviour-preserving.** All 27 existing call sites use the identical `Some(s) → set status → return` shape (verified across `main.rs:775 … :10107` and `editor.rs:474`), and `residue_latch_status` (`main.rs:672-690`) is left untouched for the export.

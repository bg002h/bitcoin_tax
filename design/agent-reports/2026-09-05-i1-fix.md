## 1. WHAT WAS BUILT

**One predicate**, `compliance::identification_is_timely(made: OffsetDateTime, disposition:
OffsetDateTime) -> bool` (`crates/btctax-core/src/project/compliance.rs:46`). It is now the only `<=`
between an identification instant and a disposition instant anywhere in the tree, and it carries the
authority quote plus a table of its callers.

| caller | file:line | what it decides |
|---|---|---|
| `resolve`'s §A.4 timeliness `retain` | `project/resolve.rs:1632` | whether the fold APPLIES the selection — the FILED NUMBER |
| `identification_made` | `project/compliance.rs:137` | the §A.5 verdict `verify` prints, and the fold's FR-34 advisory |
| `optimize::persistability` | `optimize.rs:493` | whether `optimize accept` may WRITE without an attestation |
| `optimize::proposed_compliance_status` | `optimize.rs:528` | the status `optimize run` PRINTS |

`identification_made` widened from `(TaxDate, Option<TaxDate>, Option<TaxDate>)` to
`(OffsetDateTime, Option<OffsetDateTime>, Option<TaxDate>)`. `election_from` stayed a `TaxDate`
deliberately and the doc says why: a `MethodElection` is a standing order *effective from a date*
(§A.5(a)), it is resolved date-wise by `resolve_election`, and it is never compared against the
disposition's instant.

### The design questions the brief asked

**(a) Where does the predicate live?** `compliance.rs`, as the brief guessed — checked, not assumed.
`compliance.rs` already imports from `resolve.rs`, so the reverse direction was the risk; Rust module
cycles inside one crate are legal, and `resolve.rs:1632` reaches it as
`crate::project::compliance::identification_is_timely`. `optimize.rs` is in the same crate.
Re-exported from `project/mod.rs` so the four call sites and the tests all name the same symbol, and
so it is greppable.

**(b) Does `optimize` genuinely have an instant, or only a date?** **It genuinely has one, at both
ends, and was throwing them away.**

- The *sale* instant: `optimize_year` already looked the disposal's import event up (to get the
  wallet) and read only `d.disposed_at` off the `Disposal` record. `ev.utc_timestamp` — the very
  field `resolve` reads into `Eff::utc` for the fold's own drop — was one line away.
- The *made* instant: every CLI entry point holds `now: OffsetDateTime` and was calling
  `tax_date(now, UtcOffset::UTC)` on the way in. **Three** entry points, not two: `cmd::optimize::run`,
  `cmd::optimize::accept`, and `Session::optimize_proposal` (the TUI's door, which the B3 review did
  not name). All three now pass `now` through whole.

So no narrowing was justified there and none was kept. `optimize_year`'s `proposal_made` is an
`OffsetDateTime`, and `Target` (the per-disposal tuple) carries `(id, wallet, TaxDate,
OffsetDateTime, Sat)`.

**Two granularities remain, and both are stated at the point of use rather than left implicit.** The
tax DATE still drives the §6045 broker envelope (`year >= 2027`), the §1.1012-1(j)(6) applicability
window, pool keys, and the joint-enumeration TIME order — all calendar rules, written in the
authorities as dates. That is why `DispositionMoment { date, at }`
(`compliance.rs:58`) exists rather than three bare time parameters: `persistability` and
`proposed_compliance_status` each take a sale moment *and* a made instant, and two adjacent
`OffsetDateTime` arguments can be transposed with no type error at all. Boxing one of them removes
that class.

★ I deliberately did **not** refine the joint-enumeration TIME order from date to instant even though
the instant is now in the tuple. It would change which candidate assignments the optimizer enumerates
for same-day contended disposals — a behavioural change outside I-1. Recorded in the `Target` doc.

**(c) The one place a date is widened, stated at the site.**
`conservative::tranche_broker_specific_id_advisory` keeps `TaxDate` parameters and widens to UTC
midnight internally, with the reasoning in its doc: its only caller reads `LedgerState::Disposal`,
which records `disposed_at: TaxDate` and no timestamp; it deliberately passes the sale's own date as
`selection_made` (there is no selection — the warning is prospective); and it fires only on the
`ForbiddenBroker2027` branch, a pure year test. Both sides widen to the same midnight, so the answer
is identical under every granularity, and a made-date one day later still widens to a later midnight
and is still correctly late. An `OffsetDateTime` in that signature would have been a fiction the
caller had to invent.

### Blast radius, as the compiler reported it

`identification_made` is `pub(crate)` with two callers. Widening it reddened `fold::consume_principal`,
which gained an explicit `at: OffsetDateTime` parameter — following the `IdScope` precedent in that
same function ("passed EXPLICITLY at every call site rather than inferred, so the compiler forces a
new call site to answer the question"). All four call sites had `eff.utc` already in scope.

`optimize_year`'s signature change reddened 24 call sites (21 in tests, 3 in `btctax-cli`), and the
`Target` change reddened `contention_groups`, `group_candidate_assignments`, `independent_group_maps`
and three inline unit tests. Every one was mechanical and every one was found by `rustc`, not by
reading.

### ★ A stale-artifact trap in the harness itself, found and fixed

The first sweep restored each file with `shutil.move(bak, path)`, which carries the **backup's older
mtime**. Cargo then kept the *mutated* artifact for the restored source. It did not corrupt any
mutation result (each mutation writes a fresh mtime, and cargo recompiles a crate from all its current
sources), but it left the tree compiled-stale *after* the sweep — and the next test I wrote ran
against the M10-mutated library and failed for a reason that had nothing to do with it. I spent four
diagnostic rounds on a defect I had planted and un-planted.

The harness now `os.utime`s each restored file, all sources were touched, and **both sweeps were
re-run from a clean build**; the table above is the re-run. This is exactly the green-and-blind shape
this repo hunts, in a measuring instrument rather than in the code — worth recording because any
mutation harness built here will hit it.

★ `cargo fmt` (the pre-commit gate) then reflowed three of the mutation anchors, so **both sweeps
were run a third time against the formatted source that is actually committed.** All ten verdicts are
unchanged. A mutation table measured on a tree that is not the committed tree measures nothing.

## 3. THE FOUR CONSTRAINTS — how each is honoured

1. **Per-field, never per-type.** `ConsentTerm::ComputedTax.{delta_usd, deduction_delta_usd}` and
   `ConsentTerm::Uncomputable.{gain_delta_usd, deduction_delta_usd}` go through
   `signed_by_design`/`signed_by_design_opt` — deliberate no-ops whose *call* is the whitelist, so
   the exemption is greppable rather than an absence. `ConsentTerm::Unrealized.{sat,
   hypothetical_reduction}` sit in the *same enum* and are guarded, which is exactly what a per-type
   rule cannot express; a test pins each direction.
2. **No serde.** Nothing in the change touches a `Deserialize` impl. `load_all` is untouched, and
   `load_all_still_reads_a_pre_existing_impossible_row` writes a negative row behind the seam with
   raw SQL and asserts it still loads — the invariant is forward-only by construction.
3. **Refuse, never normalise.** The module only reads and returns `Result`; the ban is in its
   header with the reason (`fingerprint` → conflict `EventId`). No `.abs()`, clamp or round added.
4. **The advisory did not move.** `sats_as_dollars_advisory` is untouched, and the module header
   records *why* it cannot live at this seam (no price provider; a decision's `utc_timestamp` is its
   creation time, not the target event's date). Filed as **FR-41**.

## 5. THE DECISIONS THE BRIEF ASKED FOR

### (a) Should the individual doors ALSO guard early? — **One yes, three no.**

| door | early guard? | why |
|---|---|---|
| TUI `classify-raw` (`form.rs`) | **YES — done** | This is not a new copy; it is *removing a bypass of a helper that already exists in the same file*. `parse_nonneg_usd` sits at `:691` and is used by seven other call sites, and `validate_classify_raw_acquire`/`_income` were reaching past it to a raw `Usd::from_str`. Routing them through it makes the file consistent instead of divergent, and the user gets a field-level message on the form rather than an error at save. `parse_required_sat` gained the same `>= 0` check. |
| CLI `classify-raw` | no | A guard here would be a genuinely new second copy, of a check the seam already performs, on a surface where the seam's message (`refused: Acquire.usd_cost = -1680.00 — no legitimate negative cost basis …`) already names the field. |
| CSV adapters (Coinbase/Swan/River) | no | The tempting "fix" is Gemini's `.abs()`, and that is the wrong direction: it *launders* impossible data rather than refusing it, and constraint (3) forbids repair at the seam for the same reason. Adding three more copies of a sign check is precisely the divergent-copy shape that let these three fall out of step with Gemini in the first place. Filed as **FR-39**. |
| `accept-conflict` | n/a | It has no code of its own; only the seam reaches it, which is why the seam was chosen. Covered by recursion into `ImportConflict.new_payload`, with a test. |

**Does the one "yes" risk the divergent-copies problem?** Marginally, and it is worth it. The
divergence risk is *two implementations of a rule that can drift apart*; here the TUI now calls the
same in-file helper as its seven siblings, and if it ever drifts, `persistence::insert` still
refuses — the structural guarantee does not depend on the TUI being right. The failure mode of the
alternative (leaving the form silently accepting `-5000` and surprising the user at save time) is
worse than the cosmetic redundancy.

### (b) Does `sat` belong in this change? — **Yes, and it is in.**

Three reasons, in ascending order. (i) It is the *same defect at the same door*: both `classify-raw`
paths parse `sat` with a bare `serde_json` / `t.parse::<i64>()` and nothing in core refused a
negative one on a payload, so splitting it would leave half the door open on the door FR-38 names.
(ii) It costs nothing extra — it is the same destructure, and deferring it would mean re-opening
this exact file later. (iii) Per *an entry is testimony*, a negative satoshi count on the ledger is
fabricated testimony even where it folds to nothing; the existing `build_op sat > 0` fold guard
makes it *harmless*, not *legitimate*, and the fold guard is not a record-time refusal.

The threshold is `< 0`, not `<= 0`: **zero stays legal**, for both USD and sat. A `$0` basis is this
application's conservative default for an undocumented tranche and for an inbound self-transfer, and
a zero-quantity row is not an error. A guard that refused zero would refuse the app's own filing
posture — pinned by `zero_usd_and_zero_sat_still_record` and
`classify_raw_zero_and_positive_usd_still_record`.

One subtlety worth recording: `Decimal` distinguishes `-0` from `0`, and `parse_usd` on an
accounting `(0.00)` produces exactly `-0`. The predicate is `is_sign_negative() && !is_zero()`, and
`negative_zero_is_not_a_negative_amount` holds it.

## 9. RESIDUAL RISK, STATED PLAINLY

1. **The `..` convention is a convention.** rustc's own `E0027` help text suggests `..` as the fix.
   A future author who takes that suggestion silently reopens the hole for *new* fields — existing
   fields stay guarded. It is one file and one grep, versus the 40 call sites the alternative would
   have needed, but it is not zero.
2. **The guard is record-time, not read-time, by design.** A vault that already held an impossible
   value keeps loading. That is deliberate (a `deserialize_with` would brick such a vault instead of
   refusing new entries), and the grep says no such vault can exist from this codebase — but the
   guarantee is "no new impossible row", not "no impossible row".
3. **Polarity only.** This gate says a value is not *impossible*. It does not say it is *plausible*
   — that is the advisory's job, and the advisory is still CLI-only (FR-41).

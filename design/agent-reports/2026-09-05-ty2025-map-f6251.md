## 1. The headline: this is NOT the TY2024 map with the year bumped

Form 6251 is one of the two forms the TY2025 law change actually rewrote. **Line 1 split into 1a/1b**
(Pub. L. 119-21, wiring Part I to the new Schedule 1-A), page 1 gained one widget, and **every page-1
field name from `f1_4` onward now means a different line than it did in TY2024.**

Measured, both years, with `./target/debug/xtask dump-fields`:

| | TY2024 | TY2025 |
|---|---|---|
| AcroForm fields | 61 | **62** |
| page-1 money widgets | 30 (`f1_3`..`f1_32`) | **31** (`f1_3`..`f1_33`) |
| page-2 money widgets | 29 (`f2_1`..`f2_29`) | 29 — **identical in name AND rect** |
| `f1_4` means | line 2a | **line 1b** |
| `f1_12` means | line 2i (ISO) | line 2h |
| inset (parenthesised) trio | `f1_5`, `f1_9`, `f1_22` | **`f1_6`, `f1_10`, `f1_23`** |
| censused block (2c–2t) | `f1_6`..`f1_23` | **`f1_7`..`f1_24`** |

A blind port therefore writes 2a's figure into 1b's box, shifts 2a..11 down one, ends with **line 11 —
the AMT itself, the figure that carries to Schedule 2 line 2 — written into line 10's box**, and leaves
`f1_33` blank on a filed return. I planted exactly this defect and watched the checker red on it (§4).

## 2. The mapping, and how it was corroborated (four independent checks, not an in-order zip)

1. **Per-page counts.** Page 1 has exactly 31 money widgets; Part I+II is exactly 31 numbered boxes
   (1a, 1b, 2a–2t, 3, 4, 5–11). Page 2 has 29; Part III is 29 (12–40).
2. **The inset trio.** Exactly three page-1 widgets are narrow — `f1_6`, `f1_10`, `f1_23` at
   x=[508,572] (w=64) against every other money box at [504,576] (w=72). The form prints exactly three
   parenthesised boxes: **2b, 2f, 2s** (extract rows 24, 28, 41). Under this assignment the two sets
   coincide exactly; under any off-by-N they do not.
3. **The 1a inset column.** `f1_3` is the only money widget outside the right-hand amount column —
   x=[410.4, 481.6], y=[648, 660]. The form prints 1a's box in the inner column (extract row 19 puts
   "1a" well left of row 21's "1b"), because 1a is a sub-total feeding 1b. `f1_3` = 1a is pinned by
   position alone.
4. **Monotonic y with matching gaps.** y descends strictly with line number on both pages, and every
   gap > 12 lands on a line the extract prints across multiple rows.

**Independently reproduced by the geometric label reader.** `xtask label-boxes f6251--2025` emits
exactly this field→label assignment; `label-census f6251--2025` reports *"60 labels, 62 boxes … 60 entry
line(s), 0 without a box"* (the 2 unlabelled boxes are name + SSN). Two methods, one answer.

> Note for the controller: `design/ty2025/recon-year-port-delta.md` §3 records that the label reader
> *"silently dropped line 1a"* on this form. **That is no longer true** — it reads 1a correctly today.
> The recon's caution stands as a class, but this specific observation is stale.

## 3. Per-line printed-text check (gate 2) — read from the TEXT LAYER, never the page

All 42 mapped lines carry their instruction text verbatim as a doc comment, and each was machine-checked
as a whitespace-normalised substring of the extract, using the **same normalisation the in-repo test
uses** (`crates/btctax-forms/tests/f6251_map.rs::every_quoted_instruction_is_verbatim_on_the_form`:
collapse whitespace, drop lone `{`/`}` brace glyphs). 42/42 verbatim.

The two traps this form is famous for, both re-read from the text layer:

- **Line 33 is "Subtract line 32 from line **22**"**, four rows above line 36's "Subtract line 35 from
  line **12**" — same verb, two-digit operands that differ by a few pixels rendered. Both confirmed
  against extract rows 136 and 140.
- **Line 6's zero-out set is "lines 7, 9, and 11"**, split across extract rows 57 and 63 by five
  brace-glyph rows. A row-wise reader stops at "lines 7, 9," and silently drops 11.

### The MFS line-4 kicker (the brief flagged it as defect-prone) — TY2025 values

From `design/forms/extract/i6251--2025.txt`, "Line 4—Alternative Minimum Taxable Income", verbatim:
*"If your filing status is married filing separately and line 4 is more than **$900,350**, you must
include an additional amount on line 4. If line 4 is **$1,174,350** or more, include an additional
**$68,500**. Otherwise, include 25% of the excess of the amount on line 4 over $900,350."*

The Exemption Worksheet note in the same document puts the MFS **zero-exemption** point at
*"$900,350 if married filing separately"* — **the identical $900,350**. The §55(d)(3) collision that has
previously cost this repo both oracles at once is still present in TY2025, at a new value.
**There is no widget for the kicker**: it folds into line 4's own box, so no field map can catch it
being dropped. That is engine work, not map work, and it is flagged here only so it is not assumed done.

reachable only through a refusal — `QuestionId::OtherOutOfScopeIncome` limb (b),
`crates/btctax-core/src/tax/questions.rs:554`, verified present and year-independent.

## 5. What I could not resolve — three items for the controller

1. **`Form6251Map` cannot deserialize this file yet, and that is correct rather than a defect in the
   map.** `crates/btctax-forms/src/map.rs:116` declares `pub line1: MoneyCell` with no
   `#[serde(default)]` and has no `line1a`/`line1b`; `money_cells()` destructures exhaustively with no
   `..`. So a `toml::from_str::<Form6251Map>` of this file would fail *missing field `line1`*.
   The map is keyed on the form's own numbering because that is the standing transcription rule, and
   because core **already models the 2025 shape** — `Form6251Line1::Y2025 { line1a, line1b }`
   (`crates/btctax-core/src/tax/form6251.rs:60`), with `f6251_fill.rs:167`'s
   `a_ty2025_shaped_line_1_refuses_against_the_ty2024_map` already asserting the TY2024 map must refuse
   it. The forms crate needs a per-year line-1 shape to match. **That is Rust work I was scoped out of.**
   Nothing loads either new file today (`f6251_pdf(2025)` returns `UnsupportedYear`; there is no
   `F6251_MAP_2025` const and no `ty2025()`), so both additions are inert and cannot break another
   agent's build.
2. **A 2025 conformance test cannot reuse TY2024's hardcoded inset list.** `f6251_map.rs` asserts the
   inset widgets end with `f1_5[0]`/`f1_9[0]`/`f1_22[0]`. For TY2025 those are `f1_6`/`f1_10`/`f1_23`.
   Better: derive the expected set from the parenthesised labels in the extract (my checker does — it
   greps `2x (` out of the text layer and gets 2b/2f/2s), so the list stops being hand-maintained.
3. **The TY2024 map's sign-convention list does not reproduce under measurement, and I did not
   change it** (out of scope — it is another form-year's file). Attributing each "enter as a negative
   amount" directive in the instructions to its own `Line NN—` section heading gives:
   - `i6251--2025`: 1b, 2b, 2c, 2d, 2f, 2k, 2l, 2m, 2n, 2q, 2s, 3
   - `i6251--2024`: 2b, 2c, 2d, 2f, 2k, 2l, 2n, 2p, 2q, 2s, 3

   The TY2024 map's prose names *"2c, 2d, 2k, 2l, 2n, 2o, 2p, 2q, 2r"* and line 3 — it includes **2o**
   and **2r**, which this measurement does not find in either year, and omits **2m**, which it finds in
   2025. Only the parenthesised trio affects the field map, so nothing here blocks this artifact; but
   the emitter's sign handling should be re-derived from the measurement rather than from either prose
   list. Command is in the map header so it is one grep to re-run.

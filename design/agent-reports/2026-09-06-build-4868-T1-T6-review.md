### I-1 (Important) — a refused `--pay` leaves a packet directory with NO `manifest.txt`, and that is exactly the state the extension's own guard cannot see

**Where.** `crates/btctax-cli/src/cmd/admin.rs:1060-1084` (the `--pay` match inside
`write_payment_voucher`), called at `:1489`, i.e. AFTER every packet PDF is on disk and BEFORE
`manifest.txt` is written at `:1503`. The guard it defeats is
`crates/btctax-cli/src/cmd/admin.rs:1691` (`if out_dir.join("manifest.txt").exists()`).

**What is wrong.** `export-irs-pdf --pay-by-check --pay <above line 37 | negative | with cents>`
refuses *after* the packet has been written. The directory is left holding the return's PDFs with no
manifest. The `extension` command decides "is this the return's envelope directory?" solely by the
presence of `manifest.txt`, so the guard reads that directory as empty ground and writes `f4868.pdf`
into it — the one outcome the guard exists to prevent, and one of the four things the brief names as
spec-forbidden ("a copy of the 4868 in the return's envelope"). The unsound assumption is
`manifest.txt present ⟺ this is a packet directory`; a refused export falsifies it.

**Evidence.** Two probes, in my worktree, both reverted.

```

ERR: usage: --pay $99999999 is more than the $53572 this return owes (Form 1040 line 37). …
OUT DIR AFTER REFUSAL (6 entries): ["00_f1040.pdf", "02_f1040s2.pdf", "12A_f8949.pdf",
                                    "12_schedule_d.pdf", "71_f8959.pdf", "72_f8960.pdf"]
manifest.txt present = false

# probe B — btctax extension --out <a directory in exactly that state>
NO REFUSAL. wrote "/tmp/.tmpJKUypP/f4868.pdf";
dir now = ["00_f1040.pdf", "02_f1040s2.pdf", "12A_f8949.pdf", "12_schedule_d.pdf", "f4868.pdf"]
```

`--pay 100.25` (a plausible typo) and `--pay <too much>` are both ordinary filer slips, so the
precondition is not exotic. Note the contrast the build itself draws: `btctax extension`'s own `--pay`
guard runs before `mkdir_out` and its tests assert `wrote_nothing(dir)`; the export path's identical
guard runs last.

**Minimal change.** Hoist the three `--pay` validations out of `write_payment_voucher` and run them in
`export_irs_pdf_from_session` beside the existing pre-byte slice refusal (`admin.rs:683`) — they need
only `voucher.pay` and, for the ceiling, `printed.forms.f1040.line37`, so the ceiling check can move
to the top of `export_full_return` immediately after `assemble_printed_return`. Pair it with a KAT that
asserts the `--out` directory is unchanged after each of the three refusals (the shape
`extension.rs::wrote_nothing` already uses).

### I-2 (Important) — the "no copy of the 4868 in the return's envelope" guard is one-directional; the chronological order walks straight past it

**Where.** `crates/btctax-cli/src/cmd/admin.rs:1691` guards `extension` against a packet directory.
There is no reciprocal check anywhere in `export_irs_pdf_from_session` / `export_full_return`
(`admin.rs:642` / `:1261`) — `mkdir_out` is recursive and idempotent (`fsperms.rs:73`) and nothing
inspects the directory's existing contents.

**What is wrong.** The natural order is `extension` in April and `export-irs-pdf` in October. A filer
who reuses one `--out` directory for the year gets the whole packet written *around* the April
`f4868.pdf`, with no refusal, no warning on stderr, and no mention in the manifest. The spec's own
rationale for the R2 refusal — *"an unlabelled copy sitting in the return's envelope is exactly what
[the form] forbids"*, and *"a filer who collated that directory by filename would attach it"* — applies
verbatim in this direction and is not implemented. The R2 refusal's literal wording is met; its purpose
is met in only one of the two orders, and the unguarded one is the one that happens first in time.

**Evidence.** Probe in my worktree (reverted): a directory seeded with `f4868.pdf`, then
`export_irs_pdf(--pay-by-check)`:

```
NO REFUSAL, NO WARNING FIELD.
dir = ["00_f1040.pdf", "02_f1040s2.pdf", "12A_f8949.pdf", "12_schedule_d.pdf",
       "71_f8959.pdf", "72_f8960.pdf", "f1040v.pdf", "f4868.pdf", "manifest.txt"]
```

The manifest that run produced (quoted in Seam 5 above) names the six stapled forms and the loose
voucher and is silent about `f4868.pdf` — so the envelope's own instruction sheet does not tell the
filer to leave it out.

**Minimal change.** In `export_full_return` (and the slice arm), before any byte: if
`out_dir.join("f4868.pdf").exists()`, refuse with the mirror of the R2 message — the 4868 is mailed
separately and its own page 2 says *"Don't attach a copy of Form 4868 to your return."*, so the return
packet may not be written on top of it. A refusal rather than a warning keeps the two directions
symmetric and costs the filer only a `--out` argument. Kill: seed `f4868.pdf`, assert the refusal and
that no packet file appeared.

### I-4 (Important) — the journey row's "closing note" against an unrecorded extension payment does not exist, and the silence costs the filer the payment twice

**Where.** `crates/btctax-cli/src/render.rs:5164-5231` (`render_extension`). The contract row is
`design/SPEC_form_4868_1040v.md:172`:

> | files, pays, then exports without recording `extension_payment` | Schedule 3 line 10 blank, line 37 too high by the payment; **the closing note is the only guard** | documentation only |

**What is wrong.** `render_extension`'s only closing note is *"Don't attach a copy of Form 4868 to your
return."* (`render.rs:5229`), which says nothing about recording the payment. The `recorded_extension_
payment` note (`:5208`) fires only in the opposite case — when a payment IS already recorded. So in the
case the journey row describes, the build says nothing at all.

The consequence is real money and btctax holds both halves of it. The filer runs
`btctax extension --pay 5000`, posts a $5,000 cheque, and nothing tells them the return must be told.
In October the return's Schedule 3 line 10 is blank, so 1040 line 33 is $5,000 short, line 37 is $5,000
high, and `--pay-by-check` prints a Form 1040-V whose box 3 asks for the $5,000 again. The figures are
all arithmetically correct given the stored inputs — this is not a computation defect — but the seam
between the two commands is exactly what the spec assigned a guard to, and the guard is absent. The
build already takes responsibility for the *other* direction of this same seam (the recorded-payment
note and the `--pay` default), which is what makes the omission an asymmetry rather than a scope line.

I record honestly that the row admits a weaker reading — "the closing note" could mean "there is only
a documentation sentence and it happens to be about something else". Under that reading the build
conforms. I judge the stronger reading correct because calling a note that is silent on the hazard "the
only *guard*" against that hazard is not a coherent sentence.

**Evidence.** `sed -n '5208,5231p' crates/btctax-cli/src/render.rs` — the whole tail of the renderer;
the `past_due` block and the "Don't attach" line are all that follow the line table. The field the
filer must set exists and is authorable (`btctax-input-form/src/spec/sections.rs:1037-1052`,

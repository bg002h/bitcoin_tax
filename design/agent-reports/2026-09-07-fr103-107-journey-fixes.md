## FR-103 — car-loan interest accepted in silence on a year with no Schedule 1-A → REFUSES

### What changed

`[schedule_1a]` data on a year whose Schedule 1-A does not exist now **refuses**, on both screen
tiers, naming the year, the window, and that the figures reach no line.

Three supporting pieces, each chosen so the rule cannot rot:

1. **`tax::tables::SCHEDULE_1A_YEARS`** — `2025..=2028` written **once**. `schedule_1a_params` tests
   membership of it; the refusal's sentence formats `{first}`/`{last}` from it. The table's `None`
   and the message a filer reads can no longer name different years when the provisions sunset.
2. **`Schedule1aInputs::carries_data()`** — a `let Self { tips, overtime, vehicles } = self;`
   **destructure with no `..`**. A fourth Part collected on that struct (Part V's senior deduction is
   the obvious next one) is a *compile error here*, not a silent hole in the refusal.
3. **`RefuseReason::Schedule1aNotOnThisYearsReturn { year }`** — placed **first** among the
   Schedule 1-A rules. Order is the finding, not taste: on TY2024 a claimed Part II would otherwise
   be met by `QualifiedTipsCautionNotMet`, which tells the filer to set three §224 conditions — three
   answers that cannot help, on a schedule that still will not exist once they are given.

### ★★★ The unit-level kill was NOT enough, and this is the most important thing in this report

The rule was written, its `screen_param_free` / `screen_inputs` KAT passed on both tiers — and the
shipped command **still imported the walk's TOML in silence.** Driving the real binary:

```
$ btctax --vault v.pgp income import --year 2024 --file hh.toml

EXIT=0
```

**Cause:** `income import` (`cmd/tax.rs`) ran `screen_param_free` on the parsed row **before**
`return_inputs::set` stamped `tax_year` from the row key (§G-15). At screening time `tax_year` was
the TOML's `0` — *"not stated"* — so **every year-scoped rule in the screen was structurally blind on
the one command that creates a row.** FR-103's was the first rule that needed the year, and it did
not fire on the exact case it was written for. No unit test could see this: they hand the screen a
`ReturnInputs` whose year is already set.

**Fix:** `return_inputs::stamp_year(&mut ri, year)` extracted from `set` (one rule, two call sites —
`set` now calls it too) and invoked in `cmd/tax.rs` immediately above the screen. The
disagreement refusal is `set`'s, called rather than copied.

After the fix, the walk's own case, and the other direction:


## FR-105 — NOT IMPLEMENTED. The controller's mechanism reading is REFUTED.

The brief: *"Verify the mechanism first, then implement… If your investigation shows my reading is
wrong, stop and say so in the report rather than implementing either way."* It is wrong. Nothing was
changed in the interview.

### The reading under test

> the gates are re-asked because the leaf has a *value* but no `AnswerRecord` — the value arrived by
> TOML import, and an imported value is **not testimony the filer gave to a question as worded**.
> Under this repo's answered-ness doctrine, re-asking is therefore **correct**, and suppressing it
> would silently promote imported data to sworn testimony.

### The measurement

A temporary probe in `cmd/answer.rs`'s test module (since removed; `live_questions_with` is private).
One dependent, every §152 gate leaf answered by `testonly::answer_all_dependent_gates`, every live
declaration answered, and an **empty** `answer_log` — the imported-TOML shape:

```
MEASURE-1 leaves answered, NO records:
  screen_param_free            = None
  interview_state.blocking.len = 0
  ... of which dependent-ish   = 0
  dependent-gate ASKS put to the filer = 15
MEASURE-2 leaves answered AND every gate carrying a Given record:
  answer_log.len               = 15
  dependent-gate ASKS put to the filer = 15
MEASURE-3 declarations (all answered, no records) still asked = 33
```

### What that says, in three parts

1. **The record is not the cause.** Adding a `Given` `AnswerRecord` for all 15 gates changes the ask
   count by zero (15 → 15). The stated cause does not produce the stated effect.
2. **The actual mechanism is unconditional re-asking.** `income answer` puts **every live question**
   to the filer every session — dependent gates and return-level declarations alike (33 answered
   declarations re-asked in the same run, each with `currently y` and Enter-to-keep). The ask loop
   (`live_questions_with` + the sweep in `answer_return_inputs`) never calls `answer_status` and never
   reads `ri.answer_log`. Liveness is `walk_dependent(ri, row).demands(gate)` for a gate and
   `(q.live)(&ri)` for a declaration — neither knows about answered-ness at all.
3. **The normative premise does not hold either, and this half matters more.** An imported leaf with
   no record **already stands as answered everywhere**: `screen_param_free` returns `None` and the
   panel's `blocking` is `0`. `screen_dependent_gates` gates on `gate_is_answered(d, gate)` — the
   *leaf* — and reads the record only for the `WordingChanged` staleness check; the `FORM_QUESTIONS`
   tier gates on `(q.get)(ri).is_none()` in exactly the same way. So suppressing the re-ask could not
   "promote imported data to sworn testimony": under the current design that promotion, if it is one,
   happens **at import**, and is a separate question from FR-105's.

The consequence for the ruling: *"make the prompt explain why it is asking when a value is already
shown"* would have the prompt state a reason the code does not have. The honest explanation is *"this
command re-asks everything; Enter keeps what is on file"*, which is a different sentence and a
different decision — the controller's, not mine.

FR-105 stays open. A **measured note** was added under its `FOLLOWUPS.md` entry recording the above,
so the next reader does not implement from the refuted premise. That note is the only FR-105 edit; it
is listed under Deviations.

## FR-107 — Form 5498-SA's y/n had no truthful answer for an early filer

### The decision, and why

**Chosen: reword. NOT the tri-state.**

The census tri-state already exists at the data level — `None` means *"not asked / not yet
received"* — and it **BLOCKS commit** (this module's own table). That is right for a broker who has
not mailed by February and will mail in March. It is a **brick** here: Form 5498-SA cannot arrive
before the return is due, so *not yet received* would block a correct return until June, permanently,
for every early filer. Giving this row the tri-state would convert a wording problem into an
unfileable return.

The honest fix is to ask a question whose answer the filer **has**: what is in their hands today, plus
what a *No* costs them (nothing).

### What changed

```
Form 5498-SA is furnished AFTER the filing deadline: the instructions for Forms 1099-SA and 5498-SA
tell the trustee "you must provide a statement to the participant (generally Copy B) by June 1", and
no line of Form 8889 reads this form — so if it has not arrived, answer No, and nothing on your return
changes. Do you have one or more Form 5498-SA IN HAND for this year (the trustee of a health savings
account sends one reporting the year's contributions and the account's fair market value)?
```

- The quoted clause is `i1099sa--2025.txt`'s own sentence (*Statements to Participants*, at `:369`),
  **verbatim and year-free** — the extract prints *"by June 1, 2026"*, and typing a year into a prompt
  asked of every year would be a second copy of derived data.
- The timing comes **before** the question for two reasons that happen to agree: the row's own
  invariant (`every_prompt_names_the_document_and_is_a_question`) requires a prompt that ends in `?`
  and cites its attributing instruction — my first draft ended in a period and dropped "instructions",
  and that test caught it in the gate — and a filer told the deadline before being asked answers once
  instead of answering and then wondering.
- No R15-banned word (`transfer` / `lot` / `FMV`); "fair market value" is spelled out, as before.
- The wording change moves the prompt hash, so a previously-given answer reads `WordingChanged` and is
  re-asked. That is R10.3 working: it is a different question.

### Where

`crates/btctax-core/src/tax/document_census.rs` (the prompt + the reasoning),
`crates/xtask/src/prompt_check.rs` (the clause, the per-clause `extract`, the kill).

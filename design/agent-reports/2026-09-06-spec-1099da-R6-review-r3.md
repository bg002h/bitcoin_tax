## T9 — verdict

**The design is right; the accessor as specified is wrong in two ways and the `report` clause it
depends on is under-partitioned.** Dropping the committed row is the correct call, and the kill at
`:379-380` is a genuine discriminator that reds on any create-a-row design — C-3 is properly closed.
But the fold specifies the accessor's precedence in one clause (`:288`, `:367-368`) and specifies it
**backwards** relative to `input_form_store::load`, the §6.1 precedence every other reader in the
product uses (**C-4**); and it says *"the DRAFT row's"* without ever saying whether that is `load`
(schema-gated, parked-aware, fails closed) or `get_draft_row` (raw, neither) (**I-10**). Both are
one-sentence fixes.

`resolve.rs` is genuinely untouched and needs to be: arm (2)'s predicate is the accessor, arm (1)'s
stays `return_inputs::exists`, and no path in R6 reaches the resolver except `report`, which the fold
correctly leaves on its existing ladder. Confirmed against `resolve.rs:76-134` and
`admin.rs:670-680`.

**The flush-cadence window.** `flush_tax_inputs_draft` (`main.rs:937-995`) fires on a section change,
the editor idle tick, flow close, and `q`, and the `NoTables` commit branch flushes explicitly
(`:1393`). So the journey the fold describes — answer the block, leave the flow or the app, run the
CLI export — always has the answers on disk. The only window is "the TUI is still open, mid-section,
before the idle tick", which is a pre-existing property of every draft and not worth a spec change.
**Not a finding.**

## The `report` clause (2a)/(2b) — verdict

**(2a) is exactly what the code does today — but only on the branch the fold happens to describe.**

the sentence, and the fold correctly claims nothing more.

**What is wrong is that (2a) and (2b) do not partition state (2).** See **I-11**.

## New findings

### C-4 (Critical) — the T9 accessor's committed-over-draft precedence inverts §6.1, so a filer who corrects a 1099-DA answer in the TUI files the superseded one, with no way to fix it and the product telling them it was saved

**Where.** Spec `:287-289` (arm (2)'s predicate) and `:367-368` (T9's accessor).
Code: `crates/btctax-cli/src/input_form_store.rs:133-137`, `:165-210`, `:302-326`;
`crates/btctax-tui-edit/src/main.rs:1385-1414`; `crates/btctax-cli/src/cmd/tax.rs:28`, `:200-207`.

**What is wrong.** The fold specifies, twice and identically: *"the committed row's
`broker_reporting` **if a committed row exists, else** the DRAFT row's."* That is the **opposite** of
`input_form_store::load`, whose own doc states the product's rule — *"the working return for a year,
resolved through the §6.1 precedence: **a draft shadows the committed row**"* — and which is what the
TUI, and therefore the filer's screen, uses (`persist.rs:82`). T9 introduces the only reader in the
product with the inverted precedence, and it is the one that routes a **filed** form.

The two rows coexist routinely, and on exactly the year arm (2) exists for:

1. `income import --year 2026` stores a committed row (`tax.rs:206`) — the fold names this as (2b)'s
   only creator, and it is permitted on a params-less year by design (`tax.rs:200-205`).
2. The filer opens the TUI. `load` returns `Committed(ri)` (no draft yet). They correct a 1099-DA
   answer — say `mixed` → `basis_matches`, or `basis_matches` → `proceeds_only`. `dirty` is set; the
   next flush point writes the **draft** (`main.rs:978`). The committed row is untouched.
3. They press commit. `commit` returns `NoTables` **and writes nothing and deletes no draft**
   (`input_form_store.rs:307-310`), and the TUI answers: *"{year} has no full-return tables yet
   (v1: TY2024) — inputs SAVED as a draft; finalize when tables publish."*
4. `broker_answers(conn, 2026)` per T9 finds a committed row → returns the **superseded** answers.
   `export-irs-pdf --tax-year 2026` routes the Form 8949 boxes and the Schedule D lines from them.

The filer files box G where they answered I, or box I where they answered G. Nothing on the printed
page, in the export report, or in the TUI says which answers were used — and the TUI shows the draft,
so every surface the filer can see agrees with the correction that was not filed. **There is no exit
through the designed authoring surface**: on a params-less year every TUI commit returns `NoTables`
forever, so the committed row can never be superseded from the TUI. `income import` again refuses
without `--force` (`tax.rs:28`), and nothing tells them that.

This is also the sentence at `:375-377` — *"its commit modal says the answers are held in the draft
and that the slice reads them"* — being **false** whenever a committed row exists. The fold
instructs the build to print a promise the fold's own precedence breaks.

**Minimal change.** One clause, and it makes the accessor a wrapper rather than a new rule. T9
becomes: *"`input_form_store::broker_answers(conn, year)` resolves the year's working return through
`input_form_store::load` — the §6.1 precedence every other reader uses, **a draft shadows the
committed row** — and returns its `broker_reporting`. It never introduces a second precedence: the
answers the export files are the answers the TUI shows."* Amend `:288` to match. Kill: a params-less
year with a committed row answering `basis_matches` **and** a draft answering `proceeds_only` →
`export-irs-pdf` writes box **I**, not G, and the same vector with the two swapped writes G — a test
that reds on the committed-first design and on any future re-inversion. `load` takes `&Connection`
and its stale-WIP delete is in-memory only, so it is callable from `export_irs_pdf_from_session`'s
`&Session` with no signature change.

### I-10 (Important) — T9 says "the DRAFT row's" without the §6.3 stale split or the `parked` flag, so a draft the store would discard or fail closed on can route a filed Form 8949

**Where.** Spec `:288`, `:367-368`. Code: `crates/btctax-cli/src/input_form_store.rs:32-34`,
`:165-210`, `:348-372`, `:385-393`.

**What is wrong.** There are two readers of that table and they behave oppositely, and T9 names
neither. `get_draft_row`'s own doc: *"The RAW draft row — **does NOT gate on `SCHEMA_VERSION`**
(Task 3 `load` decides discard-vs-refuse per §6.3)."* An implementer reaching for the raw reader —
the obvious choice for a fn described as "reads … the DRAFT row's" — gets both failures the store
was built to prevent:

- **A stale WIP draft** (`version != SCHEMA_VERSION`, `parked = 0`) is one `load` **deletes** as
  regenerable. It deserializes into today's `ReturnInputs` only because almost every field carries
  `#[serde(default)]` — so a schema change touching `BrokerReporting`'s own shape yields *silently
  partial or empty answers* out of a row the product considers unreadable, and those answers pick
  the boxes on a filed Form 8949.
- **A stale PARKED draft** is one `load` refuses outright — `Err(CliError::StaleParkedDraft)`, and
  the doc says why: *"it may hold carryover that exists ONLY in the draft (C-1), so REFUSE (fail
  closed) rather than destroy irreplaceable data."* The raw read **fails open** on precisely the row
  the store fails closed on.

Separately, and independent of staleness: a **version-current parked** draft is a real, reachable
state with no committed row at all. `park_to_profile` stashes the committed return into the draft
with `parked = 1` and then deletes the committed row (`:361-366`), after which `active_source`
reports `TaxProfile` (`:385-393`). The year has been deliberately switched *off* those inputs. T9's
accessor — under either precedence — returns that parked row's answers, so arm (2) prints a slice
routed from testimony the filer withdrew, on a year the product's own status line calls
`tax-profile`.

**Minimal change.** Two clauses in T9: *"the draft is read through `input_form_store::load`, so the
§6.3 stale split holds unchanged — a stale WIP draft is discarded (and the export surfaces the
`StaleNote`), a stale parked draft REFUSES (`StaleParkedDraft`) before any byte. A **parked** draft
(`parked = 1`) is a return switched to the tax-profile and carries no live answers: the accessor
returns `None` for it, so arm (2) falls to arm (3) rather than filing withdrawn testimony."* Kills:
a vault whose draft is at `SCHEMA_VERSION - 1` and `parked = 1` → `export-irs-pdf` refuses, `out_dir`
absent; the same at `parked = 0` → the stale row is discarded and the export takes arm (3), never
routing from it; a version-current parked draft → arm (3)'s refusal, not a printed slice.

### I-11 (Important) — state (2) has three sub-states, not two, and the one the fold omits is the modal R6 journey: `report` exits **1**, so the fold's own kill cannot pass

**Where.** Spec `:314-322` (*"State (2) has two sub-states"*) and the kill at `:392` (*"`report` in
state (2) exits 0 with the answers block and the note"*).
Code: `crates/btctax-cli/src/resolve.rs:76-134` (steps 2–4); `crates/btctax-cli/src/cmd/tax.rs:481-497`,
`:524-533`; `crates/btctax-core/src/tax/compute.rs:269-275`; `crates/btctax-cli/src/main.rs:218-220`.

**What is wrong.** State (2) is *"the ANSWERS are stored AND `full_return_for(year).is_none()`"*.
The fold partitions it by **where the answers live** (draft vs committed). But `report`'s outcome is
decided by a *different* variable — whether a `tax_profile` exists — and that splits (2a) in two:

- **(2a-i)** draft-only **and** a stored `tax_profile` → `resolve_core` step 2 →
  `Provenance::StoredProfile` → the crypto-delta report, exit 0. This is what the fold describes,
  and it is correct.
- **(2a-ii)** draft-only **and no** `tax_profile` → step 2 misses, step 3 is off by default, step 4
  returns `Provenance::Missing` with `profile: None`. `is_return_inputs_uncomputable()` is **false**
  (provenance is `Missing`, not `ReturnInputs`), so `resolve_and_screen` returns `Ready { profile:
  None }` rather than `Uncomputable`. `compute_tax_year` then returns
  `NotComputable(TaxProfileMissing)` — *"no tax_profile set for 2026"* — and `main.rs:218-220`
  **`return Ok(ExitCode::from(1))`**.

(2a-ii) is not an edge case: it is the *default* state of the filer R6 was written for — TY2026, the
TUI as the primary authoring surface (`:375-376`), the 1099-DA block answered, and no `tax-profile`
ever entered, because entering one is the *other* branch of the `t` toggle. Such a filer runs
`report --tax-year 2026`, sees `NOT COMPUTABLE [TaxProfileMissing]`, and gets exit 1 — while
`export-irs-pdf` happily prints their slice. Neither amended sentence fires either: both
`uncomputable_sentence` and `import_note` are (2b)'s, and neither is reached on this path
(`import_note` is printed by `income import`, `uncomputable_sentence` only via
`uncomputable_detail`). And the fold's kill at `:392` asserts exit 0 for "state (2)" without
qualification, so run on a (2a-ii) vault it **reds** — a kill the build cannot land as written.

**Minimal change.** Make the partition exhaustive and name the third outcome: *"(2a) the answers live
in the DRAFT row only. `report` resolves on the unchanged ladder: **with** a stored `tax_profile` it
renders the crypto-delta report and the answers block and exits 0; **without** one it is
`NotComputable [TaxProfileMissing]` and exits 1 exactly as today — the answers block still prints
(it is built after the resolve), and the NOT-COMPUTABLE line gains the clause `export-irs-pdf
--tax-year {y} still prints the crypto slice from these answers` so the filer is not told the year is
dead. A draft never shadows a `tax_profile`, so (2a) never *loses* a figure it had."* Then split the
`:392` kill in two, one per sub-state, naming the expected exit code for each.

# Lived journey walk — the btctax interview, played as a real filer

Two walks, both driven through the real CLI (`init` → `import` → `income import`/`income answer` →
`report` → `export-irs-pdf`), never the TUI. Every command below actually ran against the binary built
from this tree (`cargo build`, dev profile, at commit `121c8805`). All figures are invented; every SSN
is in the never-issued area-000 space; every EIN/TIN is drawn from `scripts/pii-scan-generic.sh`'s
`ALLOWED_EIN` list; every name is obviously fictional (surname "Testcase").

### 2.2 `btctax init`

`init` reads the vault passphrase from a secure prompt (no TTY → refuses immediately with
`error: io: No such device or address (os error 6)` — this is a **deliberate** secret-handling
refusal, not a bug; per this project's severity ruling secret-handling friction never gates). Driven
interactively via a pty (`pexpect`):

```
$ btctax --vault v.pgp init --key-backup key-backup.asc
Vault passphrase: ********************************
Confirm passphrase: ********************************
Initialized vault v.pgp (key backed up to key-backup.asc)
```

For every command after this, the documented `BTCTAX_PASSPHRASE` env var (`main.rs:51`) was exported
so later commands run non-interactively — the same mechanism the tool's own docs recommend for
scripting.

### 2.4 The household TOML (`income import`)

Per the spec's own §4.2 decision, box-level document data (W-2/1099/1098 amounts) and dependent
identity/§152-gate leaves have no CLI form-entry screen — they enter through `income import`'s TOML or
the TUI, exactly as the tool's own worked example (`docs/examples/examples.md` J6) does it. I built
`household.toml` with every dollar figure, every identity field, and the full dependent §152 gate set
(matching the shape of the shipped fixture `crates/btctax-cli/tests/fixtures/examples/nine_dependents_amt_inputs.toml`),
but **deliberately omitted** every "fail-loud, no safe default" gate — the whole `[documents]` census,
`home_sale.sold_main_home`, `can_be_claimed_as_dependent_{taxpayer,spouse}`, `foreign_accounts`,
`foreign_trust`, `sch1.hsa_activity`, `dual_status_alien`, `filing_form_4952`,
`other_out_of_scope_income`, `digital_asset_activity`, `claiming_mortgage_interest_credit`,
`filer_tin_issued_by_due_date`, the three mortgage declarations, all nine HSA (Form 8889) eligibility
gates, and the skippables (blindness ×2, DOBs, the sales-tax election, donation questions) — so that
those would be asked LIVE by `income answer`, exercising the real interview.

```
$ btctax --vault v.pgp income import --year 2024 --file household.toml
Imported full-return inputs for tax year 2024.
```

### 2.8 `export-irs-pdf` — the wall (Finding #2, the worst of the day)

```
$ btctax --vault v.pgp export-irs-pdf --out irs --tax-year 2024
error: IRS form fill: geometric read-back FAILED (mis-mapped cell): form1[0].Page2[0].f2_04[0]: x-center 446.0 not in column 1 cluster (504.0, 576.0) (mis-mapped column)
```

Exit code 2. **No `irs/` directory was created — zero bytes written, no packet at all.** Reproduced
twice, deterministically. `f2_04` is mapped in `crates/btctax-forms/forms/2024/f1040.map.toml:75` as
`line18 = "topmostSubform[0].Page2[0].f2_04[0]"` — Form 1040 line 18 (tax after Schedule 2 Part I), an
entirely ordinary money line present on any full return with tax due; nothing about my household's
data is exotic (no AMT, no unusual credits). The tool's own `export-irs-pdf --help` explains the
mechanism: *"Every written value is read back GEOMETRICALLY against the blank PDF's own field
coordinates and the fill FAILS CLOSED on any mis-placement — a wrong tax form is never written."* — a
deliberate safety property (never silently emit a misfiled PDF), but for this household it means the
safety net itself is what stops the return: the mapped field's real on-page x-position (446.0) does not
fall inside the money-column band the code expects (504.0–576.0) for that row, so the read-back check
that is supposed to catch a wrong VALUE instead caught what looks like a wrong CELL COORDINATE in the
line-18 map entry itself. No override flag exists (`--forms` is documented as *"ignored on a
full-return year"*).

## 4. FINDINGS

Ranked by how much each would matter to a real filer at a deadline.

**1. [CRITICAL — blocks filing entirely] `export-irs-pdf` crashes for the whole TY2024 full return.**
What I wanted: the printed packet for a fully-answered, fully-computed, correct return (the interview
completed with 0 blocking, 0 refusing). What happened, verbatim: `error: IRS form fill: geometric
read-back FAILED (mis-mapped cell): form1[0].Page2[0].f2_04[0]: x-center 446.0 not in column 1 cluster
(504.0, 576.0) (mis-mapped column)`, exit 2, **no output directory, no bytes written**. Class: a
refusal (fail-closed by design) that behaves like a crash from the filer's chair — a cryptic internal
coordinate message, no guidance, no workaround (`--forms` is documented as ignored on this path). What
I dropped: nothing — there was nothing to drop; the return itself is complete and correct
(`report`/`income project` both show it), only the PDF-writing step fails. This is a mainstream
household shape (MFJ, wages, mortgage, 4 kids, some Bitcoin gains) — not an edge case I constructed to
break something.

**2. [Important — silent, no signal at all] TY2024 has no field for car-loan interest, and says
nothing about it.** What I wanted: enter $1,850 of 2024 car-loan interest. What happened: `income
import` accepted a fully-detailed `[[schedule_1a.vehicles]]` row with **exit 0 and no message of any
kind**; the figure is stored (`income show` echoes it back) but the computation discards it entirely
(`Schedule1A::compute` returns `None` before 2025, "because the form has no line"), and grepping the
advisories module turns up nothing that ever mentions it. Every *other* out-of-scope item in this
codebase gets an explicit refusal or a printed advisory sizing the gap; this is the one silent
exception I found. What I dropped: the car loan, per the task's own year note — but a filer who didn't
already know that would have no way to learn it from the tool.

**3. [Important — misleading "success" near a deadline] `export-irs-pdf --tax-year 2025` silently
produces a 2-file crypto-only packet, with no indication the household's full-return data (already
imported) isn't in it.** What happened: `Filled IRS forms for tax year 2025 → irs/f8949.pdf
irs/schedule_d.pdf`, exit 0, no warning. The dispatch's "answers-driven" branch checks only the
TY2026+ broker-reporting table, so a TY2025 filer who carefully entered wages/dependents/mortgage/HSA
gets the exact same 2-form output as someone who never ran `income import` at all, with nothing in the
CLI output distinguishing the two cases.

**4. [Minor — UX friction, not incorrect] Dependent §152 gates are re-asked in full, every single
`income answer` session, even when every leaf was already truthfully answered via the imported TOML.**
For 4 dependents that is ~64 additional y/n/date prompts per session (bare Enter re-confirms the value
shown as "currently ..."). Correct, but tedious, and nothing in the prompt explains *why* an
already-answered gate is being asked again.

**5. [Minor — confusing message] The "before" answer panel undercounts.** The panel printed "BLOCKING
(36)" at the start of the session, but two more questions (`InterestOrDividendsWithout1099`,
`StateRefundWithout1099g`) became live and were asked mid-session, triggered by my own earlier census
answers within the *same* pass. By design (documented in-source as the M-3 seam-review fix), but the
panel a filer reads to gauge "how much is left" is a moving target they aren't warned about.

**6. [Minor — real but narrow ambiguity] Form 5498-SA's census row cannot honestly represent "haven't
received it yet, and don't need it."** Form 5498-SA is legally issued only after the April filing
deadline (contributions can be made up to the return's due date), so an early filer can never truthfully
answer "Yes" to the census row, yet the true state is "not yet received," not "will never receive." The
census is a plain y/n at the keyboard (unlike the tri-state the spec itself describes for "not yet
received"), so I answered "n" — a defensible but not literally true testimony given the household
doesn't need the form to compute its own HSA figures.

**Observed and correct (not findings, per the task's own list):** student loan interest deducting $0
despite a real $2,700 paid (§221 phases out completely at this income); Child Tax Credit / Credit for
Other Dependents both $0 despite 4 dependents, one under 6 and one 17+ (§24(b) phases the CTC out
entirely at $800k MFJ) — and the row-(7) grid still correctly differentiates Jasper (18, "Credit for
other dependents") from the other three (under 17, "Child tax credit"), proving the age-cutoff logic
works even though the dollar amount is moot here.

## 6. WHAT SURPRISED YOU

- **`init` needs a real TTY and gives no hint why.** Piped stdin gets `error: io: No such device or
  address (os error 6)` with no suggestion to use a terminal or the `BTCTAX_PASSPHRASE` env var. Once
  I found that var in `main.rs`, everything else scripted cleanly — but I had to go read the source to
  find it; nothing in `--help` mentions it. (Per this project's own severity ruling, secret-handling
  friction never gates — noting it here as a surprise, not a finding.)
- **The interview's actual question ORDER does not match the panel's print order**, and isn't the
  registry declaration order either — the document census came first in the live run, ahead of the
  dependent-status/foreign-account declarations the "before" panel lists first. Nothing wrong, just
  unexpected while scripting answers by keyword.
- **A census "No" can silently open a brand-new, unpreviewed question in the very same pass** — the
  "document-less income door" pattern (Finding #5) is a well-reasoned design (the form really does ask
  "did you have interest with no 1099"), but from the driver's seat it looks like the interview
  changed its mind about how many questions there are, mid-conversation.
- **The dependent grid asks you to reconfirm children you already fully described**, every time,
  forever (as far as I could tell in one session) — I expected "already answered" fields to be skip-
  or summary-only.
- **The PDF export's fail-closed geometry check is a genuinely good idea** (never silently mis-file a
  form) — and it is also, in this run, the single thing standing between a complete correct return and
  a printed packet, for an entirely ordinary household. The safety net and the blocker are the same
  code path.
- **`export-irs-pdf` never told me it was falling back** to a 2-file crypto slice on TY2025 even though
  I had just imported a whole household's worth of full-return data for that exact year in the same
  session. I had to read the dispatch source to learn the crypto-slice path was chosen because of an
  unrelated TY2026-only field being empty, not because of anything about TY2025 readiness per se.

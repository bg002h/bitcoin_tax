## Verdicts (a)–(e)

### (a) R4-I1 — placement is implementable exactly where claimed, and the kill has a real (if overstated) population

Confirmed live against `crates/xtask/src/label_reader.rs`. Inside
`every_mapped_line_lands_on_its_own_printed_label` (`:1577`), the walk over `every_map()` has exactly
two `continue` arms before any grid logic could run:

```rust
let stem = match &m.stem {                      // arm 1 — the geometry-fixture join, :1594-1600
    Ok(s) => s.clone(),
    Err(why) => { r.unwitnessed.push(...); continue; }
};
let join = match label_join(&stem) {             // arm 2 — the label-column join, :1601-1606
    Ok(j) => j,
    Err(why) => { r.unwitnessed.push(...); continue; }
};
```

"AFTER the `m.stem` geometry join and BEFORE `label_join`" places the new grid branch in exactly the
one gap that exists between these two arms — unambiguous, and matches the r4 report's own diagram of
the two arms.

**The kill has a population, but the spec overcounts it.** `GRID_MAPS` (`:1138-1163`) declares exactly
six `(year, form)` pairs: `(2017,f8949)`, `(2024,f8949)`, `(2025,f8949)`, `(2024,f8275)`,
`(2017,f8283)`, `(2025,f8283)`. `ls design/forms/geometry/` shows fixtures for only **four** of them —
`f8949--2024.json`, `f8949--2025.json`, `f8275--2024.json`, `f8283--2025.json`. The two `2017` entries
have **no** geometry fixture to delete: `f8949--2017.json` and `f8283--2017.json` do not exist, and the
`2017/f8283` `GRID_MAPS` reason string says so itself — *"unreachable: no TY2017 geometry"*
(`label_reader.rs:1162`). So "deleting a declared grid's fixture must still red its year" is
demonstrable on **4** maps, not the "six grid maps" the spec's new parenthetical claims. → new Nit,
below (does not affect whether the kill is implementable or correct — it is, on the four that have a
fixture).

## NEW findings

### NEW-M1 — Minor — the fold's citation for `name_line` overclaims what the cited TOML contains

**Where:** R1 (`:80-82`): *"…bound by NAME with the corpus's own cell names (`name_line`,
`address_street`, `address_city`, `address_state`, `address_zip`, `taxpayer_ssn`, `spouse_ssn` —
`forms/2024/f1040.map.toml:117-127` spells the same cells so)…"*

**What is wrong:** `forms/2024/f1040.map.toml:117-127` spells six of the seven names verbatim
(`taxpayer_ssn`, `spouse_ssn`, `address_street`, `address_city`, `address_state`, `address_zip`) —
verified by direct read. It does **not** spell `name_line`; that file's `[header]` table has no combined
name field at all, only `taxpayer_first`/`taxpayer_last`/`spouse_first`/`spouse_last`
(`f1040.map.toml:117-121`), and `grep -rn "name_line" crates/btctax-forms/forms/*/*.toml` returns
nothing across the whole corpus — the key does not exist in any committed map. `name_line` is instead a
Rust struct field, `ReturnHeader.name_line` (`crates/btctax-core/src/tax/packet.rs:338`) — which the
same spec's own table two lines earlier cites correctly as the *provenance* for `f1_4` (*"1 `f1_4` …
`ReturnHeader.name_line` (the 1040's own name line)"*). The choice of `name_line` as the new map's key
is reasonable (it mirrors the field it will hold), but the parenthetical falsely claims the cited TOML
range is where that spelling comes from.

This does not change what gets built — a builder who reads the whole document sees the correct
provenance in the table above — but it is exactly the shape of defect this project's own doctrine
singles out ("verify citations against current source"), and a reader who trusts the parenthetical
without checking would come away believing `f1040.map.toml` already establishes a `name_line`
convention it does not.

**Minimal change:** *"…bound by NAME with the corpus's own cell names for the address and SSN cells
(`address_street`, `address_city`, `address_state`, `address_zip`, `taxpayer_ssn`, `spouse_ssn` —
`forms/2024/f1040.map.toml:117-127` spells the same cells), and `name_line` for the combined name cell
(matching `ReturnHeader.name_line`, `packet.rs:338`, which is what fills it)…"*

### NEW-N1 — Nit — "the six grid maps are the population" overcounts the kill's actual population by half

**Where:** T5 (`:229`): *"…while a declared grid that has LOST its geometry fixture is still counted
unwitnessed by the join above it (kill: deleting a declared grid's fixture must still red its year —
the six grid maps are the population)…"*

**What is wrong:** `GRID_MAPS` names six `(year, form)` pairs, but only four have a geometry fixture on
disk today to delete: `design/forms/geometry/{f8949--2024,f8949--2025,f8275--2024,f8283--2025}.json`
exist; `f8949--2017.json` and `f8283--2017.json` do not. The `2017/f8283` entry's own reason string
says why: *"unreachable: no TY2017 geometry"* (`label_reader.rs:1162`). The kill is sound and
implementable on the four that do have a fixture — this is a precision issue in the parenthetical, not
a defect in the kill itself. (Inherited near-verbatim from r4's own Minimal-change suggestion, which
made the same "six … the only population it applies to" claim — not newly introduced by r5's phrasing.)

**Minimal change:** *"…the four declared grids with a geometry fixture today are the population
(`f8949--2024/2025`, `f8275--2024`, `f8283--2025`); the two TY2017 grids have no fixture to lose and are
already unwitnessed via the arm above."*

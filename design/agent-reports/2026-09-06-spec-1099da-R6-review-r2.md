## New findings

### C-3 (Critical) — T9's `ReturnInputs::default()` writes a filing status the filer never gave into the committed row, and that row shadows their stored `TaxProfile` — which makes the fold's own I-3 promise unreachable

**Where.** Spec `:339-346` (T9), interacting with `:308-313` (the I-3 fold).
Code: `crates/btctax-core/src/tax/return_inputs.rs:1340-1355`, `:913-914`, `:936`;
`crates/btctax-core/src/tax/classifier.rs:143-147`;
`crates/btctax-cli/src/resolve.rs:84-119` and `:50-52`;
`crates/btctax-cli/src/cmd/tax.rs:482-494`, `:219-236`;
`crates/btctax-cli/src/cmd/admin.rs:846`;
`crates/btctax-core/src/tax/compute.rs:270-272`;
`crates/btctax-tui-edit/src/edit/persist.rs:138-141`.

**What is wrong.** Four limbs, one root cause — T9 creates a **committed** `ReturnInputs` row out of a
type whose own doc calls it a test convenience.

1. **Fabricated testimony.** `impl Default for ReturnInputs` sets
   `filing_status: FilingStatus::Single`. Every neighbouring field's `Default` carries the comment
   *"`None` = never asked … Default() is a TEST convenience, so it must not fabricate an answer"* —
   `filing_status` fabricates one only because the frozen `FilingStatus` has no `Default` and the
   field is not `Option`. A committed `return_inputs` row is the filer's sworn input; a defaulted one
   swears Single.
2. **It falsifies a landed exemption's stated reason.** `classify()` exempts `filing_status` from the
   answered-ness census with the reason, verbatim: *"filing_status has no `#[serde(default)]` — a TOML
   without it refuses to parse, so **no default to launder** (§2.1)"*. T9 manufactures exactly that
   default. The census then reports the row as fully accounted-for while the single most consequential
   line on Form 1040 is an invention — the answered-ness invariant defeated by a premise rather than
   by a bug, which is why no existing test reds.
3. **It shadows the filer's stored `TaxProfile`, permanently.** `resolve_core` step 1 is
   `return_inputs::get(conn, year)`; on TY2026 `full_return_for` is `None`, so it returns
   `profile: None, provenance: ReturnInputs` and **never reaches step 2** (`tax_profile::get`).
   `is_return_inputs_uncomputable()` is then true and `resolve_and_screen` returns `Uncomputable`.
   Consequences, all new the moment a T9 row exists: `report --tax-year 2026` goes from *working off
   the stored `tax_profile`* to `Err`; `schedule_se.pdf` stops being written (`admin.rs:846` takes the
   `Uncomputable { .. } => None` arm); `optimize` and `what-if` share the ladder.
   **The fold's own I-3 sentence — *"renders the crypto-delta report … exiting 0"* — cannot hold**,
   because in state (2) the resolver hands back no profile at all and `compute_tax_year` raises
   `TaxProfileMissing` (`compute.rs:270-272`). The fold fixes `report`'s exit code and leaves its
   figure with no source.
   The TUI's commit modal already models this hazard — `persist.rs:138-141`, *"the commit modal's
   shadow warning (§9 create-row amendment): committing a full return for a year that also has a
   tax-profile leaves the profile saved [but shadowed]"* — and `commit_broker_answers_only`, as a new
   function, bypasses it.
4. **T9's third sentence is false.** *"`income import` of a file carrying only `tax_year` +
   `[broker_reporting.*]` reaches the same row."* A scripted scan of `ReturnInputs`'s body finds
   `filing_status` is the **only** field without `#[serde(default)]`, and `parse_return_inputs_toml`
   (`cmd/tax.rs:219-236`) is a plain `serde_ignored::deserialize` with no container default — such a
   file fails with *missing field `filing_status`*. This is not an accident to route around: it is the
   mechanism the classifier's exemption relies on.

Once TY2026's `FullReturnParams` land — the Jan-2027 window R6 is written for — the same row flips the
year from arm (2) to arm (1) (*"A year with inputs AND parameters is the full return, always"*), where
`ReturnHeader::build` refuses on the empty SSN. The filer who only ever answered broker questions is
then locked out of the slice they wanted, with an SSN error and no hint that `income clear` is the
exit. That is the closed loop C-2 raised, moved nine months downstream.

**Minimal change.** Do not create a committed `ReturnInputs` row at all. The answers are **already
persisted** on the path C-2 walked: the `NoTables` branch writes the whole working `ReturnInputs` —
`broker_reporting` included — into `return_inputs_draft` (`tui-edit/src/main.rs:1393`). Only the
*reader* is missing. So T9 becomes:

> **T9 — read the answers without committing a return.** A dedicated accessor
> `input_form_store::broker_answers(conn, year) -> Option<BrokerReporting>` reads the committed row's
> `broker_reporting` if a committed row exists, else the DRAFT row's. Arm (2)'s predicate becomes
> *"the answers are stored"* (that accessor is `Some` and non-empty), **not** `return_inputs::exists`;
> `resolve.rs` is untouched, so a draft still cannot shadow a `tax_profile`, and I-11 is not merely
> preserved but never approached. No row is created, so no `filing_status` is invented.
> Kills: TY2026 + a TUI commit of the 1099-DA block → the draft holds the answers,
> `return_inputs::exists(2026)` is **FALSE**, and `export-irs-pdf --tax-year 2026` reaches arm (2);
> the same vault with a stored `tax_profile` for 2026 → `report --tax-year 2026` still resolves
> `StoredProfile` and exits 0 (this is the kill that reds on the `ReturnInputs::default()` design, and
> it is the one T9 as written cannot pass); TY2026 + a params-less commit of the FULL return → still
> `NoTables` + draft (I-11 unmoved).

If the owner prefers a row after all, R6 must instead say that arm (2) requires a filer-stated
`filing_status` (i.e. `income import` is the only authoring surface, and the TUI's block hands the
filer a TOML) — and R1's *"reversing it means a `broker_reporting` vault table both arms read"*
(`:207`) must be reconciled with R6's *"No new vault table"* (`:329`); today the fold leaves both
sentences standing.

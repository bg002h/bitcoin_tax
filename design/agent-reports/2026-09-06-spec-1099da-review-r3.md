## NEW findings

### I-1 — IMPORTANT — the cohort's acquisition date is not computable at `form_8949`; the fold moved it OFF the only field that is

**Where:** spec R1 `:113-115` ("The date is the lot's **acquisition event date** (via `lot_id` → the
lot's origin event), NOT `DisposalLeg::acquired_at`"); hook row `:228`; T2 `:254-256`. Code:
`crates/btctax-core/src/forms.rs:118`, `crates/btctax-core/src/state.rs:331-357`,
`crates/btctax-core/src/project/fold.rs:1644-1650`, `crates/btctax-core/src/project/pools.rs:192,219`.

**What is wrong.** Both routes the sentence offers are dead at the named site.

1. `form_8949(state: &LedgerState, year: i32)` receives no event log, and `LedgerState` has no
   events field (`lots`, `holdings_by_wallet`, `disposals`, `removals`, `income_recognized`,
   `pending_reconciliation`, `blockers`, `stats`, `pseudo_synthetic_count`, `promoted_origins`,
   `shortfalls`). So `lot_id.origin_event_id` → "the lot's origin event" cannot be resolved.
2. `lot_id` → `Lot` (whose `acquired_at` *would* serve) fails for precisely the rows that need it:
   `finalize` pushes a lot into `st.lots` **only `if lot.remaining_sat > 0`**, and the pools
   `retain(|l| l.remaining_sat > 0)` after every consumption. A lot sold out by the disposal is
   **gone** from `state.lots` — the common case for a Form 8949 row.

So the cohort table, the load-bearing input to the whole box routing, has no defined value for a
sold-out lot, and the table has no "lot not found" row. The two force-fits are the r2 N-2 shape
again: fall back to `leg.acquired_at` (which R1 explicitly forbids, and which is the §1015 gift date
in the loss zone) or default to `Noncovered` (a silent wrong grouping, and it would also kill the
`BrokerCohortUnknown` trigger N-5 exists to create). Widening `form_8949` to take the events is not
cheap either: it is called from `packet.rs` inside core's assembly and from both TUIs off a
`LedgerState` snapshot, none of which hold the event log.

**Minimal change:** carry the fact forward on the leg, the way this codebase already solved the
identical problem. `LedgerState.promoted_origins` exists verbatim because a promoted tranche is
"indistinguishable from the leg alone" (`state.rs:345-352`). Add `acquired_event_at: TaxDate` (or
the derived `cohort`) to `DisposalLeg`, set in the fold where the `Lot` is in scope, and say so in
R1 and the hook table. Then `form_8949` needs nothing new, and the compiler reds every `DisposalLeg`
literal.

### I-2 — IMPORTANT — R2's routing has no rule for a row with no provider key

**Where:** spec R2 `:183-189` ("Per row, `(term, answer for the row's key)` → box"); R1 `:131-133`
(the key is `provider` = `Source::tag()`); code `forms.rs:118-166` (rows are emitted for **all**
legs), `state.rs:213-215` (`leg.wallet` may be `WalletId::SelfCustody`), `forms.rs:148`
(`box_needs_review = matches!(leg.wallet, Exchange{..})` — the code already distinguishes them).

**What is wrong.** A key exists only for `WalletId::Exchange { provider, .. }`. A **self-custody**
disposition — a peer-to-peer sale, a spend, a non-exchange venue — produces a Form 8949 row with a
cohort but **no provider and therefore no key**, so `(term, answer for the row's key)` is undefined
for it. The spec never says what box such a row gets on a live year. Today the code prints I/L for
every TY2025+ row (`forms.rs:135-146`), and T2 replaces that branch wholesale.

The two readings diverge sharply and neither is written down: if "no answer ⇒ unanswered ⇒ REFUSE"
is applied, every TY2026 return containing one self-custody sale is hard-blocked with no exit — a
refusal firing on a case where no 1099-DA can exist. If a silent `NotReported` default is applied,
the box is right but by exactly the hardcoded assumption R1's first sentence forbids ("the tool
never assumes"), with no rule and no kill holding it. The spec's own framing makes this the
`BrokerCohortUnknown` mistake in reverse.

This is inherited from r1/r2 rather than introduced by r3, but it became load-bearing when r3 made
the routing answer-driven for every row, and it is the second non-refusing divergence question (a)
asked for.

**Minimal change:** one sentence in R2 — *a row whose wallet is not an `Exchange` has no key and no
1099-DA can exist for it: `NotReported` routing (I/L), by mechanism, not by default* — plus a T2
kill: TY2026, one self-custody disposition and one answered exchange disposition → the self-custody
row prints I/L and does **not** refuse.

### I-3 — IMPORTANT — `BrokerCohortUnknown` is a hard refusal with no exit, on a provenance this product ships a feature for

**Where:** spec R1 `:110` (the Unknown row), R2 `:186` ("`Unknown` cohort → refuse (R1)"), T2
`:256-257`. Contrast `:87-88` and `:91-92`, where `BasisDiffers` and `Mixed` each name the per-lot
import as the exit.

**What is wrong.** The other three refusals tell the filer how to file anyway. This one does not.
A filer whose 2026 exchange-credited reward lot is sold in 2026 — `FmvAtIncome` (staking, mining,
interest, airdrop credited into the account) or `CardRewardRebate`, which is a **shipped FR-45
feature of this product** (`event.rs:36-51`) — is blocked from filing TY2026 entirely, and the only
escapes are deleting a truthful ledger event or misstating the provenance. `screen_absolute`'s own
history condemns exactly that shape in its doc comment ("escapable only by a false 'No' under §6065
or by deleting a truthful ledger event", `return_1040.rs:2637-2643`).

It is also unnecessary as a *correctness* device now that `Mixed` exists. The cohort is only a
grouping: because R1 `:116-118` enumerates each key's rows and the filer answers off the forms in
hand, a row placed in the "wrong" bucket still receives the answer its own form supports, and a
bucket whose forms disagree refuses as `Mixed`. So the Unknown refusal buys nothing the C-1 fix does
not already buy, and costs a hard block.

**Minimal change:** give it an exit, one sentence in R1. Either route Unknown lots to a **third key**
the filer answers (`(provider, Unknown)`, enumerated like the others — the filer holds the form and
can read box 2/box 9 off it), or place them in `Noncovered` and rely on `Mixed`; keep
`BrokerCohortUnknown` only for a lot with no resolvable provenance at all, and say what the filer
does about it.

### I-4 — IMPORTANT — the blind-spot paragraph cites the wrong authority, and the notice that governs TY2026 is committed in `legal/` and unread

**Where:** spec R1 `:127-129` ("That is the specific-ID question (Rev. Proc. 2024-28;
§1.1012-1(j)) the owner action T7 exists for — a standing lot-identification instruction to each
exchange is what makes the two partitions coincide"); T7 `:273-276`.

**What is wrong.** Two things, in an added paragraph whose whole job is to make the chosen blind spot
defensible.

1. **Rev. Proc. 2024-28 is not the specific-ID rule.** It is the §1012(c)(1) safe harbor for
   allocating *unused basis* per wallet/account as of Jan 1 2025 (`legal/SOURCES.md:36`, "Per-wallet
   basis transition + safe harbor"; `legal/research/REPORT_us_btc_tax_TY2025-2026.md:127-132`). The
   identification rule is §1.1012-1(j)(3) alone, which the spec already cites correctly.
2. **`legal/text/irs-guidance/Notice_2026-20.txt` governs this exact question for this exact year and
   is never cited.** Its title is "EXTENSION OF TEMPORARY RELIEF UNDER SECTION 1.1012-1(j)(3)(ii)";
   §3.03 sets the relief period as "beginning on January 1, 2025, and ending on December 31, 2026";
   §4.02(2) permits adequate identification by "Recording a standing order on the **taxpayer's books
   and records** … before the units covered by the order are sold"; and §4.05 says that where the
   taxpayer has done so, "for Federal income tax purposes the units sold … are the ones identified in
   the taxpayer's books and records **regardless of whether the information reported by the broker to
   the taxpayer matches** the taxpayer's books and records."

That changes both halves of the sentence. The blind spot is not merely undetected for TY2026 — on a
books-and-records identification it does not make the return **wrong**, which is a materially
different risk statement for the owner. And T7's action is stated as the only path ("a standing
lot-identification instruction to each exchange"), when §4.02(2) offers one btctax is already
positioned to satisfy, and §4.03 says the §1.1012-1(j)(3)(ii) broker-deeming rule *stops applying*
when the taxpayer takes the books route. T7 is a NOW owner item with a date, so the wrong framing
costs real effort. This is the repo's own recurring class (the tax-authority hierarchy; the answer
being in the manual), against a source already committed here.

**Minimal change:** in R1 `:127-129`, drop Rev. Proc. 2024-28, keep §1.1012-1(j)(3), and add one
sentence: *for the relief period through 2026-12-31, Notice 2026-20 §4.02/§4.05 makes a standing
order recorded on the taxpayer's own books an adequate identification, and the units so identified
govern regardless of what the broker reports* — then restate T7 as "record the standing HIFO
identification in the filer's own records **and/or** instruct each exchange", with the notice cited.

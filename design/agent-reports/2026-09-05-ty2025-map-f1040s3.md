## 2. Gate item 4 — the expected line set, enumerated FROM the form's extracted text

Read off the right-aligned **margin** label column of `design/forms/extract/f1040s3--2025.txt`
(`pdftotext -bbox`, bare sub-letters resolved against the last numeric parent). Never a range, never a
hand list — **35 labels**:

```
1 2 3 4 5a 5b 6 6a 6b 6c 6d 6e 6f 6g 6h 6i 6j 6k 6l 6m 6z 7 8 9 10 11 12 13 13a 13b 13c 13d 13z 14 15
```

Labels with **no box**, *derived* (a label to which the join assigned nothing) rather than hand-listed —
the derivation matters, because a hand-list of headings reds on nothing when a heading is dropped:

| label | printed text | |
|---|---|---|
| `6` | `6   Other nonrefundable credits:` | heading for 6a–6z |
| `13` | `13  Other payments or refundable credits:` | heading for 13a–13z |

So **33 entry-taking lines**; `6z` and `13z` each hold **two cells** (description + amount) → **35 entry
cells**, plus the 2 identity cells = the 37 fields `dump-fields` reports. Nothing is left over in either
direction: no label with a box is unaccounted by the map, and no box is unclaimed.

## 3. Gate item 2 — the per-line printed-text check

CENTRE**), run **per column** — AMOUNT gutter `x≈488–498`, MID gutter `x≈392–407`, margin `x≈40–56`.
Result: AMOUNT 14 labels ↔ 14 boxes, MID 19 ↔ 19, **no label unclaimed, none claimed twice**. Then the
line each map entry *claims* was asserted equal to the line geometry *derives*, for all 35 non-identity
boxes: **AGREE, 35/35**.

Every sentence quoted in a doc comment was checked verbatim against the extract (whitespace-normalised

## 4. What changed vs TY2024 — ★★★ the printed form did not move, the field suffixes did

`diff -b` over the two extracts (past the generated header) reports **only** the year stamp, a new
`Created 11/17/25` footer, and two inserted blank lines. Same line numbers, same sentences, same
cross-references. The recon (`design/ty2025/recon-year-port-delta.md`) called Schedule 3 **TRIVIAL** and
attributed the 39→37 field drop to *"a minor internal consolidation with no line-number or content change
observed."* The line-number/content half of that is right. The "minor" half is not: **the consolidation
renumbers every field after line 6m.**

Both write-in description areas collapsed from a **pair** of single-line cells into **one Multiline
cell** — verified from the PDF's own `/Ff` (qpdf `--qdf`, names UTF-16BE-decoded): `8392704` =
Multiline|DoNotScroll on exactly those two boxes, `8388608` on every other money box. Losing one field at
6z and one at 13z shifts the suffixes down:

**A copy of the TY2024 map would look right and be wrong on 4 of its 5 mapped lines**, with no printed-
text signal anywhere to prompt a re-read:

- `line8 = f1_26` would write the total nonrefundable credits into the box printed **"9 Net premium tax
  credit. Attach Form 8962"** — not an omission but *fabricated testimony*, asserting a marketplace-
  insurance credit with no 8962 behind it.
- `line10 → f1_28` writes line 11; `line11 → f1_29` writes line 12.
- `line15 = f1_39` names a field that **does not exist** in this PDF, so the payments total never reaches
  the page and the filer is billed for money already paid.

Only `[identity]` and `line1` survive a blind port. This is the concrete instance of the brief's rule —
the TY2024 map is not evidence about the TY2025 PDF.

Two TY2024 traps re-verified on the TY2025 PDF rather than carried across:

- **Root subform is still `topmostSubform[0]`** — *not* the `form1[0]` used by Schedules 1 and 2. I
  checked this per form because it is not stable across forms: Schedule A's TY2025 root **is**
  `form1[0]` (`form1[0].Page1[0].f1_1[0]`), changed from its own TY2024 `topmostSubform[0]`.
- **Line 6e is still a live ReadOnly widget** — `/Ff 8388609`, the *only* ReadOnly field on the form, and
  it still consumes a suffix number (`f1_12`=6d, `f1_13`=6e reserved, `f1_14`=6f). Anything that walks
  suffixes and "skips reserved lines" misaligns 6f–6m by one.
- The **`f2_` prefix slip survives, renumbered**: the 6z description is `f2_22[0]` on **page 1**, and
  there is no `f1_22` anywhere in the document. (TY2024's was `f2_23`.) A page heuristic keyed on the
  leaf prefix contradicts the `Page1[0]` subform segment, which is correct.

## 5. Census disposition — all 30 unmapped fields, with a reason

**Direction, stated once:** the whole form is credits and payments. Every line only ever reduces tax or
increases the refund, so each blank is a class (B) forgone benefit — lawful silence that can only
**overstate** tax. There is no understatement risk anywhere on Schedule 3. That is why the per-field
reasons stay short. No field is classified `gap`.

## 7. Unresolved / for the controller

1. **`extract-geometry` was deliberately NOT run.** It writes `design/forms/geometry/<stem>.json`, a
   shared tracked file outside my two-file allowance, so I reproduced the same join myself from
   `pdftotext -bbox` + `dump-fields` in scratchpad. If the committed geometry fixture is wanted for
   `f1040s3--2025`, someone with a wider allowance must generate it. **`label-census f1040s3--2025` cannot
   run until they do** — it hard-errors on the missing fixture.
2. **No Rust was compiled or run** (per the brief — nine agents share the cargo lock). So the map is
   verified against the gate's *predicate*, transcribed into Python, not against the gate *binary*.
   Specifically unproven-by-execution: that `Schedule3Map::parse` accepts this file (it parses as TOML
   and carries every required key — `form`, `year`, `identity{name,ssn}`, `line1`, `line8`, `line10`,
   `line11`, `line15` — with `[census]` tolerated as an unknown table exactly as in TY2024).
3. **Wiring is not done and was not mine to do.** `Schedule3Map::for_year` matches only `2024` and
   `map.rs`/`pdf.rs` carry only `SCHEDULE_3_MAP_2024` / `SCHEDULE_3_PDF_2024`; `field_census.rs`'s gate is
   pinned to `year = 2024`. All three are Rust source.
4. **Suggested B1 kill-test for whoever wires this up.** The defect this port exists to prevent is
   *silent*, so it deserves a planted-defect test rather than trust: set `line8` to `f1_26` (the TY2024
   suffix) and assert the suite reds. Today nothing would — the census union check still balances,
   because `f1_26` is a real field on the form; it is merely the *wrong* one, and it would move to the
   mapped set while line 9 vanished from the census. A `line → field` assertion driven by the geometric
   join is what would catch it. Filing that is the controller's call; I did not touch test source.

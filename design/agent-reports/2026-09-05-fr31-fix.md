# FR-31 — the fix: a `--to-wallet` self-transfer link can no longer book the same coins twice

**Branch** `fix/fr31-transfer-double-basis`, branched from `feat/schedule-1a-ty2025` (`ff839ce7`).
**Gate** `make check` → **2799 tests run, 2799 passed, 12 skipped**, clippy `-D warnings` clean.
**Scope** FR-31 only. FR-32 and FR-33 were not touched (one incidental observation on FR-33 is at the
end, filed as an observation, not a change).

---

## 1. What was wrong, restated from the code

Moving coins between your own wallets is the most common operation a bitcoin holder performs, and
btctax could book that one movement twice — relocating the real lot into the destination *and*
minting a fresh origin lot for the coins arriving there. Doubled basis shrinks gain, so it
**understates tax**, and the ledger said nothing.

Three limbs, all controller-verified in the brief and all re-confirmed against the source here:

1. `resolve.rs` — the entire `consumed_ins` block sat inside
   `if let TransferTarget::InEvent(in_id) = &tl.in_event_or_wallet`. `--to-wallet` is
   `TransferTarget::Wallet`, so it never marked the arriving deposit consumed.
2. `reconcile.rs` — `bulk-link-transfer` hardcodes `TransferTarget::Wallet(dest)`, so the bulk path
   structurally *cannot* consume an in-leg.
3. `conservation.rs` — FR9's `balanced` compares satoshis only, and the phantom lot increments
   `sigma_in` and `sigma_held` by the same amount, so it still balanced.

And the tool routed the filer in: the unconsumed deposit keeps `UnknownBasisInbound`, the exact
selection key of `bulk-classify-inbound-self-transfer`.

## 2. What I chose, and what I rejected

### CHOSEN — (a) refuse, in the engine. The guarantee.

A new **Hard `BlockerKind::SelfTransferDoubleBooked`**, raised in `resolve` at a new `1e-FR31` pass
placed immediately after the existing `[R0-I1]` cross-type overlap guard (the exact precedent: a
check that needs *every* pass-1e map, because a `ClassifyInbound` may be appended after the link).

It fires when a live `TransferLink{Wallet(w)}` coexists with a deposit at `w` that

- is a `TransferIn` on its **effective** payload (so a `ClassifyRaw`'d row is covered),
- is **not** in `consumed_ins` and **not** in `passthrough_skip` — both fold to `Op::Skip` and mint
  no origin lot, so neither can be a double-book, and
- **could be the same movement** under the shared pairing predicate.

The blocker names the link decision, the out-leg, the deposit, both amounts and both dates, and the
two commands that resolve it. `event` is the **inbound** leg, which is what lets the CLI's bulk plan
filter on it by id.

**It refuses; it never repairs.** No decision is excluded, no pairing is applied, nothing is
auto-matched. `--to-wallet` names a destination, not an in-event, so *which* deposit it meant is the
filer's testimony — and the owner's self-transfer policy ("matched pairs are **confirmed**, not
auto") is exactly the ruling that forbids software from answering it. A Hard blocker is the
fail-closed answer: `compute_tax_year` step (1) refuses every year while one is open, so no
understated number can reach a return, and the filer clears it by naming the true pairing or voiding
the wrong decision.

**Deliberately included: the UNCLASSIFIED deposit.** It doubles nothing *yet*. But it carries the
`UnknownBasisInbound` that walks the filer into variant C, so the refusal has to reach it — that is
the difference between fixing the defect and fixing only its last step.

**Deliberately not keyed to `SelfTransferMine`.** The mechanism is "an origin lot is minted at the
wallet a link relocates into", so `Income` and `GiftReceived` classifications are caught by the same
clause and are covered by tests. Enumerating the variants we happened to observe is the compression
this repo has a standing rule against.

### CHOSEN — the pairing predicate becomes ONE definition

`crates/btctax-core/src/project/pairing.rs` (new) now owns the amount tolerance
`max(fee_sat, ceil(0.005 × principal))` and the ±2-day directional window, lifted **verbatim in
behaviour** out of `Session::self_transfer_match_plan`, which now calls it.

That matters beyond tidiness: `match-self-transfers` **proposes** pairs and this guard **refuses**
them, and two spellings would let the tool propose a pairing the engine never notices, or refuse one
it will not offer to confirm. The module doc states the asymmetry that makes a heuristic admissible
at all — the predicate may only ever propose or refuse, never pick and apply, so a false positive
costs a blocker naming both events and can never move a filed number.

`WalletId::label()` moved to core for the same reason (the refusal renders a copy-pasteable
command); `btctax_cli::render::wallet_label` now delegates.

### CHOSEN — the routing half, both directions

- `Session::bulk_self_transfer_in_plan` **withdraws** any deposit carrying
  `SelfTransferDoubleBooked` from the offer. The engine would refuse it afterwards anyway, but an
  offer to make the ledger worse is not a neutral offer.
- `Session::bulk_link_transfer_plan` gained a third bucket, `skipped_would_double_book`: an outflow
  whose other leg is already an **unreconciled** deposit at the destination is **held back and
  listed**, not linked. This is limb 2 answered structurally — the bulk form can only write
  `--to-wallet`, so it must not write it where an in-leg exists. Candidates come from the
  `UnknownBasisInbound` blocker set, which is exactly the un-consumed population (a consumed deposit
  raises no blocker), so this can never withhold a row whose pairing the filer already named.
- `main.rs` prints the held-back rows in both the dry run and the apply, each with the
  `match-self-transfers` line to run. Never silent.

### REJECTED — (b) a `--to-event` form on `bulk-link-transfer`

A single `--to-event` value is meaningless across N rows, and a bulk *auto*-pairing is precisely the
auto-matching the owner's policy rejects. The precise, confirmed-per-pair form already exists and is
already wired to the same `link_transfer(out, InEvent(in))` call:

```
reconcile match-self-transfers <in> <out> --action relocate
```

So the gap was never a missing command — it was that nothing pointed at it. It is now named in the
blocker text, in the bulk preview, and in `--help` for both `link-transfer --to-wallet` and
`bulk-link-transfer --to-wallet`.

### REJECTED — (c) a Σbasis conservation invariant, **with a demonstration**

A Σbasis identity in `conservation.rs` is **structurally blind to this defect, for the same reason
the sat identity is.** The phantom origin lot adds its basis to the "in" side and to the "held" side
by the same amount, so a basis identity balances exactly as `sigma_in == … + sigma_held` does. It
would have been a green instrument that never discriminates — B1's named failure mode, shipped
deliberately.

This is not an argument in prose. It is pinned by a test:
`variant_d_wallet_link_plus_stated_basis_is_refused` asserts that after the doubling
`conservation_report(&st).balanced` is **still `true`**, with the reason in the assertion message. If
someone later adds a Σbasis identity believing it closes FR-31, that assertion is the thing to read.

The detection genuinely has to be the pairing check, and it has to live where the decisions are —
`resolve`. One instrument, one place.

## 3. Test-first, and the B1 kills

`crates/btctax-core/tests/self_transfer_double_book.rs` (14 tests) was written **before** the guard.
Five assert the refusal, nine assert it stays silent — the discrimination half, which is what makes
the first five mean anything.

Three independent mutations, `cp` backups only, all restored (`git status` clean of stray edits):

| # | mutation | result |
|---|---|---|
| 1 | `continue` at the top of the guard loop | **5 failed, 9 passed** — exactly the positive cases, exactly the discrimination cases surviving |
| 2 | `legs_could_be_one_movement` → `return true` | **3 failed** — `different_amount`, `outside_the_window`, `preceding_the_withdrawal` |
| 3 | drop the `consumed_ins || passthrough_skip` exemption | **2 failed** — `already_consumed_by_another_link`, `dropped_by_a_passthrough` |

Mutation 3 is worth recording: on the **first** attempt it killed nothing, because no test then
exercised a ledger with both a `--to-wallet` link *and* a consumed deposit at the same wallet. The
exemption clause was untested. Two tests were added to make it load-bearing, and the mutation was
re-run to confirm the kill. That is B1 working as intended — the honest kill-test could not be
written without finding the blind spot.

The two CLI guards were mutated together (`if false && …` on both filters) and both new CLI tests in
`crates/btctax-cli/tests/reconcile.rs` went red, then green on restore.

The `pairing` module ships its own unit tests for the tolerance arithmetic, the window direction, and
the `None == None` txid trap (two absent txids must not pair everything).

## 5. Residue, honestly

**One accepted false positive, no escape hatch.** A `--to-wallet` link to a wallet that has *both* an
unrelated arrival of near-identical size inside the ±2-day window *and* a real arrival that was never
imported produces a refusal with no in-event to name. The filer must void the link. There is no
"these are distinct movements" confirmation decision in the ledger vocabulary. This is fail-closed
and cannot move a filed number, so it does not gate — but it is a real dead end for that filer, and
adding such a decision (mirroring `SelfTransferPassthrough`'s shape) is the clean follow-up.

**Not touched, by instruction:** FR-32 (§1015 loss cap on the reconstructed-basis path) and FR-33
(post-hoc `LotSelection` with no made-date guard).

**One observation on FR-33, for whoever owns it:** the `1e-FR31` guard I added sits between the
`[R0-I1]` passthrough guard and the pseudo-reconcile injection at `1f`. The §A.4 `LotSelection` block
FR-33 concerns is much further down (~`resolve.rs:1500+` after this change shifts line numbers).
Nothing I did touches it, but line-number citations in FR-33 will have drifted by roughly +90 lines
on this branch.

**A note on the suite.** The first `make check` run reported one `SIGKILL` in
`btctax-forms::full_return_forms` at test 1865/2797. It passes in isolation and passed on all three
subsequent full runs; it is memory pressure from `make check` running the full suite and clippy
concurrently, not a defect. Recorded because a green run after a red one deserves the explanation.

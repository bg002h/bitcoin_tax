## Wired (5 call sites)

1. `--basis` (`ClassifyInboundSelfTransfer`)
2. `--donor-basis` (`ClassifyInboundGift`) — named
3. `--fmv-at-gift` (`ClassifyInboundGift`) — same command as #2; leaving it unchecked while fixing
   `--donor-basis` on the identical decision would have been a half-fix, since both feed the same
   §1015(a) dual-basis computation (inflating `fmv-at-gift` disables the loss cap in favor of the
   larger donor basis — can only make an allowed loss bigger, i.e. understate tax).
4. `--fmv` (`ClassifyInboundIncome`) — becomes the acquired lot's basis via `BasisSource::FmvAtIncome`,
   the same class of risk as `--basis`, one indirection removed.
5. `--fmv` (`SetFmv`) — the later-correction path for the same Income FMV; `ManualFmv` can only ever
   target an `EventPayload::Income` (enforced upstream by `guard_decision_conflict`/`would_conflict`,
   confirmed by reading `resolve.rs`'s "ManualFmv targets non-Income event" refusal), so it shares
   exactly the risk of #4.

## Not wired (noted, not fixed — out of FR-37's scope)

- **`--fee`** (`reclassify-outflow`): reduces net proceeds/increases deductible cost, not literally
  "basis." Same understate direction, but a structurally different field FR-37 doesn't name. Candidate
  for a future follow-up.
- **`optimize consult --proceeds`, `what-if sell/harvest --price`**: Mode-2 what-if calculators —
  explicitly "Writes NOTHING," a fundamentally different risk class from a filed decision.
- **`classify-raw`'s embedded `usd_cost`** (`Acquire{sat, usd_cost, ...}` JSON): a **wider** gap than
  FR-37 — it has **no validation at all**, not even the `>= 0` sign check `parse_nonneg_usd_arg` gives
  every CLI flag. Real basis-bearing risk, but a different class of defect; flagged, not fixed here.

## Did the predicate need to change for a basis field?

**Yes, in one respect (date), no in another (threshold).** `amount_fmv_advisory` was written for
`--amount`, where "market value" is priced at the **event's own date** — correct for proceeds/FMV, but
wrong for a **basis** field, whose true reference is the coins' **original acquisition** date, which can
predate the event by years.

Renamed the function to `sats_as_dollars_advisory` and parameterized it by `field`/`what` (so the
message text stays accurate per call site) — **one implementation, reused at all 6 call sites** (the
pre-existing `--amount` site plus the 5 new ones), never a second copy. For the date, each caller passes
the semantically correct anchor when known (`--acquired` for self-transfer basis, `--donor-acquired` for
donor basis) and falls back to the receipt date when that override was omitted (`--fmv-at-gift` and
`--fmv`-on-Income always use the receipt/event date directly — that IS the semantically correct date for
an FMV-at-receipt field).

The **100x threshold itself needed no change**: the classic sats/dollar mixup is off by a ratio of
`1e8/price`, which is enormous — >>100x — at *every* BTC price this app has ever priced (even 2013's
~$1,000/BTC gives 100,000x). So even the RECEIPT-date fallback (an approximation, not the true
acquisition date) still reliably catches the real mistake on a basis field, and a legitimate historical
low basis can never trip a false positive — the check is `amount > 100 × market_value`, and a real,
smaller-than-market-value basis is on the wrong side of that inequality by construction. This reasoning
is spelled out in `sats_as_dollars_advisory`'s doc comment in `reconcile.rs`.

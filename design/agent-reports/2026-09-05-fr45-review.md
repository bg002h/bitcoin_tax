# FR-45 review — `7cfabdbe` "a Gemini card reward is an Acquire at FMV, not a zero-basis transfer"

> **Redacted for privacy (owner instruction, 2026-09-05).** Exact transaction counts from the
> maintainer's real Gemini export were replaced with qualitative wording before this repo went
> public. No finding, severity, file reference, reasoning or conclusion was altered.

**Verdict: the change is CORRECT in its tax treatment and its refusal, and the four new adapter tests
plus the ring test do discriminate. But the predicate is guarded only against a varying *value* and
not against a missing or blank *column*, which silently restores the exact defect it fixes — proven
by execution, not argued. 0 Critical / 2 Important / 3 Minor / 1 Nit.**

Scope: `7cfabdbe` and its diff only. `make check` greenness, the four mutation counts, the owner's
tax determination, and the three declared out-of-scope residues were taken as settled per the brief.

## What I verified as CORRECT (no finding — recorded so a later reader does not re-derive it)

Read, not inferred from doc comments or the commit message:

- **Match-arm ordering is sound.** `crates/btctax-adapters/src/sources/gemini.rs:213` is the guarded
  `"credit" if is_card_reward(...)` arm and `:238` is the general `"credit"` arm. Rust matches
  top-down, so the guard wins; the general arm is unreachable for a reward row. Confirmed by
  execution: the four new tests pass and `a_genuine_on_chain_credit_is_still_a_transfer_in` sees
  exactly one `TransferIn` out of four `Type=Credit` rows.
- **`Direction::In` is right on both sub-arms**, and using `In` on the *refusal* sub-arm (rather than
  `Trade`, which the file's other `Unclassified` emissions use) is a quiet win, not a slip: the
  semantic mint key is `dir|utc_ms|type|sat` (`normalize.rs:54-60`), so a reward row keeps the
  *identical* `source_ref` whether it resolves to an `Acquire` or refuses to `Unclassified`. A later
  price-cache refresh therefore re-imports the same row under the same ref.
- **The price date matches the lot date.** The adapter prices at `tax_date(utc, tz)`
  (`gemini.rs:214`); the fold sets `Lot.acquired_at = eff.date()` (`fold.rs:790, 813`) which is
  `tax_date(utc, original_tz)` (`fold.rs:725`). No off-by-one-day between basis and holding-period
  start.
- **The refusal is loud, not silent.** `Op::Unclassified` raises `BlockerKind::Unclassified`
  (`fold.rs:1628-1633`), so an unpriced reward gates the return rather than vanishing.
- **No stale-price back door.** `BundledPrices::usd_per_btc` / `LayeredPrices::usd_per_btc`
  (`crates/btctax-adapters/src/price.rs:58, 100`) are exact-date lookups with no gap fill and no
  carry-forward, so "the dataset cannot price the day" really is a refusal and not a stale number.
- **Σin conservation is unchanged by the reclassification.** The old path
  (`TransferIn` → `SelfTransferInbound` lot) already did `stats.sigma_in += sat` at `fold.rs:1385`;
  the new path does it at `fold.rs:824`. No double-count, no gap.
- **Blast radius of `BasisSource::CardRewardRebate` is clean.** There are exactly four `match bs`
  sites on the enum plus two rank/tag maps, and I read all six:
  `btctax-cli/src/render.rs:48` (`"card_reward_rebate"`), `btctax-core/src/forms.rs:276`
  (`H::Other`), `btctax-tui-edit/src/edit/form.rs:1770` (ring) and `:1789` (display), and
  `btctax-tui/src/tabs/tags.rs:29` (rank `10`, matching declaration order — `event.rs:54` puts the
  variant last) and `:57` (tag). **No site got a wrong arm and no site has a catch-all `_` that
  would have absorbed it.** The two documented `basis_source` *overwrite* sites
  (`fold.rs:1093` relocation → `CarriedFromTransfer`; `transition.rs:101` Path-A →
  `ReconstructedPerWallet`) exempt only `EstimatedConservative`; a `CardRewardRebate` lot is
  overwritten there exactly like `ExchangeProvided`/`FmvAtIncome`, carrying `usd_basis` and
  `acquired_at` intact. That is correct and consistent.
- **`Form8283HowAcquired::Other` is the right mapping, and it is display-only.** `how_acquired` has
  exactly two consumers: `form8283.rs:385, 431` (prints the literal string via `how_str`, where
  `Other` → `"Other"`) and `render.rs:1151` (the CSV column). It reaches **no** arithmetic. The
  §170(e) deduction is computed from holding period and basis at `fold.rs:1568-1607`, never from
  `how_acquired`. The commit's claim "drives no deduction math" checks out. Substantively, "Other"
  is also the honest answer on column (d): a rebate is neither a purchase of *this* property nor a
  gift, and `Review` (lost origin) would overstate the uncertainty.
- **The four new adapter tests are not vacuous, and the reported mutation counts are internally
  coherent.** Reverting the predicate reds all four (acquires 0≠2, phrase-count 0≠2, TransferIn 3≠1,
  unclassified 0≠1); byte-exact reds three (test 3 survives because the unpriced row still refuses);
  a `$0` on unpriced reds three (test 4 survives). That matches 4/3/3/1 exactly, which is decent
  independent evidence the mutation run was real.
- **The ring test genuinely discriminates a dropped *or* added ring entry.** The walk is a fixed
  9 steps and asserts it returns to `start`; drop an entry and it lands elsewhere, add one and the
  9th step no longer closes. (Its blind spot is narrower and is M-2 below.)

## Important

### I-1 — A missing or blank `Specification` column silently restores the zero-basis defect, with no error, no counter and no test

**Severity: Important.**
`crates/btctax-adapters/src/sources/gemini.rs:213` (`row.opt(cols::SPECIFICATION)`) together with
`crates/btctax-adapters/src/read.rs:39-44`:

```rust
/// Optional column: `None` if absent OR blank.
pub fn opt(&self, col: &str) -> Option<&str> { ... .filter(|s| !s.trim().is_empty()) }
```

**What is wrong.** The commit reasons carefully about failing open on the *value* — "a byte-exact
match would fall back to the zero-basis TransferIn path — SILENTLY" — and pins that with a test. It
then leaves the *identical* fail-open one level up, on the column. `opt` cannot distinguish "the
column is absent" from "the cell is blank" from "the row is short", and all three route a reward
straight past the guard into the general `"credit"` arm at `:238` → `TransferIn` → the inbound
self-transfer path → zero basis. Nothing counts it, nothing warns, no `Unclassified` is emitted, and
`GroupOutput` has no field that would reveal it.

The assumption is not obviously safe: **the repo's own §9.1 fixture, whose header list is documented
as "the REAL §9.1 header names", does not contain `Specification`** (`tests/gemini.rs:595` says so
explicitly, which is why FR-45 needed a second fixture). The one place in this repo that records
Gemini's confirmed schema omits the column the whole fix now depends on.

**Failure scenario (executed, not hypothesised).** I ran a throwaway probe test against this commit's
adapter with a real `BundledPrices`:

- Input: a Gemini XLSX whose header omits `Specification`, one row
  `Date=2025-03-02 11:00:00, Type=Credit, BTC Amount BTC=0.00100000`.
  Output: `TransferIn(TransferIn { sat: 100000, src_addr: None, txid: None })`.
- Input: the same file *with* the header present but the cell blank on the reward row.
  Output: `TransferIn(...)` again.

Both are the pre-FR-45 defect verbatim: 0.001 BTC at zero basis, over-stating the gain on every later
disposal, silently. Multiply by every reward row in a real export.

**Minimal fix.** Do not make `Specification` a required column via `row.get` — that would break the
§9.1 fixture and every legacy export. Instead check the *header set* once, before the row loop, and
refuse rather than mis-classify:

```rust
let has_spec = rows.first().is_some_and(|r| r.cells.contains_key(cols::SPECIFICATION));
```

and in the `"credit"` general arm, when `!has_spec` and the row carries neither `Tx Hash` nor
`Deposit Destination`, emit `Unclassified` (+`out.unclassified += 1`) instead of `TransferIn`. Pair it
with a B1 negative test — a fixture with the header removed asserting the row does *not* become a
`TransferIn`. (Note the adjacency: the general rule "a credit with no `Tx Hash` cannot be a
self-transfer" is the brief's declared out-of-scope item. The in-scope half is narrower — the adapter
must not silently assume a column it now depends on is present.)

### I-2 — `fee_usd` is hardcoded to zero, discarding a stated fee; the test that "pins" it asserts the hardcode and cannot fail

**Severity: Important.**
`crates/btctax-adapters/src/sources/gemini.rs:224`:

```rust
// A reward payout carries no fee; measured every reward row blank.
fee_usd: Usd::ZERO,
```

**What is wrong.** The abs-normalised `fee` for this row is already computed at `gemini.rs:120-123`
and is what every other arm in the file uses (`:169`, `:178`). This arm throws it away and substitutes
a constant. Because `Lot.usd_basis = a.usd_cost + a.fee_usd` (`fold.rs:817`), a stated fee is silently
*removed from basis* — understating basis, overstating gain. It is the "hardcoded zero vs computed
zero" shape this project has a standing rule about: the two are indistinguishable on the page.

The accompanying assertion in
`crates/btctax-adapters/tests/gemini.rs` —
`assert_eq!(a.fee_usd, Usd::ZERO, "a reward payout carries no fee")` — reads as an observation about
Gemini's data but is in fact a tautology over the code's own constant. It is satisfied for **every**
input, so it can never discriminate.

**Failure scenario (executed).** Same probe harness; a reward row identical to the fixture's row (1)
but with `Fee (USD) USD = 1.25`:

```
Acquire { sat: 100000, usd_cost: 88.71, fee_usd: 0, basis_source: CardRewardRebate }
```

The $1.25 is gone. Basis $88.71 instead of $89.96, and the three FR-45 tests stay green.
Taxpayer-adverse, and small per row, but it is data destruction rather than a refusal — the opposite
of the discipline the rest of the commit applies.

**Minimal fix.** One character class of change: use the value already in hand.

```rust
fee_usd: fee,
```

and change the test to feed a fee-bearing reward row and assert the fee reaches the basis, so the
assertion has something to be wrong about. If the owner prefers the refusal posture instead, the
alternative is to emit `Unclassified` when a reward row carries a non-zero fee — but silently
zeroing it is not one of the two defensible options.

## Minor

### M-1 — A negative-amount reward credit now mints a *basis-bearing* phantom lot, flipping the error direction toward understatement

`crates/btctax-adapters/src/sources/gemini.rs:118` (`.abs()`, pre-existing) meeting the new arm at
`:213`.

`sat` is unconditionally `.abs()`ed before the match. A `Type=Credit` row with a negative
`BTC Amount BTC` whose `Specification` contains the phrase — a reward reversal or clawback booked as
a negative credit — therefore becomes a *positive* acquisition. Executed:

```
input:  Type=Credit, Specification="Gemini Credit Card Reward Payout Reversal", BTC Amount BTC=-0.00100000
output: Acquire { sat: 100000, usd_cost: 88.71, fee_usd: 0, basis_source: CardRewardRebate }
```

The `.abs()` is pre-existing and this row was already mis-handled before FR-45 — but the *direction*
changed. Before, the phantom landed as a $0-basis inbound-self-transfer lot (taxpayer-adverse). Now it
lands with $88.71 of real basis in the pool, available to a later disposal — the understatement
direction, which is the one this project treats as worse. Not Important because no negative-amount
reward row has been observed (the full-export measurement is the evidence against it), and the `.abs()`
predates the commit. **Fix:** in the reward arm, refuse (`Unclassified`) when the parsed BTC amount is
negative, rather than inheriting the file-wide `.abs()`.

### M-2 — The ring test's `ON_RING` is a hand-written list, so it cannot catch the one thing it exists to catch: a *future* variant left off the ring

`crates/btctax-tui-edit/src/edit/form.rs:4102-4118` (`const ON_RING: [BasisSource; 9]`).

The test is a genuine improvement and does red on a dropped, duplicated or added ring entry (the walk
length is fixed at 9 and must close). But its exhaustiveness against the *enum* is a hand-list. Add an
11th `BasisSource` variant, wire it to `=> ExchangeProvided` off-ring, and nothing goes red — which is
precisely the FR-45 situation the test was written to prevent recurring. This repo's standing rule is
that the expected set is derived, never hand-listed.

**Fix:** put an exhaustive `match` inside the test that classifies every variant as on-ring or
off-ring and build `ON_RING` from it. The compiler then reds (`E0004`) on any new variant, forcing an
explicit decision, and the walk assertions stay as they are.

### M-3 — `tags.rs` states a byte-for-byte parity guarantee against the CLI tag that no test holds

`crates/btctax-tui/src/tabs/tags.rs:69-70`:

```rust
// FR-45 — must MATCH the CLI tag byte-for-byte; a divergence here is a UI/CSV split.
BasisSource::CardRewardRebate => "card_reward_rebate",
```

I grepped both crates: **no test references `basis_source_tag` in either `btctax-cli` or
`btctax-tui`, and the string `card_reward_rebate` appears in no file under any `tests/` directory.**
The compiler forces an arm to *exist* in both maps; nothing forces the two strings to agree. A
guarantee asserted in a comment with no test that reds when it is removed is the shape B1 exists to
outlaw. Consequence is a display/CSV inconsistency, not a wrong figure — hence Minor.

**Fix:** the tag vocabulary is a stable CSV contract, so it belongs in one place. Either move
`basis_source_tag` into `btctax-core` and have both crates call it, or add one test asserting the two
functions agree for every variant (via the same exhaustive-match technique as M-2).

### M-4 — A stated `USD Amount USD` on a reward row would be discarded in favour of the dataset close

`crates/btctax-adapters/src/sources/gemini.rs:215` — `resolve_fmv(None, date, sat, prices)`.

`resolve_fmv`'s entire first branch (`normalize.rs:16-18`) exists to prefer an exchange-stated USD
value over the dataset, and this call hardcodes it away. That is consistent with the file's other
callers (`river.rs:146, 164` also pass `None`), so it is not an inconsistency — but here the commit's
own justification is an empirical measurement ("blank on every reward row"), and the code does not degrade
gracefully if that measurement stops holding. Gemini stating a value would be *better* evidence of
FMV than a daily close, and it would be thrown away silently.

**Fix:** `resolve_fmv(row.opt(cols::USD_AMOUNT).map(|s| parse_usd(SRC, row.line, "USD Amount USD", s)).transpose()?.map(|u| u.abs()), date, sat, prices)`
— which is what that parameter is for, and costs nothing when the column is blank.

## Nit

### N-1 — A dust reward rounds to a $0.00-basis `CardRewardRebate` lot on a *priced* day

`fmv_of` rounds to cents with `MONEY_ROUNDING` (ties-to-even, `conventions.rs:22-23`), so any reward
under ~half a cent yields `Some(0.00)` — an `Acquire` that passes the refusal check and produces a
zero-basis lot. Executed: 5 sat on 2025-03-02 →
`Acquire { sat: 5, usd_cost: 0.00, fee_usd: 0, basis_source: CardRewardRebate }`.

The refusal test's message — "an unpriced reward must never become a zero-basis lot — that is the
original defect" — remains literally true as scoped (it filters on the *unpriced* case), so this is
not a false PASS. And $0.00 *is* the correctly rounded FMV; the bound is half a cent per lot, ~$3 over
the full reward set. Recorded only so a future reader is not surprised to find zero-basis `CardRewardRebate`
lots in a vault and conclude the fix regressed.

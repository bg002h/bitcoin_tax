## Direction analysis — Schedule 2 is the dangerous form

Every amount line here **increases** what is owed, so a blank that should have carried a number is an
**understatement**. "Not modelled" is therefore not by itself adequate provenance. The lines a filer
btctax serves could actually owe, and what stops each from printing silently blank — all re-verified
in current source, not copied from the TY2024 prose:

| line | mechanism | verified at |
|---|---|---|
| 5 — Form 4137 unreported tips | W-2 box 8 allocated tips > 0 **refuses** (`RefuseReason::AllocatedTips`) | `return_refuse.rs:1208` |
| 13 — W-2 box 12 uncollected SS/Medicare | `INERT_BOX12_CODES` is a fail-closed **allowlist** (D,E,F,G,H,S,AA,BB,EE,DD); A/B/M/N refuse with `UnsupportedBox12Code` | `return_refuse.rs:29`, `:1220` |
| 2 — AMT | **mapped and populated** (see above), no longer in this class | `packet.rs:656` |
| 6 — Form 8919 | safe direction: such income reaches btctax as SE income and pays **both** halves via Schedule SE line 4 ⇒ overstates | — |

**The new line-4 exemption block runs the other way and is safe by construction.** Checking box 1, 2
or 3 asserts an *exemption* from self-employment tax; btctax has no exemption input, computes
Schedule SE in full, and leaves the boxes blank — which **overstates** the tax for an exempt filer
and can never understate it for anyone. That is why the three boxes and the write-in are `unmodeled`
and not `gap`. Authority for what each box means, transcribed from `design/forms/extract/i1040gi--2025.txt`
("Line 4 / Self-employment Tax"): box 1 = approved Form 4361; box 2 = approved Form 4029; box 3 = the
write-in case, entering **"EAS"** (citizen abroad covered by a foreign social-security system),
**"ECI"** (community income the filer did not earn) or **"EN"** (notary-public fees) *"on the entry
space next to box 3."* This matches the position already recorded for Schedule SE line A and
`crates/btctax-cli/LIMITATIONS.md:321` (*"Clergy self-employment is OUT OF SCOPE … Use a preparer."*).

## Open items for the controller — none blocking

1. **`Schedule2Map::for_year` is still TY2024-only**, and `map.rs` / `pdf.rs` have no
   `SCHEDULE_2_MAP_2025` / `SCHEDULE_2_PDF_2025` constant. Wiring those is Rust work outside this
   agent's write scope. This map is inert until then, and TY2025 full-return support remains
   fail-closed on `tax_tables.rs::ty2025_full_return_must_stay_fail_closed_until_complete`.
2. **`field_census.rs::census_accounts_for_every_field` is hard-coded to `let year = 2024;`.** The
   gate that would enforce this map's exactness does not yet run against 2025. I reproduced it
   faithfully by hand (result above), but it is a checker that cannot currently fail on this file —
   exactly the class B1 exists to name. Extending the test to iterate both years is a small edit and
   should land with the wiring.
3. **A `field_census` trap worth knowing.** `map_and_census` treats *any* quoted chunk containing
   `[0]` and `.` as an FQN, so writing a bracketed field name inside a `reason = "…"` string
   registers as a **phantom** and reds the gate. My first draft did exactly that in three reasons
   and the gate caught it; the cross-year notes now live in comment lines instead. Worth a line in
   `design/forms/README.md` — every other TY2025 map being written today can hit it.
4. **I did not commit `design/forms/geometry/f1040s2--2025.json`** (brief: touch only the two output
   files). Other agents appear to be keeping theirs. Regenerate in one command if the fixture set
   should be uniform: `./target/debug/xtask extract-geometry f1040s2--2025`.
5. **`Schedule2Map`'s Rust doc comment still carries the obsolete "line 2 is $0 by construction"
   prose** (`map.rs:1524-1531`). Untouched here; the TY2025 map states the corrected position.

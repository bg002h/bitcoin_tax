# Independent DESIGN review — spec 1099-DA **R6** (S10 reversed)

- **Artifact:** `design/SPEC_1099da_broker_reporting.md` §"R6 — the crypto slice files a LIVE year
  from the stored answers…" (lines 276–316), read against `design/ROADMAP_STATUS.md` §0a S10.
- **Worktree HEAD:** `d63a971a`. Read-only; no source edited, no commits, no subagents.
- **The one question:** is R6 sound and complete for the owner's ruling *"we will need to have
  option to file 2026 tax year with crypto sales"*, such that an implementer building it **exactly
  as written** gives the filer a correct, fail-closed TY2026 crypto-slice filing path?
- **Verdict: NO — 2 Critical, 5 Important.** The rule's *shape* is right (route from the stored
  answers, refuse the unsettled key, never let a slice print where the full packet can). What is
  wrong is that two of its load-bearing sentences assert capabilities the build does not have:
  the slice's Schedule D **cannot** print the per-box lines, and the TUI input form **cannot**
  store the inputs arm (2) dispatches on. Both are one-sentence claims in R6; both are false at
  `d63a971a`; each on its own makes the TY2026 journey either wrong or impossible.

Machine-checked before writing (values pasted, not recalled): `full_return_for(2026)` is `None`
(`ty2026_full_return_must_stay_fail_closed`; `cargo nextest run --locked -p btctax-adapters -E
'test(ty2026)'` = 12 passed). `TEMPLATE_YEARS` is generated from "any pdf **or** map bundled"
(`build.rs:172-176`). `ScheduleDMap` carries `line1b/line2/line8b/line9`, but
`grep -n "line1b\|line2\b\|line8b\|line9\b\|line3\|line10" crates/btctax-forms/src/schedule_d.rs`
returns exactly two hits: `:78 &map.line3` and `:96 &map.line10`.

## Per-lens findings

### 1. Journey — the owner's 2027-season path

Walked (a) finals bundled / no `FullReturnParams`, (b) TUI input form → answer the seeded Form
1099-DA block → commit, (c) `export-irs-pdf --tax-year 2026`.

**Step (b) does not happen.** `input_form_store::commit`
(`crates/btctax-cli/src/input_form_store.rs:309-311`) returns `CommitOutcome::NoTables` when

`crates/btctax-tui-edit/src/main.rs:1385-1408` then flushes a *draft* and says *"2026 has no
full-return tables yet (v1: TY2024) — inputs SAVED as a draft; finalize when tables publish."*
Arm (2)'s predicate is `return_inputs::exists`
(`crates/btctax-cli/src/return_inputs.rs:137-145`), which reads the **committed** `return_inputs`

Divergences tried, classified:

| self-custody-only TY2026 vault | not live → slice fills I/L | correct (R1 kill holds) |

| `--pay-by-check` / `--forms full-return` on arm (2) | refuse (they sit after the `exists` branch) | correct, but see M-2 |

### 2. Fail-closed — can arm (2) print a box the answers did not choose?

**No, for the 8949 box itself.** `route_8949_boxes`
(`crates/btctax-core/src/forms.rs:139-183`) errors rather than defaults on
`None`/`Mixed`/`BasisDiffers`, and a keyless (self-custody) row keeps the mechanism's I/L.
`screen_broker_reporting` (`return_refuse.rs:888-980`) additionally refuses an answer nothing reads.
That half of R6 is sound.

**Yes, for Schedule D.** The box the 8949 page carries and the Schedule D line its total lands on are
chosen by two different code paths, and only one of them was built → **C-1**.

**Screens the full return runs that arm (2) does not:** `screen_inputs`,
`screen_compute_dependent`, and every row of `screen_absolute` **except**
`screen_broker_reporting`. Of those, exactly one bears on a form the slice *prints*: the Form 8283
restriction row (`return_1040.rs:2660-2680`), which arm (2) now skips while holding the adverse
answer → **I-5**. `screen_inputs` (SSN shape, negative inputs, filing status) touches nothing the
slice emits — correctly omitted, but R6 should say so. The promote gate and the pseudo attestation
gate already run on the slice arm (`admin.rs:718-726`) and need no change.

No cell is left undefined by R6's three arms, and R1's liveness and R6's arms do not disagree. The
one place two rules *appear* to disagree — R1's N-3 "the slice is CLOSED on a LIVE year" versus

### 4. `report` and the readiness surfaces

`report --tax-year 2026` with inputs stored returns `Err` at `crates/btctax-cli/src/cmd/tax.rs:492`,
**before** the `render_broker_answers` block at `:518-533` — so the surface R1 makes mandatory

unreachable on the one year R6 exists for → **I-3**. `uncomputable_sentence` gaining a clause does
not fix that; it describes the refusal, it does not lift it.

`import_note`'s sentence is still *literally* true about `report`, but it is (a) the only thing
`income import` prints after storing the TY2026 answers and (b) interpolated verbatim into
`slice_broker_refusal` (`admin.rs:2019-2030`), where it will now sit inside R6's new "a full return
is not required" sentence and contradict it → **I-4**.

### 5. The TUI export

`snap.broker_answers` exists and carries the stored answers per year (`tui/src/app.rs:139`), so the
data is there. Two things are wrong: `do_export` passes `None` for `answers`
(`crates/btctax-tui/src/export.rs:212`), and — the question the brief asks — **the ordering does not
hold**: `mkdir_owner_only_exclusive` is at `:184`, `write_form_csvs` (inside which
`routed_8949_rows` raises the broker refusal) at `:205` → **I-2**. Every existing `do_export` test
uses a `SelfCustody` wallet (`:833`), so the live path has never been observed — a B1 gap, not
merely an untested branch.

### 6. The finals gate

R6 says "TY2026 prints nothing until its Form 8949 and Schedule D FINAL revisions are bundled
(`SUPPORTED_YEARS` is the template years)". `SUPPORTED_YEARS` is `TEMPLATE_YEARS`, generated as
*any year with at least one bundled pdf **or** map* → **I-1**.

The other two candidate gates: a **TaxTable** is *not* required (the slice omits Schedule SE when
`table_for` is `None`; TY2026's table is bundled anyway, `tax_tables.rs:79`), and **price coverage**
binds only a `Filable` year (`year_readiness.rs:78-86` sits inside the `YearStatus::Filable` arm), so
a slice-filing `preparing` TY2026 is never checked against a short dataset → **M-5**.

### 7. Kills

R6's list discriminates arm (2) from arm (1) (TY2024 + inputs → full packet) and from arm (3)
(TY2025 + inputs → prints), and it does cover "routing from the answers but skipping the unread
check" (the unread refusal is named). Missing kills are given per finding below; the one that matters
most is **M-3** — the stated Schedule D kill asserts only that line 1b carries the G total, which a
filler writing *both* 1b and 3 would pass while double-reporting the same proceeds.

## Findings

### C-1 (Critical) — the crypto slice's Schedule D cannot carry the per-box lines, so a routed G/H/J/K packet reports its totals on the "Box C or I" / "Box F or L" lines

**Where.** Spec line ~289: *"The slice's Schedule D carries the per-box lines (1b/2/8b/9) exactly as
T4 prints them."* Code: `crates/btctax-cli/src/cmd/admin.rs:832-834` (`fill_schedule_d(&totals, …)`);
`crates/btctax-forms/src/lib.rs:182-185`; `crates/btctax-forms/src/schedule_d.rs:63-120`;
`crates/btctax-core/src/forms.rs:480-485` (`ScheduleDTotals`).

**What is wrong.** T4 built lines 1b/2/8b/9 on the **full-return** chain only — `ScheduleDLines`
(`crates/btctax-core/src/tax/printed.rs:963-1022`), filled by `fill_schedule_d_full`. The slice uses
a different pair: `schedule_d(state, year) -> ScheduleDTotals`, which has **no box dimension at all**
(only `st` / `lt`), and `fill_schedule_d_totals`, which writes exactly `map.line3` (`:78`, comment
*"Line 3 (Part I total = Box I)"*) and `map.line10` (`:96`, *"Line 10 (Part II total = Box L)"*).

So an implementer building R6 as written ships this: Form 8949 pages boxed **G**, and Schedule D
line 3 — *"Totals for all transactions reported on Form(s) 8949 with Box C or Box I checked"* —
carrying their entire proceeds/basis/gain, with 1b blank. That is a wrong return of exactly the class
this spec was written to close (Fable plan review C1), and it is self-contradictory on its face: no
8949 page in the packet has box I checked. The map is not the blocker — the 2025 map already carries
the FQNs (`forms/2025/schedule_d.map.toml:15` line1b, `:17` line8b) — the aggregation and the filler
are.

**Evidence.** `ScheduleDTotals { st, lt }` (`forms.rs:480-485`); the two-hit grep over
`schedule_d.rs` recorded in the header; `ScheduleDLines`'s own doc comment says *"since spec 1099-DA
T4; a G or H page-set lands on 1b/2"* — a promise the slice path cannot keep.

**Minimal change (a build task, not wording).** R6 replaces the sentence with:

> **T8 — the slice's Schedule D, per box.** Add `schedule_d_by_box(rows: &[Form8949Row])` in
> `btctax-core::forms`, aggregated from the **ROUTED** rows (never re-derived from `state`, so the
> page-set and the schedule cannot disagree), and extend `fill_schedule_d_totals` to write
> `line1b`/`line2`/`line8b`/`line9` from it, leaving `line3`/`line10` to the I/L residue **only**.
> A box group with no rows writes nothing.
> Kill: a live-regime `basis_matches` slice → `f8949.pdf` carries a G page-set, Schedule D **line 1b**
> carries the G total **and line 3 is BLANK**; on a G+I mix each total lands on its own line and
> `1b_d + 3_d == st.proceeds` cross-foots.

### C-2 (Critical) — the journey R6 names cannot store its own precondition: the TUI input form cannot commit `ReturnInputs` for a year with no `FullReturnParams`

**Where.** Spec lines ~296-300: *"the answers stay on `ReturnInputs` … authored through the TUI input
form — whose Form 1099-DA block is seeded from the ledger's keys on a basis year — or `income
import`."* Code: `crates/btctax-cli/src/input_form_store.rs:302-326`;
`crates/btctax-tui-edit/src/main.rs:1336`, `:1385-1408`;
`crates/btctax-cli/src/return_inputs.rs:137-145`.

**What is wrong.** `commit` opens with

```rust
let (Some(table), Some(params)) = (table, params) else {
    return Ok(CommitOutcome::NoTables); // I-11: no tables for this year → write nothing
};
```

and the caller binds `params = fr.full_return_for(year)`, which is `None` for 2026 by design
(`tax_tables.rs:169-173`, held by `ty2026_full_return_must_stay_fail_closed`). The TUI therefore
saves a **draft** into `return_inputs_draft` and tells the filer *"inputs SAVED as a draft; finalize
when tables publish."* Arm (2) dispatches on `return_inputs::exists`, which queries `return_inputs`.
The two tables are distinct (`input_form_store.rs:18`, `:79`).

Net effect for the owner in the 2027 season: answer the seeded 1099-DA block, commit, run
`export-irs-pdf --tax-year 2026`, and land on arm (3)'s refusal telling them to *"answer them in the
TUI input form … then export again"* — the exact thing they just did. A closed loop with no exit
except discovering that only `income import` writes the committed row. R6 is therefore **incomplete
for its own ruling**: it names two authoring surfaces and only one of them reaches the arm it
defines. (The I-11 guard itself is a *user decision* — "store full return before tables" — so the fix
must not relax it for the full-return path.)

**Minimal change.** R6 gains a task:

> **T9 — commit the answers on a params-less year.** Either `input_form_store::commit` splits its
> gate (a year with a `TaxTable` but no `FullReturnParams` commits when `screen_inputs`'s
> params-independent rows pass), or — the narrower option — a
> `commit_broker_answers_only(year, &BrokerReporting)` writes/merges **just** `broker_reporting`
> onto the committed row (creating it from `ReturnInputs::default()` when absent), leaving the I-11
> finalize guard on the full return untouched. The TUI's commit modal offers it on a live year whose
> params are absent, and says which of the two it did.
> Kills: TY2026 + a TUI-committed 1099-DA answer → `return_inputs::exists(2026)` is TRUE and
> `export-irs-pdf --tax-year 2026` reaches arm (2); TY2026 + a params-less commit of the *full*
> return → still `NoTables` + draft (I-11 unmoved).

If the owner prefers the smaller build, R6 must instead **delete the TUI from its authoring list**
and say plainly that `income import` is the only surface reaching arm (2) until the finals land — but
that contradicts R6's own "seeded from the ledger" sentence and T6's block, so the task above is the
honest reading of the ruling.

### I-1 (Important) — the finals gate R6 names is not the gate the build has; a partially-ported TY2026 writes a half-populated packet directory

**Where.** Spec lines ~304-306. Code: `crates/btctax-forms/build.rs:172-176`;
`crates/btctax-forms/src/lib.rs:97`; `crates/btctax-cli/src/cmd/admin.rs:802-806` then `:808`
(`mkdir_out`).

**What is wrong.** `TEMPLATE_YEARS` is *every year with at least one bundled pdf **or** map*:

```rust
.filter(|(_, stems)| stems.values().any(|(pdf, map)| *pdf || *map))
```

The January-2027 port is not atomic, and Form 4868 for TY2026 is needed on **2027-04-15**, i.e.
plausibly *before* the return forms are transcribed. The moment any single TY2026 template lands,
`SUPPORTED_YEARS.contains(&2026)` is true, the slice's pre-check passes, `mkdir_out` runs,
`basis_methodology.txt` and `form_8275.txt` are written (`admin.rs:811-817`), and only then does
`Form8949Map::for_year(2026)` raise `UnsupportedYear` (`map.rs:581-582`). Worse in the other order:
with f8949 bundled and `schedule_d` absent, `f8949.pdf` is on disk (`:826-830`) before
`fill_schedule_d` fails — a directory holding a Form 8949 and no Schedule D, which is precisely the
mailable-chimera shape the whole-branch M-2 pre-check exists to prevent (its own comment,
`admin.rs:793-800`), and the error text says "unsupported year" about a year that *is* supported.

**Minimal change.**

> Arm (2) refuses **before `mkdir_out`** unless BOTH `Form8949Map::for_year(y)` and
> `ScheduleDMap::for_year(y)` resolve — a partially ported year names the missing stem and writes
> zero bytes. (`SUPPORTED_YEARS` is a year-level answer and is not this gate.)
> Kill: a fixture year with one bundled template and no f8949 map → refusal, `out_dir` does not
> exist; add the f8949 map only → still refused, naming `schedule_d`.

### I-2 (Important) — the TUI export's broker refusal happens AFTER the exclusive mkdir, and R6's TUI clause names a dispatch that path does not have

**Where.** Spec lines ~294-296. Code: `crates/btctax-tui/src/export.rs:176-213`;
`crates/btctax-cli/src/render.rs:944-963`, `:1206-1230`.

**What is wrong.** Two things.

(a) `do_export` runs `fsperms::mkdir_owner_only_exclusive(&state.out_dir)` at `:184` and calls
`write_form_csvs` at `:205`; the broker refusal is raised inside `routed_8949_rows`
(`render.rs:954` → `:1214-1216`). So a live TY2026 export leaves the timestamped directory behind on
a refusal, contradicting `do_export`'s own doc contract (*"a refused export creates NO out_dir and
writes ZERO bytes"*, `:145-150`) and R0-I1. The `regime_or_refuse` call at `:180` **is** before the
mkdir, but it only covers the *unsupported-year* refusal — the comment at `:177-179` claims the
ordering for the 1099-DA refusal it does not actually cover. No test observes this: every
`do_export` fixture uses `WalletId::SelfCustody` (`:833`), so the live branch has never been red.

(b) `do_export` passes `answers: None` unconditionally (`:212`) even though `snap.broker_answers`
holds them (`tui/src/app.rs:139`). And the TUI export is the **CSV** export — it has no full-return
arm, so "takes the same three-way dispatch" is not implementable as written and risks an implementer
wiring the full-return packet into the viewer.

**Minimal change.**

> The TUI export is CSV-only and has no full-return arm: it passes
> `snap.broker_answers.get(&year)` into `write_form_csvs`, and the 1099-DA screen + route runs
> **before** `mkdir_owner_only_exclusive`, so a refusal leaves no directory.
> Kill: a TY2026 snapshot with one **exchange** disposition and no stored answer → `do_export` errors
> and `out_dir.exists()` is FALSE; with the answer stored → `form8949.csv`'s `box` column is G.

### I-3 (Important) — `report --tax-year 2026` refuses wholesale on exactly the state R6 creates, so the row enumeration R1 mandates is unreachable to a CLI filer

**Where.** Spec lines ~291-293 (*"`report --tax-year Y` in state (2) keeps its outcome"*). Code:
`crates/btctax-cli/src/cmd/tax.rs:482-497` (early `return Err`) versus `:518-533`
(`render_broker_answers`, unreachable after it); `crates/btctax-cli/src/resolve.rs:183-187`.

**What is wrong.** R1 makes the enumeration a *duty*: *"The answer quantifies over a row set the
engine derived, so the tool MUST show it: `report` and the TUI prompt enumerate each key's rows …
before the answer is taken."* In state (2), `resolve_and_screen` returns `Uncomputable` and `report`
converts it to a hard `Err` before the broker block renders. A filer authoring via `income import`
(which C-2 shows is the *only* surface reaching arm (2)) therefore has **no** way to see the rows
they are swearing `basis_matches` over, and no way to preview the boxes the export will print, short
of exporting the PDF and opening it. Note the year's `TaxTable` **is** bundled (`tax_tables.rs:79`),
so the crypto-delta half of the report is fully computable — it is being withheld only because the
*full-return* half is not.

R6 answering "keeps its outcome" is the wrong answer once the slice can print: the reason for the
refusal (no `FullReturnParams`) no longer implies there is nothing true to show.

**Minimal change.**

> In state (2), `report --tax-year Y` renders the crypto-delta report and the Form 1099-DA
> broker-answers block, and prints `uncomputable_sentence` as a **NOTE** in place of the
> dual/absolute section, rather than exiting non-zero.
> Kill: TY2026 + stored inputs + one exchange row → `report` exits 0, lists the key with its rows and
> column (e), and states the absolute return is not computable; TY2026 + inputs + a
> `screen_inputs`-refusing field → still a hard refusal.

### I-4 (Important) — R6 amends `uncomputable_sentence` but not `import_note`, which is what `income import` prints and what the arm-(3) refusal quotes

### I-5 (Important) — arm (2) prints `form_8283.pdf` at full FMV while holding a declared restriction the full return refuses on

**Where.** Spec lines ~285-288 (*"…through exactly the screen and router the full return uses
(`screen_broker_reporting` then `route_8949_boxes`)"* — i.e. only that screen). Code:
`crates/btctax-core/src/tax/return_1040.rs:2660-2680`; `crates/btctax-cli/src/cmd/admin.rs:886-903`;

affected"*. The slice writes `form_8283.pdf` from `form_8283(state, year, &details)` at full FMV,
with no such screen. Before R6, TY2026 + stored inputs refused (at `screen_full_return`); after R6 it
prints. R6 therefore moves a state from screened to unscreened while btctax **holds the filer's
adverse answer** — the "a figure with no reader" shape, on a form the packet actually emits.

amounts, filing status) and `screen_compute_dependent` reach nothing the slice prints, and the

**Minimal change.** R6 gains a sentence enumerating what arm (2) screens and why:

> Arm (2) runs, before any byte: the promote gate, the pseudo-attestation gate,
> `screen_broker_reporting`, and the Form 8283 restriction row in its slice-appropriate form —
> `ri.donations_had_restrictions == Some(true)` **and** the year emits an 8283 (`form_8283(…)`
> non-empty). It does not run `screen_inputs` or `screen_compute_dependent`: neither reaches a figure
> the slice prints.
> Kill: TY2026 + inputs + `donations_had_restrictions = true` + a donation → refusal, no

### M-1 (Minor) — "the same refusal text the full return prints" is the wrong sentence on arm (2)

The full return wraps a `Refusal` as *"the {year} return is not computable [{reason:?}]: {detail} —
no forms were written"* (`admin.rs:1236-1241`). On arm (2) that asserts the return is not computable
when the slice *is* printable as soon as the key is answered. R6 should say "the same `Refusal`
`reason`/`detail`, in the slice's own sentence", and the kill should pin the leading clause.

### M-2 (Minor) — the `--pay-by-check` / `--forms full-return` refusals are reached by falling through the `exists` branch, not by living inside it

`admin.rs:700-720` places both refusals **after** the
`if return_inputs::exists { … return }` block. An implementer reading "THE DISPATCH becomes
three-way" may write arm (2) *inside* that block and silently bypass both. R6 should say arm (2) is
reached by **not returning early** — the `exists` branch keeps its `return` only when
`full_return_for(year).is_some()`.

### M-3 (Minor) — the Schedule D kill does not discriminate against double-reporting

*"Schedule D line 1b carries the G total"* is passed by a filler that writes the total to **both** 1b
and 3 — which double-counts short-term proceeds on the face of the schedule. The kill must assert
line 3 is blank, and on a G+I mix that `1b + 3` cross-foots to the part total.

### M-4 (Minor) — R6 newly makes TY2025 + stored inputs print a box R1 records as wrong

R6's own kill says TY2025 (templates, no params) + stored inputs now PRINTS where it used to refuse
"no full-return tables for 2025". Under the proceeds-only regime those rows belong in H/K and btctax
files I/L — R1 records this as a known gap owned by the S1 decision. The gap is already reachable
with *no* inputs, so this is not a new class, but R6 widens it. One clause: R6 should say the TY2025

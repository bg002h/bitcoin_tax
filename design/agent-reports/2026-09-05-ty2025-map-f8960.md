unchanged, and this was measured, not assumed.**

- `dump-fields` on `design/forms/2025/f8960--2025.pdf` and on `crates/btctax-forms/forms/2024/f8960.pdf`

- `diff -b` of the two committed text layers differs in **exactly three hunks**: the two extract header

- No line renumbered, none retired, none changed meaning, none added. The traps that bit other forms
  this year did **not** occur here: no Schedule C-style letter/content swap, no Schedule 2-style
  "Reserved for future use" retirement (verified verbatim in `f1040s2--2025.txt` line 59), no
  Schedule A-style root-subform rename — the root is still `topmostSubform[0]`.

**Three things I changed in the prose, all deliberate:**

1. **Corrected a stale header claim.** The TY2024 map's header still says the derived totals 9d and 11
   *"ARE filled, at zero"*. FR-12 (closed 2026-09-05) made `Form8960Lines::line9d` an `Option<Usd>`,
   and FR-39 names line 11 as the same shape one line down. Both are `Production::Combine` — *blank iff
   every operand is blank* — and neither carries a *"-0-"* clause (Part II has none anywhere; the
   form's first is line 12's). The TY2025 header states this correctly and says the TY2024 sentence
   was overtaken rather than silently dropping it. They stay **mapped**, because the emitter must be
   able to write them the moment 9b is allocated: mapped ≠ populated.
2. **Corrected the line-4b instruction citation** (apostrophe + file/heading provenance, §2 above), and
   added the §1411(c)(6) sentence that settles the point directly.
3. **Added the port's own provenance block** — the sha256, the dump command, the two-column label
   correlation, the bijection count — so the next year's porter can re-run the check instead of
   trusting this file.

**One check I ran that the TY2024 map does not document.** I re-derived the emitter's own geometric
oracle from `form8960.rs` (MID `[410, 482]`, AMOUNT `[504, 576]`, strictly descending y over the
15-cell `map.lines()` order) and ran it against the real rects. A map pointing a line at the wrong
column fails closed at fill time; this catches it now instead:

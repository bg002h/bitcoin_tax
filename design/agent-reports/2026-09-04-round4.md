## VERDICT

Said plainly, because the brief asks for it: the shipped guard at `HEAD` is *correct*. I found no

The fix is roughly five lines of fixture. This is a short round-5, not a reopening.

## FINDINGS

### I-1 (Important) — the kill test cannot see `Storage` at all, and its doc says it can. A guard restricted to committed entries survives it, and re-opens 102 → 42 exactly.

**The mutation** (my fifth — full detail in the next section): in `regen_would_drop`, restrict the
comparison to committed entries, the natural response to FR-26's documented pain.

```rust
    let mut dropped: Vec<String> = existing
        .iter()
        .filter(|e| e.storage == Storage::Committed)   // <-- planted
        .map(|e| e.path.clone())
        .filter(|p| !fresh.contains(p.as_str()))
        .collect();
```

**Result: `regen_refuses_to_delete_a_document_whose_binary_is_missing` PASSES. The whole `xtask`
suite passes — 67/67.** Measured, not reasoned.

**Why the test cannot see it.** `regen` derives `Storage` from `git check-ignore` run with
`current_dir(root)` (`authority_manifest.rs:699-703`), and the fixture root is a
`tempfile::tempdir()`, which is not a git repository. The command exits 128, and

```rust
            .unwrap_or(false);      // authority_manifest.rs:703
```

turns that into `Storage::Committed`. **Every entry the fixture ever creates is `Committed`.** The
`fatal: not a git repository` lines printed six times during this test at `HEAD` are that failure,
visible in the test output today.

I proved it both directions rather than inferring it:

| planted filter | test result | what it proves |
|---|---|---|
| `e.storage == Storage::Committed` | **PASS** (suite 67/67 green) | no fixture entry is `Note` |
| `e.storage == Storage::Note` | **FAIL** at `authority_manifest.rs:990`, first victim | both fixture entries are `Committed` |

**The overclaim** — this is simultaneously the question-3 finding, and it is false today:

- `authority_manifest.rs:948` — `/// ★★ **Both storage classes.** … This plants one of each — a note-backed form and a committed statute — because one arm passing proved nothing about the other.`
- `authority_manifest.rs:979` — `// ── Each storage class, one at a time. Removing EITHER must refuse, and must not write. ──`

It plants one of each **note-presence** shape — with a sibling `.pdf.txt`, and without — and that
distinction is real and load-bearing: it is what kills M3, the round-3 blind spot. But `Storage` is
what `regen_would_drop` actually reads (`e.storage`), and on that axis the fixture is a constant. The
inline comment at line 981 hedges honestly (`// note-backed, gitignored in the real repo`); the two
headline claims above do not, and they are the ones a future reader will trust.

**Why this mutation and not any other.** Mutation coverage is never total, and a surviving mutation
is not automatically a finding. Two objective facts distinguish this one:

1. The artifact **promises** to catch it, in writing, twice (lines 948 and 979).
2. The repo **already documents the pressure that produces it**. `FOLLOWUPS.md` FR-26 records that
   the refusal fires on every fresh clone, that there is no fetcher, and that "the maintainer's next
   move is 60 hand-issued `curl`s." FR-26 forecloses a `--force`. It does not foreclose the quieter
   edit — *"the (A) PDFs are gitignored, of course they are missing; only guard the committed ones"*
   — which is exactly M5, and which reads as a **narrowing to the safe case** rather than as a
   widening.

**The cost if it lands.** Measured from the real manifest: 102 entries, **60 `note` / 42
`committed`**. Under M5 the 60 note entries are no longer guarded, so a regen on a fresh clone drops
all 60 and refuses on none: `--regen` writes **42 entries**, silently. That is not an analogue of the
original defect; it is the original defect, byte for byte, with the whole suite green — which is the
state this entire branch exists to make impossible.

**Fix (small, and it re-earns B1).** Make the fixture produce both `Storage` values, then re-run M5
and watch it red:

- `git init` the tempdir and write a `.gitignore` covering `design/forms/**/*.pdf`, so
  `check-ignore` classifies the form as `Note` and the statute as `Committed`; **or**
- fully hermetic, no git: assert on the baseline manifest that both `Storage` variants are present.
  That assertion **reds today**, which is itself the proof the gap is real, and it forces the
  fixture fix rather than merely documenting it.

Either way the B1 question — *"which test reds when this is removed?"* — gets a true answer for the
storage axis, which it does not have now.

### M-1 (Minor) — `git check-ignore` fails OPEN to `Committed`, and the guard cannot see that either.

`.status().map(|s| s.success()).unwrap_or(false)` (`:701-703`) collapses three different situations
to `Storage::Committed`: the file is tracked; the tree is not a repo; **`git` is not on `PATH` at
all**. In a tree where git cannot classify, `--regen` would rewrite all 60 note entries to
`storage: "committed"` — no path is dropped, so `regen_would_drop` returns empty and the refusal
never fires, and `verify` stays green because its `Committed` arm hashes files that are present and
regen has just written those hashes. The manifest silently loses the storage classification of 60
documents with every instrument OK.

Same root cause as I-1, and demonstrated by the same evidence (the fixture *is* a tree where git
cannot classify). **Minor** only because `--regen` is a maintainer command run inside the repo, so
the real-world probability is low — but the shape is fail-open, which this repo has a standing memory
about, and it is one line to make it `Err` loudly instead.

### M-2 (Minor) — the guard covers path DROPS, never entry DEGRADATION: an unreadable-but-present file zeroes a committed authority's hash, and `verify` then reports OK.

Probed hermetically in a tempdir (P2/P3 below). With a committed statute present but unreadable
(`chmod 000`), `collect_sources` still finds it, so the path is in `fresh`, so **nothing is dropped
and the refusal does not fire**. `regen` then hits

```rust
            Err(_) => (note_sha, 0), // gitignored and absent locally — trust the note   (:729)
```

and writes `sha256: ""`, `bytes: 0` for a statute. `verify` does not catch it either: its committed
arm is `if !abs.is_file() { MissingFile } else if let Ok((sha, _)) = sha256_of(&abs)` (`:239-241`),
and the read error falls out of the `if let` silently. Net effect: `authority-manifest` prints OK
over a manifest that has lost the hash of a rung-4 authority. (The dangling-symlink variant, P2,
reaches the same write but *is* caught afterwards, because `is_file()` is false there.)

Two notes on scope and fairness. First, `:729` dates from `3c49618c` (2026-07-30, on `main`), so its
origin is outside this review's window; I raise it because this branch's guard now makes the
comment's stated case (`gitignored and absent locally`) **impossible** — `collect_sources` walks the
filesystem, so an absent file is never in `sources` — leaving the comment describing a branch it
cannot take. Second, FR-25 already owes *"either fix the parse and let notes be the source of truth,
or delete the dead fallback"*; this belongs on that entry, adding (a) the one reachable shape and
(b) the `verify` blind spot that keeps it silent. It does not gate.

### N-1 (Nit) — `regen_would_drop`'s doc summary is stale against its own signature.

`:540` still reads *"Returns an empty vec when no manifest exists yet."* The function now returns
`Result<Vec<String>, String>` and has a **third** outcome — present-but-unreadable → `Err`, refuse —
which is documented only in the body comment. The doc-comment summary, which is what shows in
rustdoc and in an IDE hover, describes two of three arms. Two lines.

### N-2 (Nit) — two prose records were not carried forward by `01e48226`.

- `FOLLOWUPS.md:5629` — *"mutation-verified red against three breakages"*, and it lists three. M4
  (corrupt ≡ absent) made it four.
- `CONTINUITY.md:805` — the `--regen` paragraph documents only the missing-document refusal, not the
  corrupt-manifest one.

Both are **under**-claims, so neither is the question-3 shape and neither is dangerous. Recorded only
because this branch's own fold commit counted stale prose as "the FOURTH stale count this branch has
found," and these are the fifth and sixth.

## THE FIFTH MUTATION

**What I invented.** Not a reordering and not the temp-file-and-rename the brief suggested — both of
those are held by the byte-comparison M1 already covers, since any write that reaches
`MANIFEST.json` before the refusal reds the assertion regardless of how it got there. I went after
the axis the test *asserts* it covers instead:

> **M5 — restrict the drop check to `Storage::Committed` entries.** Rationale a maintainer would
> actually write: the (A) PDFs are gitignored, their absence on a fresh clone is normal and is
> exactly FR-26's complaint, so only a *committed* file going missing is a real loss.

**What happened: the test SURVIVED. Green, and so was the whole `xtask` suite (67/67).**

Then, to be sure the survival was the fixture and not luck, I flipped the same filter to
`Storage::Note` and it **failed instantly** on the first victim — proving the fixture contains no
`Note` entry at all, and therefore that the test is blind to this axis in both directions rather
than accidentally passing one.

Both mutations reverted; the file is byte-identical to `HEAD` (sha256 `2c7813ec8d6cb535…`, `git
status` clean).

The brief's two named candidates, answered directly:

- **Reordering the arms** — `regen_would_drop`'s `match` arms are `Ok(e)` / `Err(e) if exists` /
  `Err(_)`; the patterns are disjoint, so a reorder is either a no-op or does not compile. Not a
  live hazard.
- **Temp file + rename** — the test holds. If the guard sits between the temp write and the rename,
  `MANIFEST.json` is untouched and the test correctly passes (the behaviour is correct). If the
  guard moves below the rename, `MANIFEST.json` changes and the byte-comparison reds. The assertion
  is on the file, not on the write call, so the refactor cannot smuggle a breakage past it. This is
  precisely what round 3's I-1 fix bought, and it works.

## WHAT I VERIFIED AND HOW

**Question 1 — a fourth path to the same data loss.** I built a temporary probe test in a tempdir
and ran seven constructions. Recorded here so round 5 does not re-derive them:

| probe | construction | result |
|---|---|---|
| P1 | manifest is valid-but-empty `[]`, victim absent | proceeds — **correct**, nothing was listed to lose; and `census` reds on it, so an empty manifest is loud, not silent |
| P2 | dangling **symlink** replacing a committed statute | proceeds, manifest rewritten, entry becomes `sha256:""`/`bytes:0` — but `verify` afterwards reds with `MissingFile`. See M-2 |
| P3 | committed statute present but **unreadable** (`chmod 000`) | proceeds, same degraded entry, and `verify` reports **OK**. This is M-2, the one silent variant |
| P4 | committed file **content revised** | hash absorbed silently — but this is `--regen`'s documented purpose, and `Problem::HashMismatch`'s own text already says *"never regenerate to make this go away."* Not a finding |
| P5 | a whole `KNOWN_ARCHIVES` tree deleted | **REFUSED**, manifest byte-unchanged. Fails closed |
| P6 | is `MANIFEST.json` itself collected as a source? | no |
| P7 | manifest truncated to a valid **one-entry** array, victim absent | **REFUSED**. (Genuinely truncated JSON is invalid and takes the corrupt arm.) |

Also settled by reading and by grep, not by inference:

- **Guard placement.** `regen` has exactly one write, `fs::write(manifest_path(root), …)`, as its
  last statement. The guard is ~60 lines above it and precedes the entry-building loop. The two
  things that run *before* the guard — `harvested_urls` and `collect_sources` — are read-only.
- **Windows path spelling.** `collect_sources` and `collect_notes` both normalize `\` → `/`; the
  manifest stores `/`; `regen`'s `dropped`/`notes` partition compares normalized against normalized;
  `notes_without_binaries` re-joins forward-slash relatives, which Windows accepts. CI does run this
  test on Windows (`ci.yml:23` `windows-latest`, `:36` `cargo test --workspace --locked`), and it is
  green there. I could not execute on Windows myself — see below.
- **FR-25's note-format claim, machine-checked because it is checkable:** 60 of 60 notes write
  `# sha256  <hash>`; **0** write the `sha256:` form `regen` parses; and the 64-hex-line fallback
  cannot match `# sha256  <hash>` (trimmed length exceeds 64). FR-25's *"it has never once fired"*
  is exactly right.

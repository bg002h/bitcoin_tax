## 1. Site 1 - BUNDLED_FORMS_PER_YEAR (supported_years_cross_product.rs:147)

### 1a. The trace, and where it goes further than the brief anticipated

The brief's Section 2 worried that a count derived from YEAR.toml would go silent if an asset and its
YEAR.toml line were deleted together, because the hand-typed pin is what currently catches that. I
planted exactly that case twice (see 1b) and found three independent things catch it, not one:

1. line_set.rs's schema() match (lines 141-234) is a compile-time gate, and it fires first.
   LineSet is generated by build.rs from a glob over forms/<year>/*.map.toml - delete a map and
   the generated enum loses that variant. But schema() is a hand-authored, one-arm-per-revision match
   over that generated enum (e.g. line 181: LineSet::F1040sb_2025 maps to Schema::ScheduleBMap).
   Deleting the map without also removing this line does not compile: error E0599, no variant found
   for enum LineSet. A real retirement needs three edits (asset, YEAR.toml, line_set.rs), not two.
2. year_record.rs's OWN anti-shrink pin (lines 43-51) is a second, independent hand-typed
   literal holding the exact same numbers (2024 maps to 20, 2025 maps to 18, 2026 maps to 0, other
   panics), with a doc comment (line 40) citing the identical rationale as BUNDLED_FORMS_PER_YEAR's:
   "a record regenerated to match a directory that lost a file would pass both existing checks. These
   counts do not come from the glob." This pin reads YearRecord::for_year(year).forms_expected.len()
   - i.e. it is already the check FR-156 imagined building - and it is untouched by anything done to
   BUNDLED_FORMS_PER_YEAR, so even a future YEAR.toml-derived version of the site-1 pin would still
   sit behind this one.
3. count_verdict in supported_years_cross_product.rs itself - the one the brief asked about -
   compares the hand-typed pin against a count measured from forms/<year>/*.pdf on disk (not from
   YEAR.toml at all, today). This is the fourth angle: disk-vs-hand-typed, independent of both 1 and 2.

So the brief's feared scenario ("nothing reds") does not occur today, and not narrowly - it is
caught by three unrelated mechanisms before count_verdict is even reached in the "naive" plant, and by
two of them (site 1's own check plus year_record.rs's) even in the "proper" plant. Given this repo's
own precedent for valuing redundant witnesses (two-oracle validation, the AMT witness census), and given
CLAUDE.md's explicit "derive the list, or make the compiler hold it" rule already being satisfied
elsewhere (year_record.rs's pin, line_set.rs's exhaustive match), removing the fourth witness in
supported_years_cross_product.rs would trade a working, cheap, currently-discriminating check for
nothing - the failure mode described in FR-156's filing is not actually reachable by deriving this pin
from YEAR.toml, but pinning it by hand is also free and adds a fourth angle a YEAR.toml-sourced
derivation could never give (disk truth vs. declared intent). Keep it as-is.

## 2. Site 2 - the Form6251Map/Form8995AMap refusal loop (map_pdf_conformance.rs:200)

### 2a. The trace

The loop: for unmapped in [2023, 2025, 2026], assert Form6251Map::for_year(unmapped) is_err, and
assert Form8995AMap::for_year(unmapped) is_err - six assertions. Measured what actually makes each
one refuse, against the real bundled state (forms/2024/, forms/2025/, forms/2026/ - the last holds
only YEAR.toml, no PDFs; there is no forms/2023/ at all):

- Form6251Map::for_year(2023): no forms/2023/ at all, refuses via UnsupportedYear. Borrowed absence,
  but 2023 will essentially never be bundled (a backward port) - low practical risk.
- Form6251Map::for_year(2025): forms/2025/f6251.map.toml EXISTS, but its row's line_set resolves via
  line_set::schema to Form6251ObbbaMap, not Form6251Map, so it hits the "other" arm - a real
  cross-schema refusal. DURABLE - the one assertion in this loop testing real logic.
- Form6251Map::for_year(2026): forms/2026/ has no f6251 asset (a "preparing" record, empty
  forms_expected), refuses via UnsupportedYear. Borrowed, and HIGH risk - TY2026 is the literal next
  port.
- Form8995AMap::for_year(2023): same as the 2023 case above. Borrowed, low risk.
- Form8995AMap::for_year(2025): forms/2025/ has no f8995a asset at all (YEAR.toml's forms_absent
  table names it: "not ported to TY2025"), refuses via UnsupportedYear. Borrowed - no cross-schema
  case exists for this stem at all right now.
- Form8995AMap::for_year(2026): same as the 2026 case above. Borrowed, high risk.

This is a live instance of the FR-136 shape (design/agent-reports/REPORT-a5-fr136.md,
design/HARNESS.md's B1b amendment): five of the six assertions name a year because it happens to have
no bundled asset for that stem, not because of any real logic. The day TY2026 ships an f6251 or
f8995a asset (assuming either keeps the same schema Form6251Map/Form8995AMap already know), those two
is_err() calls flip to Ok, and the test goes red about the instrument, at the exact moment a port is
being shipped - not from a regression. Form8995AMap::for_year(2025) carries the identical risk the
day that gap is filled. Only the Form6251Map::for_year(2025) assertion is testing something that will
stay true regardless of future ports (a real, already-shipped cross-revision conflict).

### 2b. Why this is NOT fixed here

FR-156's brief scope is "small... hygiene, not a sweep," in-scope for the two files named in Section 1
plus whatever minimal edit the Section 2 answer requires. Two candidate fixes were considered and both
rejected as out of this budget:

- Derive the "should refuse" set from for_year's own current behavior. Tautological - it would test
  whether for_year agrees with for_year, which can never fail. This is the null-test antipattern
  CLAUDE.md's "derive the list, or make the compiler hold it" section warns is worse than the list it
  replaces.
- Derive it from line_set::schema directly (the same independent-of-for_year mechanism the per-stem
  dispatch cross-check in supported_years_cross_product.rs already uses) - principled, but real design
  work: it has to partition "genuinely no asset" from "wrong schema," decide what a synthetic/sentinel
  year should be for the "no asset ever" case (site 1's own
  the_unsupported_year_refusal_names_exactly_the_supported_years test already uses -1 for exactly this
  reason), and get FR-136's own remedy pattern (derive the victim from the measured set) applied to a
  form-refusal test rather than a form-presence test it hasn't been applied to before. FR-136 itself
  needed a dedicated opus-tier task (design/agent-reports/PLAN-fr134-151-burndown.md's A5) to do this
  correctly for two other files; doing it hastily here risks shipping a "correctly-designed guard, fixed
  carelessly" - the exact failure this repo's harness doctrine names as worse than not fixing it.

Recommendation (not filed to FOLLOWUPS.md - leaving FR numbering to the controller): a follow-up,
owning phase "before the TY2026 f6251/f8995a port lands" (mirrors FR-136's own urgency, since that is
precisely when this self-destructs), scoped to: replace the borrowed-absence years (2026, and 2025 for
f8995a) with a derivation off line_set::schema / the measured bundled set, matching the "derive the
victim" remedy already used in year_record.rs and form_delta.rs; keep 2023 and the real f6251/2025
cross-schema case as-is (durable, not at risk).

## 3. ★★★ The design requirement that is the whole point of doing this now

**Because every field name is identical across the two revisions, a single struct carrying one year's
cross-reference would fill the other year's form and NOTHING WOULD RED.** The AMT base would be computed
from the wrong line of Schedule 1-A. That is the same class as this project's original AMT defect, where a
cross-reference transcribed one line off inflated the tentative minimum tax by $200,000 on one vector — and
it is invisible to the field map, to the geometry fixture, and to read-back.

So the deliverable is not just "a struct that parses". It is a structure in which **adding the 2026 revision
without stating its own two cells is a BUILD ERROR**, per `CLAUDE.md`'s *"derive the list, or make the
compiler hold it"*. Two shapes are defensible and you choose, stating why:

- **(a) one struct per revision** — the literal reading of the transcription rule; the two cells differ, so
  the revisions differ; or
- **(b) one struct for the shared layout plus a per-revision table** for the two year-varying cells, where
  the table is exhaustive over the line sets that use this schema, so a new revision cannot compile without
  filling it in.

Either way: **line 4's dollar figure must never be a literal in this struct** — it is
`AmtParams.mfs_kicker_start`, already per-year and already correct for 2026. And line 1a's Schedule 1-A line
number must be per-revision, not a constant inherited by whoever wires 2026.

## What changed vs TY2024

### 1. ★★ Root subform renamed — **no FQN survives the year**

`topmostSubform[0].Page1[0].…` → `form1[0].Page1[0].…`. A port that copied the TY2024 file and bumped
`year` would name 37 fields, none of which exists. (Schedule 2 uses `form1[0]` in *both* years, so
this is a per-PDF authoring artifact, not a TY2025 convention — check it per form.)

### 2. ★★★ The SALT limitation changed, and **the map cannot carry the change**

Line 5e, verbatim from the two text layers:

- **2024:** *"Enter the smaller of line 5d or $10,000 ($5,000 if married filing separately)."*
- **2025:** *"Enter the smaller of line 5d or $40,000 ($20,000 if married filing separately). If Form
  1040 or 1040-SR, line 11b is more than $500,000 ($250,000 if married filing separately), or if you
  completed Form 2555, Form 4563, or excluded income from Puerto Rico, see instructions ."*

The cap rose **and** a MAGI phase-down appeared (Pub. L. 119-21; the instructions'
**"State and Local Tax Deduction Worksheet"**, `design/forms/extract/i1040sca--2025.txt` line 862).

**The dangerous part is that this is invisible to every check in this deliverable.** The 5e *box* is
in the same column, at the same size, taking the same kind of value. The field map is complete and
correct, and the number written into it can still be a TY2024 answer. `dump-fields` cannot see it,
the census cannot see it, the label reader cannot see it, and the printed page cannot show it. So the
map header says it in the loudest terms available, and this report says it here: **a correct field map
is a necessary and not a sufficient condition for filing this schedule for TY2025.** The worksheet is
already transcribed at `design/ty2025/SPEC.md` §5.5 and is not built;
`tax_tables.rs::ty2025_full_return_must_stay_fail_closed_until_complete` already names *"a scalar
`salt_cap` against a §164(b) phase-down"* as one of its blockers, and must stay closed.

### 3. Two cross-references moved, because Form 1040 restructured

| line | 2024 | 2025 |
|---|---|---|
| 2 | "Enter amount from Form 1040 or 1040-SR, **line 11**" | "**line 11b**" |
| 17 | "…enter this amount on Form 1040 or 1040-SR, **line 12**" | "**line 12e**" |

Nothing in the map file encodes these, but whatever sources L2 or consumes L17 does.

### 4. Four fields disappeared (37 → 33) — and **not one line was lost**

Each write-in continuation block collapsed from several single-row boxes into one 24pt-tall box:

| block | 2024 | 2025 |
|---|---|---|
| line 6 description | `f1_12`, `f1_13` (2) | `f1_12` (1) |
| line 8b payee name/ID/address | `f1_17`, `f1_18` (2) | `Line8b_ReadOrder[0].f1_16` (1) |
| line 16 description | `f1_30`, `f1_31`, `f1_32` (3) | `f1_28` (1) |

4 boxes lost; 37 − 4 = 33, which accounts for the entire count change. Every one is censused; btctax
fills none of them. **No line's disposition changed between the years** — the TY2025 census is the
TY2024 census minus exactly these four boxes.

### 5. Two new read-order subforms

Line 2's box is now `Line2_ReadOrder[0].f1_4[0]`; line 8b's payee block is
`Line8b_ReadOrder[0].f1_16[0]`. TY2024 had only `Line8_ReadOrder` and `Line18_ReadOrder` (both still
present). Nesting is part of the FQN — a flat `f1_4` does not resolve.

### 6. All three x-clusters moved; the mid column by only 7.2pt

| cluster | 2024 | 2025 |
|---|---|---|
| AGI-INLINE (line 2 only) | [331.2, 402.5] | **[316.8, 388.0]** |
| MID | [417.6, 488.9] | **[410.4, 481.6]** |
| AMOUNT | [504.0, 576.0] | [504.0, 576.0] — unchanged |

Line 2 is still *not* in MID: it is inline with the printed sentence, 93.6pt left of MID and the
**same width** (71.2 vs 71.2), so a width-based check would not catch a mis-map. It keeps its own
cluster, as in TY2024. No Rust source hardcodes any of these numbers (grepped `417.6`, `488.9`,
`331.2`, `402.5` across `crates/` → 0 hits); the geometric oracle re-derives bands from the PDF.

### 7. The non-sequential-suffix trap survived, in a new costume

Reading **down** the page from 8a (`f1_15`, y=366): the next box is **`f1_17`** (y=324) = the 8b
*amount*, and only below it sits **`f1_16`** (y=300) = 8b's payee free text. The IRS numbered the text
field before the amount while printing it after. TY2024 had the identical inversion with different
numbers (8b amount was `f1_19`, above free-text rows `f1_17`/`f1_18`). Anything walking suffixes in
order trips on this in either year.

### 8. Line 8d is still a live "Reserved for future use" widget

`f1_19` in 2025 (`f1_21` in 2024). The form prints *"d Reserved for future use"* and the IRS still
ships a fillable box, consuming a suffix number (`f1_18`=8c, `f1_19`=8d, `f1_20`=8e). Never written.

### 9. Everything else is unchanged text

Lines 1, 3, 4, 5a–5d, 6, 7, 8, 8a–8e, 9–16 and 18 differ from TY2024 only by reflow — verified
fragment-by-fragment against both extracts, not by eye. The line 5 heading gained "(SALT)".

## Census disposition — all 9 unmapped fields, with reasons

btctax itemizes MEDICAL (line 1), SALT (5a–5e), MORTGAGE INTEREST reported on Form 1098 (8a) and
CHARITABLE gifts (11–14). Every field below is a deduction the filer **forgoes** by using btctax —
the safe direction: omitting a deduction can only overstate tax, never understate it. All are left
BLANK, never a misleading `0`.

| field (`form1[0].Page1[0].` …) | line | rule | reason |
|---|---|---|---|
| `f1_12[0]` | 6 | `unmodeled` | *"Other taxes. List type and amount:"* — the write-in DESCRIPTION block (one 24pt box in 2025, two rows in 2024). btctax collects only the enumerated SALT categories, lines 5a–5c. |
| `f1_13[0]` | 6 | `unmodeled` | Line 6 amount — same reason; line 7 therefore equals line 5e. |
| `f1_17[0]` | 8b | `unmodeled` | Line 8b AMOUNT — *"Home mortgage interest not reported to you on Form 1098."* btctax collects `mortgage_interest_1098` only, i.e. interest that IS on a 1098. |
| `Line8b_ReadOrder[0].f1_16[0]` | 8b | `unmodeled` | The 8b payee block — *"…show that person's name, identifying no., and address."* Free text; nothing to write while 8b itself is unmodeled. |
| `f1_18[0]` | 8c | `unmodeled` | *"Points not reported to you on Form 1098. See instructions for special rules."* Not collected. |
| `f1_19[0]` | 8d | `artifact` | The form's own text is *"Reserved for future use"* — the IRS ships a live fillable box for a line it has explicitly reserved. No decision is encodable, **by the form's own statement**. |
| `f1_27[0]` | 15 | `unmodeled` | *"Casualty and theft loss(es) from a federally declared disaster (other than net qualified disaster losses). Attach Form 4684…"* btctax models no Form 4684. Text unchanged from TY2024. |
| `f1_28[0]` | 16 | `unmodeled` | *"Other—from list in instructions. List type and amount:"* — write-in DESCRIPTION block (one 24pt box in 2025, three rows in 2024). btctax offers no write-in itemized deduction. |
| `f1_29[0]` | 16 | `unmodeled` | Line 16 amount — same reason. |

**Line 9 is NOT censused** — it is mapped (`line9 = f1_21`). btctax collects
`schedule_a.investment_interest`, gated by the Schedule D line 20 / Form 4952 declaration
(`RefuseReason::Form4952Required`), so the printed amount is always one deductible in full under
`i4952`'s own exception. Same disposition as TY2024.

Every census entry's `line` was cross-checked against the geometric `label-boxes` assignment — a
census row that *claims* line 8c while pointing at line 8d's widget would red.

## Unresolved / for the controller

   `ScheduleAMap::for_year(2025)` until `design/ty2025/SPEC.md` §5.5 lands; the existing fail-closed
   test must stay closed. This map's completeness is not evidence about that.
2. **★ The in-repo census gate cannot see this file yet.**
   `crates/btctax-forms/tests/field_census.rs::census_accounts_for_every_field` opens with
   `let year = 2024;` — a hardcoded scalar, not an iteration over `forms/*/`. So the TY2025 census I
   wrote is **checked by nothing in the suite**; I only verified it by re-implementing the gate's
   scanner outside the repo. That is the green-and-blind-instrument shape this project keeps getting
   caught by: the gate passes, and passes without ever looking at 2025. Whoever wires TY2025 should
   make that test iterate the year directories (and, per B1, watch it go red by deleting one census
   entry from this file before trusting it).
3. **No Rust source was touched** (hard rule). Still absent, and needed before anything can load this
   map: `SCHEDULE_A_MAP_2025` (`include_str!`) and `SCHEDULE_A_PDF_2025` (`include_bytes!`) in
   `crates/btctax-forms/src/map.rs` / `src/pdf.rs`, and a `2025 =>` arm in `ScheduleAMap::for_year`.
4. **`crates/btctax-oracle-harness/src/main.rs:807`** maps `"f1040sa" => SCHEDULE_A_MAP_2024`
   unconditionally, with no year dispatch. It will silently use TY2024 FQNs against a TY2025 PDF —
   and because **every** name changed (§1), that fails loudly rather than subtly, which is the good
   case. Flagged so it is fixed deliberately rather than discovered.
5. **Cross-form ripple, out of my scope:** L2 now reads Form 1040 line **11b** and L17 writes line
   **12e** (§3). Whatever produces L2's AGI and consumes L17 needs the same year-aware treatment.
6. **The label reader is calibrated on stable forms.** `design/ty2025/recon-year-port-delta.md`
   records it silently dropping line `1a` on `f6251--2025`. Schedule A is not restructured in that
   way — it yields 28 labels in both years — and I did not rely on the tool alone: the hand
   derivation from `dump-fields` y-ordering was done first and independently, and agrees on all 33
   fields. No B1 concern for *this* form, but the tool's own kill-test remains owed.

## NEW findings

### C-1 — CRITICAL — a (provider, cohort) key can still hold rows needing different boxes, and no answer refuses

**Where:** spec R1 `:100-105` (the "Why the filer's answer still binds a SET of rows" bullet), the
`BrokerReported` enum `:79-91`, R2 `:139-145`, T2's kill `:202-205`.

**What is wrong.** r2 asserts: *"The broker's lot identification may differ from the engine's … That
difference cannot change WHICH form lists a sale, only the basis printed on it — and the filer reads
the basis off the form, so it surfaces as `BasisDiffers`, which refuses."* The second sentence is
false. Whether the 1099-DA shows basis at all follows the **lot the broker identified**:
`Instructions_1099-DA.txt:253-259` — "If the digital asset sold … is a covered security … boxes 1d,
1g, **2**, and 6 must be completed"; `:260-262` — "If the digital asset sold … is a noncovered
security, you may check box 9"; and `:475-477` — "brokers may use customer-provided acquisition
information **solely for lot-selection purposes and not for reporting basis or acquisition dates**",
so even T7's specific-ID instruction does not align the two partitions. So the broker's partition of
a year's sales into box-2-checked / box-2-unchecked need not coincide with the engine's
Covered/Noncovered partition — and btctax's default method is HIFO while the spec itself says the
broker defaults to FIFO.

Consequence: one key, e.g. `(coinbase, Covered)`, can contain two rows whose 1099-DAs differ in box
2. **No value of `BrokerReported` is true of that set.** `BasisDiffers` is defined narrowly as "box 2
checked, and at least one box 1g differs" — it does not cover "some listed with basis, some
without", and neither does `NotReported`/`ProceedsOnly`/`BasisMatches`. The filer must pick one, and
the tool prints a **wrong box on at least one row of a signed return with no refusal** — the exact
outcome the spec exists to prevent, on the owner's own profile, which is what made S4 Critical. The
1099-DA is a **per-transaction** form (r1 lens 2 said so); per-row is the only grain guaranteed
homogeneous, and (provider, cohort) is coarser than that.

Compounding it: the declaration's own text — *"for every disposition at &lt;provider&gt; of units
btctax classes as &lt;cohort&gt;, the 1099-DA shows …"* — asks the filer to quantify over a row set
the engine derived and **nothing in the spec ever shows them**. T6 says `report` "shows the answers
per key", not the membership. A filer who cannot see the set will answer from the forms in their
hand, which is precisely the misaligned partition.

**Minimal change:** two sentences and one enum variant.
1. Add a fifth outcome — `Mixed` (or `NotOneAnswer`) → **REFUSE**, naming the per-lot 1099-DA import
   as the exit, so "I cannot say one thing about all of these" fails closed instead of guessing. Say
   in R1 that a key whose rows' forms disagree is exactly this case.
2. State in R1/T6 that the prompt and `report` **enumerate the rows in each key** (date, amount,
   btctax's column (e)) so the declaration is about a set the filer can see, and add T2's kill for
   the mixed key.
3. Delete or rewrite the "cannot change WHICH form lists a sale" sentence — it is the load-bearing
   claim and it is not true.

### N-1 — IMPORTANT — `BTreeMap<ReportingKey, BrokerReported>` does not serialise, and `ReturnInputs` round-trips through JSON and TOML

**Where:** spec R1 `:92` `pub struct BrokerReporting { pub answers: BTreeMap<ReportingKey, BrokerReported> }`; T6 `:214` ("`income import` TOML shape").

**What is wrong.** `ReturnInputs` derives `Serialize, Deserialize` (`return_inputs.rs:11,35`), is
**persisted as JSON** (`btctax-cli/src/return_inputs.rs:118` `serde_json::to_string(&stamped)`) and
**authored as TOML** (`income import --file <inputs.toml>`). Both formats require string map keys. A
struct key fails in both — machine-checked on the exact shape:

```
serde_json: Err(Error("key must be a string", line: 0, column: 0))
toml:       Err("map key was not a string")
```

So the very first `income import` / store of an answered `ReturnInputs` errors out
(`CliError::BadConfigValue`), and T1 cannot land as written.

**Minimal change:** nest instead of tupling the key —
`BTreeMap<String /* provider */, CohortAnswers>` with
`struct CohortAnswers { covered: Option<BrokerReported>, noncovered: Option<BrokerReported> }`.
Absent provider **or** absent cohort slot = unanswered, so answered-ness still lives in the key set,
and both TOML and JSON express it. (A string-encoded key such as `"coinbase/covered"` also works but
re-introduces parsing.)

### N-2 — IMPORTANT — `screen_inputs` cannot compute the liveness the spec assigns to it

**Where:** spec R1 `:109-121` (option (b), "its own screen in `return_refuse::screen_inputs`"); code `return_refuse.rs:853`.

**What is wrong.** `screen_inputs(ri: &ReturnInputs, tbl: &TaxTable, p: &FullReturnParams)` sees no
`LedgerState`. Liveness is *"the regime says `basis` AND the year has ≥1 disposition on an
exchange"*, and the sibling rule is *"an answer for a key with NO dispositions ⇒ `Refusal`"* — three
uses of the year's disposals, none reachable. The regime is not reachable either: `p.year` exists
(`tables.rs:454`) but `FullReturnParams` carries no `InformationReturnRegime`, and the spec's own
argument is that core cannot read `YEAR.toml`. Force-fit either way and the screen is
**green-and-blind**: refuse-always breaks every crypto-free full-return fixture, refuse-never is a
gate that cannot fire.

**Minimal change:** name the site that has all three, or state the widening explicitly. Either
(a) add `regime: InformationReturnRegime` to `FullReturnParams` (every literal reds — the compiler
does the review) **and** move the broker screen to a site that receives the `LedgerState`
(`screen_absolute` is where `DonationRestrictionsUnresolved` went for exactly this reason — R1 `:44`
says it "has the ledger AND the computed itemize election"), or (b) widen `screen_inputs`'s
signature and list the 18 call sites T1 touches (`scrub.rs:885-886`, `scrub_axis.rs:889-890,
1025, 1044`, `resolve.rs:96`, `answer.rs:429,439`, and the in-module tests).

### N-3 — IMPORTANT — the crypto-slice gate's condition is unsatisfiable, so "refuse unless answered" is silently "always refuse"

**Where:** spec R1 `:122-126`; T1's last kill `:200-201`; code `admin.rs:592`, `return_inputs.rs:137-145`.

**What is wrong.** The slice arm is reached **iff** `return_inputs::exists(session.conn(), tax_year)`
is `false`, and `BrokerReporting` is a field *of* `ReturnInputs`. So on that arm a stored
`ReturnInputs` never exists and the answers are never available: for a live year the slice arm
refuses **unconditionally**. Two consequences the spec does not state: (i) `btctax export-irs-pdf`'s
crypto slice — the whole non-full-return product surface — is **dead for TY2026+**, and the filer's
only exit is authoring full-return inputs; (ii) T1's kill ("no stored `ReturnInputs` → refusal, no
bytes") passes trivially and can never be paired with a passing case, so the gate is never observed
*discriminating* — the B1 shape.

**Minimal change:** say which one is intended. If the slice really is closed on a live year, write
that sentence, make the refusal message name `income import` as the exit, and drop the "unless"
clause. If it is not, the answers must be storable independently of `ReturnInputs` (a `broker_reporting`
table keyed by year), and T1 needs the second-direction kill: *slice arm, TY2026, answers stored ⇒
fills, boxes as answered*.

### N-4 — IMPORTANT — the fold DELETED r1's "a basis answer on a proceeds-only regime refuses" rule and its kill

**Where:** spec R2 `:143-144`; T2 `:202-205`. Compare r1 T2's kill (`diff` hunk at `:313-315`).

**What is wrong.** r1's T2 carried: *"Kill: a `Basis` answer for TY2025 (regime proceeds-only) →
`Refusal` (the broker cannot have reported basis)."* r2 replaced that kill with the cohort kill and
restated the rule as *"a `BasisMatches`/`ProceedsOnly` answer under a regime with `proceeds = false`
→ `Refusal`"* — which covers **2017/2024 only**. TY2025 is `{proceeds = true, basis = false}`, so a
stored `BasisMatches` answer for TY2025 is now:

- **not refused** (the regime has `proceeds = true`), and
- **not read** (liveness is gated on `basis`, so TY2025 rows stay I/L).

That is a filer declaration accepted and silently discarded, and the printed box (I/L = "no 1099-DA
received") **contradicts the filer's own stored answer**. It is the repo's "a figure with no reader"
class, and it points the wrong way: the tool overrides testimony with a default. Nothing gates the
field by year — `serde(default)` accepts it on any year and T6's TUI block is not year-scoped.

**Minimal change:** restore the rule in the general form the regime makes available —
*a `BasisMatches`/`BasisDiffers` answer under a regime with `basis = false` → `Refusal` (the broker
cannot have reported basis)*, and *any answer on a year where the question is not live → `Refusal`*
— and restore the kill alongside the new cohort kill in T2 rather than instead of it.

### N-5 — IMPORTANT — `RefuseReason::BrokerCohortUnknown` has no reachable trigger, while two real provenances are silently defaulted

**Where:** spec R1 `:95-99`, T1 `:196-197`, T2 `:202-204` ("a lot the engine cannot class → refuse").

**What is wrong.** `Cohort` is declared as a **total two-way partition**: `Covered` = direct purchase
into that exchange wallet on/after 2026-01-01, `Noncovered` = *"Everything else"*. Under that rule no
lot is unclassifiable, so `BrokerCohortUnknown` can never fire and T2's kill ("a lot the engine
cannot class → refuse") **cannot be written** — a refusal that does not refuse, and an instrument
that can never be seen red (B1).

Meanwhile there *are* genuinely ambiguous provenances, and "everything else" defaults them silently.
Of the 11 `BasisSource` variants (`event.rs:17-29`), `FmvAtIncome` (mining/staking/interest/airdrop/
reward credited **into the exchange account**) and `CardRewardRebate` are the live ones:
§1.6045-1(a)(15)(i)(J) covers acquisition "in exchange for cash, stored-value cards, different
digital assets, or any other property **or services**", so an exchange-credited 2026 staking reward
is arguably covered and the broker will decide, not us. Defaulting it to `Noncovered` puts it in a
key whose answer may then be wrong for it — feeding C-1.

**Minimal change:** state the mechanism instead of the outcome, as the repo's own rule requires. Name
the discriminator (`BasisSource`, `event.rs:17-29`) and give the three-way table: Covered-eligible
(`ExchangeProvided`, `ComputedFromCost` with `acquired_at ≥ 2026-01-01` in an `Exchange` wallet);
Noncovered (`CarriedFromTransfer`, `SelfTransferInbound`, `GiftCarryover`, `GiftFmvFallback`,
`SafeHarborAllocated`, `ReconstructedPerWallet`, `EstimatedConservative`, and anything pre-2026);
**Unknown ⇒ `BrokerCohortUnknown`** (`FmvAtIncome`, `CardRewardRebate` acquired in-account in 2026+).
Then the kill has an input.

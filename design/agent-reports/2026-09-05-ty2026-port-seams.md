# TY2026 port — code year-seams

**Lens:** code year-seams (which code is year-KEYED, which is year-HARDCODED).
**Date:** 2026-09-05. **Scope:** the main worktree only (`.claude/worktrees/*` excluded from every search).
**Method:** read + grep + execution of the prebuilt `target/debug/btctax`. No git/cargo/make/nextest run.

---

## Headline

**The year gate itself is sound — every emitter and both table lookups fail closed on 2026 — but two
COMPUTE-side rules that the repo deliberately made per-year are still selected by a literal, not by
`year`: Form 6251's line-1 rule (`return_1040.rs:2493` hardcodes `Y2024` while `year` is in scope 600
lines up) and Schedule 1-A's entire line numbering (one 2025-shaped struct returned for all of
2025–2028). Both are dormant only because `full_return_for` bundles TY2024 alone; both emit a wrong
number rather than refusing the instant a second full-return year lands.**

So the crypto-slice **tax arithmetic** for TY2026 is live: `BundledTaxTables::load()` inserts 2026 at

gift exclusion, SS wage base, lifetime exclusion). The crypto-slice **PDF emission** for TY2026 is
refused.

**The single year gate for the full return** is `full_return_for(year) → Some`
(`tax_tables.rs:99–104` bundles **2024 only**), reinforced per-year by the consistency guard at
`crates/btctax-cli/src/input_form_store.rs:307`:

```rust
if table.year != year || params.year != year {
    return Ok(CommitOutcome::NoTables);

```

Two standing kill-tests hold the gate open deliberately:
`ty2025_full_return_must_stay_fail_closed_until_complete` (`tax_tables.rs:814–822`) and
`ty2026_full_return_must_stay_fail_closed` (`tax_tables.rs:931–938`).

## 4. ★ Where TY2026 would produce a WRONG NUMBER rather than refusing

Three, ranked. None is reachable today; all three become live the same day a second `FullReturnParams`
year is bundled — which is the point, because that is one commit, and it is the commit this port is.

### 4.1 CRITICAL — Form 6251's line-1 rule is chosen by a literal, in a function that has no `year`

`crates/btctax-core/src/tax/return_1040.rs:2491–2493`:

```rust
        // TY2024's Part I. TY2025 passes `Y2025 { .. }` here; the year lives at THIS call site,
        // which is the one place that knows it (D-4).
        line1_rule: crate::tax::form6251::Form6251Line1Rule::Y2024,
```

**The comment is false as written.** `form6251_inputs_from_parts` (`return_1040.rs:2476–2488`) has
**no `year` parameter**. Its only production caller, `assemble_absolute`, does — `year: i32` at
`return_1040.rs:1826` — and calls it at `:2277`. Grep of the whole workspace for `line1_rule` outside
`form6251.rs` returns exactly one hit: line 2493. **No test in any `crates/*/tests/` directory
mentions `line1_rule` or `Form6251Line1Rule`** — the only references are inside `form6251.rs`'s own
unit tests, every one of which constructs the rule by hand.

Failure: `assemble_absolute(…, year = 2025 or 2026)` computes Form 6251 with the 2024 line-1 rule.
Line 4 (AMTI) combines `line1.amount_entering_line4()` — `line1` under `Y2024`, `line1b` under
`Y2025` (`form6251.rs:70–79`). Those are different quantities: 2024's line 1 is 1040 L15 (taxable
income), 2025's line 1b is `1040 L11b − (L14 − Sch 1-A L37)`. Wrong AMTI → wrong tentative minimum
tax → wrong 1040 L17/L24. Silent.

★ The sharpness: **the same function gets this right 400 lines earlier.** `Schedule1A::compute` at
`:2064–2069` is passed `year` with a doc comment explaining that taking the year from two places is
the shape §G-15 warns about. One year-dependent decision in `assemble_absolute` reads `year`; the
other does not. This is the packet.rs Form 6251 defect (`ty2024()` hardcoded while `year` was in
scope) one layer up, on the compute side, still open.

### 4.2 CRITICAL — Schedule 1-A is one 2025-numbered struct returned for four years, and the 2026 draft has already renumbered it

`crates/btctax-core/src/tax/tables.rs:1088–1089`:

```rust
pub fn schedule_1a_params(year: i32) -> Option<Schedule1aParams> {
    if !(2025..=2028).contains(&year) {
        return None;
    }
```

— returns the *identical* struct for 2025, 2026, 2027, 2028, on the stated ground (`:1086–1087`) that
"nothing here is indexed". `Schedule1A::compute` (`crates/btctax-core/src/tax/schedule_1a.rs:1311–1319`)
takes `year`, calls `schedule_1a_params(year)?`, and returns `Schedule1A`
(`schedule_1a.rs:397–404`) — **a struct with no year field and the TY2025 form's line numbering
baked in**: 52 leaves over 48 labels, `line37` at `:382`, `line38` at `:392`, emitted as literal
label strings `("37", …)`, `("38", …)` at `:545–546`.

The amounts claim may well hold. **The line NUMBERS do not.** Measured from primary sources, both
sides:

- TY2025 Schedule 1-A, `crates/btctax-core/src/tax/fixtures/schedule_1a_2025_form.txt:113` —
  `37  Enhanced deduction for seniors. Add lines 36a and 36b`; `:115` — `38  Add lines 13, 21, 30,
  and 37. Enter here and on Form 1040 or 1040-SR, line 13b`.
- TY2025 Form 6251 line 1a, as transcribed at `form6251.rs:53` — *"Subtract Schedule 1-A (Form 1040),
  line **37**"*.
- TY2026 **draft** Form 6251, `design/forms/2026/f6251--2026-DRAFT.pdf`, `pdftotext -layout` line 46:

  ```
  1a   Subtract Schedule 1-A (Form 1040), line 43, from Form 1040, 1040-SR, or
       1040-NR, line 14
  ```

  and line 77: `4  Alternative minimum taxable income. Combine lines 1b through 3.`

So the senior-deduction subtotal moves from Schedule 1-A **line 37 to line 43** — the schedule grew
by six lines between 2025 and 2026. Consequences:

1. `Form6251Line1Rule::Y2025 { schedule_1a_l37 }` (`form6251.rs:393–400`, field literally named
   `schedule_1a_l37`) **is not reusable for 2026**. A port that writes `2025 | 2026 => Y2025 { .. }`
   subtracts the wrong Schedule 1-A line — exactly the "neighbouring year's field names" class.
2. `Schedule1A` needs the per-year TYPE treatment `Form6251Line1` already got. It did not get it
   because 2025 was the only year that mattered; the asymmetry is the finding.

★ Caveat, stated plainly: this rests on **one draft document**, fetched 2026-07-29
(`design/forms/2026/f6251--2026-DRAFT.pdf.txt` records
`sha256 a547fc9d…`), and drafts are replaced in place. There is **no TY2026 Schedule 1-A in the repo**
— `ls design/forms/2026/` returns exactly two files, both the 6251 draft, and
`design/forms/extract/` contains **zero** 2026 files. The renumbering is an inference from the 6251
draft's cross-reference. Settled by fetching the 2026 Schedule 1-A itself (draft or final).

### 4.3 IMPORTANT — the only two year functions in `btctax-forms` that do not fail closed

```rust
// crates/btctax-forms/src/form1040.rs:34–39
fn f1040_clusters(year: i32) -> &'static [(f32, f32)] {
    match year {
        2017 => F1040_CLUSTERS_2017,
        _ => F1040_CLUSTERS_UNIFIED,          // ← 2026 lands here
    }
}
```

```rust
// crates/btctax-forms/src/schedule_se.rs:38–43
fn se_clusters(year: i32) -> &'static [(f32, f32)] {
    match year {
        2017 => SE_CLUSTERS_2017,
        _ => SE_CLUSTERS_UNIFIED,             // ← 2026 lands here
    }
}
```

These are the **geometry oracle** — the deliberately code-side, map-independent x-bands that
`verify_flat` checks a written value landed in (`form1040.rs:148`,
`crates/btctax-forms/src/verify.rs:358`). Their whole purpose is to distrust the map. A 2026 arm
added to `Form1040Map::for_year` without touching these silently applies the 2024/2025 bands to a
2026 PDF, and the instrument built to catch a mis-mapped cell is the one instrument in the crate
that was never told the year changed. Every other year function in `map.rs` (17) and `pdf.rs` (17)
ends in `UnsupportedYear`; these two end in `_`.

### 4.4 MINOR — a kill-test narrower than its name

`crates/btctax-forms/tests/full_return_forms.rs:509–528
full_return_forms_refuse_unsupported_years` exercises **one** fill — `fill_form_8995` — over
`[2017, 2023, 2025]`. It does not test 2026, and it does not test the other ten full-return fills.

### 4.5 NOTE — a structurally unpopulated Schedule 1-A input

`return_1040.rs:2073–2074` passes `false, false` for
`taxpayer_qualifies_as_senior` / `spouse_qualifies_as_senior`, commented "Part V seniors are wired
with the age seam in T5b; not inferred here". Direction is safe (a forfeited senior deduction
**overstates** tax), but it is a hardcoded answer to a question the filer was not asked — the
"blank because nothing populated it" class, not the "blank because the inputs say so" class. TY2025
completeness, flagged here because it is a literal standing where a `year`/DOB-derived value belongs.

## 5. CAN BE DONE TODAY — nothing here waits on the IRS

1. **Thread `year` into `form6251_inputs_from_parts` and dispatch `line1_rule` on it**
   (`return_1040.rs:2476–2493`). Today it must still yield `Y2024` for 2024, so this is behaviour-
   preserving. Land it with the test that reds when the year and the rule disagree — there is none
   today. **This is the single highest-value item on the list and it is a pure refactor.**
2. **Give `Schedule1A` the per-year TYPE treatment `Form6251Line1` already has**, or — cheaper and
   sufficient for now — narrow `schedule_1a_params` to `year == 2025` and let 2026 refuse until the
   2026 schedule is in hand. Either closes 4.2; the second is a one-line change and is the
   fail-closed direction.
3. **Make `f1040_clusters` / `se_clusters` exhaustive** (or assert their year ∈ `SUPPORTED_YEARS`),
   removing the last two silent year fallbacks in `btctax-forms`.
4. **Widen `full_return_forms_refuse_unsupported_years`** to every full-return fill and to 2026.
5. **Wire the ten staged TY2025 artifacts** — `f6251, f1040s2, f1040s3, f1040sa, f1040sb, f1040sc,
   f8959, f8960, f8995, f1040s1a`. The PDFs and `.map.toml` files are already on disk in
   `crates/btctax-forms/forms/2025/`; what is missing is `include_bytes!` + `include_str!` + a
   `for_year` arm + a `*_pdf` arm each. This is the rehearsal for the identical TY2026 chore, and
   doing it now means the TY2026 port is a repeat rather than a first attempt.
6. **Build the Schedule 1-A emitter** — map struct, fill fn, packet push. Nothing exists
   (`crates/btctax-forms/src/*.rs` has zero references). Blocks TY2025 as much as TY2026.
7. **TY2026 rate tables need nothing** — bundled, KAT-pinned, and `report --tax-year 2026` computes.
   Whatever the schedule is, this half is finished.
8. **Add `Form6251Line1Rule::Y2026`** as a compiler-driven inventory: the enum is not
   `#[non_exhaustive]`, so adding the variant enumerates, for free and exactly, every site that must
   move. Cheap recon even before its contents are known.

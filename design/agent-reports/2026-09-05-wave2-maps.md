## #9 — `Form8275Map::for_year` aliased on a YEAR LIST

### What was wrong (measured)

```rust
pub fn for_year(year: i32) -> Result<Self, FormsError> {
    match year {
        2017 | 2024 | 2025 => { let mut m = Self::ty2024(); m.year = year; Ok(m) }
        _ => Err(FormsError::UnsupportedYear(year)),
    }
}
```

The aliasing itself is right — Form 8275 is versioned by REVISION (Rev. 10-2024), not by tax year —
but the guard asserted nothing a reader could check. `| 2026` was a one-token edit, and the map
carries free-text FQNs (`p1-t80[0]`, `p2-t1[0]`…), so a Rev. 12-2026 form would take Rev. 10-2024
field names and land the narrative in whatever boxes those names then denote. It was also a *second*
year list: `pdf.rs::f8275_pdf` holds the same three years, and nothing tied them together.

### What changed

The constructor now holds **no year literal at all**. It asks two questions of two authorities:

- **which years ship a Form 8275** → `Form8275Map::bundled_pdf(year)` (a thin, testable wrapper over
  `pdf::f8275_pdf`, added because `pdf` is a private module and `sp4.rs` is an integration test);
- **is it still THIS revision** → `Form8275Map::alias_is_licensed_by(year, bundled)`, which compares
  the year's bundled bytes against `pdf::F8275_PDF_2024` — the exact document
  `forms/2024/f8275.map.toml` was transcribed from — and refuses with `FormsError::Structure` naming
  the year, the byte lengths, and the fix ("transcribe `forms/<year>/f8275.map.toml`").

`bundled` is a **parameter**, not an internal lookup, so the refusal can be observed without waiting
for the IRS to publish a revision. That is the whole B1 point: the precondition is now a check
somebody has watched discriminate, instead of a list somebody would extend.

`FormsError::Structure` was reused rather than a new variant added — `error.rs` is not my file.

## #10 — `sp4.rs` looped over years and compared all of them to the 2024 PDF

### What was wrong (measured)

`map_year_matches_bundled_pdf_fieldset_for_every_supported_year` iterated `SUPPORTED_YEARS` and then
did `let set = fieldset(F8275_PDF_2024);` **inside** the loop. It read as year-general and was a
TY2024 re-check wearing a loop: a year whose Form 8275 revision changed could not be seen.

### What changed

Each year is now compared against **that year's own asset**, `Form8275Map::bundled_pdf(year)`, and
the comparison itself was factored into `map_fields_absent_from(pdf, map) -> Vec<String>` so it could
be *watched failing*: `the_fieldset_check_can_fail_when_the_pdf_is_not_this_form` runs the 8275 map
against `F8283_PDF_2024` and requires a non-empty missing-field list. The loop also records the years
it covered and asserts it covered every `SUPPORTED_YEAR` — skipping is not passing.

**Honest limit:** today every supported year aliases the same document, so the two spellings agree.
No test can make the loop red on a *real* revision divergence until a divergent revision exists. What
changed is that the loop now reads the axis it claims to read, and the helper has been seen
discriminating.

## #11 — no `#[serde(deny_unknown_fields)]`, and `[census]` was the reason

### What was wrong (measured)

Zero occurrences of `deny_unknown_fields` in `map.rs`. Measured on the committed TY2025 Form 6251
map (`forms/2025/f6251.map.toml`), top-level keys vs `Form6251Map`'s fields:

```
file-only keys (silently discarded): ['line1a', 'line1b']
struct-only fields (missing):        ['line1']
```

So the *vanished* line was loud and the *renamed* line was half-silent — the TY2025 line-1 split
exactly.

**The thing the recon could not see from one file:** switching the attribute on breaks every map,
because **27 of the 37 committed `.map.toml` files carry a `[census]` table** that no struct models
— **793 entries**, machine-measured with `tomllib`, every one of them exactly `{ line, rule, reason }`
and all-string values. That whole block was being discarded on every parse.

### What changed

1. `#[serde(deny_unknown_fields)]` on **36 of the 37** `Deserialize` items in `map.rs` — every struct.
   The 37th is `MoneyCell`, an `#[serde(untagged)]` enum, where serde does not accept the attribute.
2. A modelled `CensusDecision { line, rule, reason }` (itself `deny_unknown_fields`) plus a
   `#[serde(default)] pub census: BTreeMap<String, CensusDecision>` field on the **17** top-level map
   structs (derived: the 17 carrying `pub year: i32`). The census is now *declared*, not swallowed —
   a blanket "unknown keys are fine" is the hole itself.
3. The one exhaustive destructure in the crate (`Form6251Map::money_cells`) names the new field.

Nothing outside `map.rs` constructs or destructures these types (grepped across `crates/`; only
`btctax-cli/src/cmd/admin.rs` and `btctax-cli/tests/export_irs_pdf.rs` touch them, by field access),
so the added public field is safe — confirmed by `cargo check -p btctax-cli --tests`.

The census's **content** gate stays where it was: `tests/field_census.rs` text-scans the file so it
sees every FQN. This change closes the KEY set; that test judges the decisions.

## Found and NOT fixed

1. **`forms/2025/f6251.map.toml` cannot be loaded by `Form6251Map` at all.** Keys `line1a`/`line1b`
   present, required `line1` absent (measured above). This is not a regression — `Form6251Map::for_year`
   already refuses 2025 — but the failure now names `line1a` instead of only "missing field `line1`",
   which is the half that used to be invisible. Fixing it means the `Form6251Line1Rule` work
   (§7 D3 of the port report: **no `Y2026` variant**), which is outside my files.
2. **`forms/2025/f1040s1a.map.toml` has no struct at all.** There is no `Schedule1AMap` in `map.rs`,
   so nothing in the crate can load Schedule 1-A. My stem→struct measurement had to record it as
   `NO STRUCT`, which is the honest verdict, not a parse result.
3. **Good news for the wiring task:** with `[census]` modelled, **9 of the 10 unwired TY2025 maps now
   deserialize cleanly** into their existing structs (`f1040s2`, `f1040s3`, `f1040sa`, `f1040sb`,
   `f1040sc`, `f8959`, `f8960`, `f8995`, plus `f1040`/`f8283`/`f8949`/`schedule_d`/`schedule_se`
   already wired). Only `f6251` (item 1) and `f1040s1a` (item 2) do not. Whoever builds
   `forms wire --check` inherits a much smaller problem than "ten stems".
4. **`pdf.rs` still holds the single remaining 8275 year list** (`2017 | 2024 | 2025`). That file is
   not mine. The one-token widening still exists there — but it now means something checkable
   ("TY2026 ships *this* document"), and the moment `forms/2026/f8275.pdf` is a different revision,
   `Form8275Map::for_year(2026)` refuses instead of aliasing. The duplicate list in `map.rs` is gone.
5. **`MoneyCell` (untagged) cannot carry `deny_unknown_fields`** — a serde limitation, not a choice.
   Covered indirectly and *measured*: its table variant `MoneyPair` denies, and an untagged enum whose
   every variant fails is an error rather than a default (plant 5).
6. **Shared-tree flux, worth knowing:** mid-session another agent's edit made
   `btctax_forms::SUPPORTED_YEARS` momentarily 2 elements (a new `supported_years_cross_product` test
   binary also appeared). Two reds during plant 4 were that, not my plant. I removed the
   `assert_eq!(supported, SUPPORTED_YEARS.len())` I had briefly put in `for_year_answers_…`: how many
   years ship a Form 8275 is the asset registry's business and is already asserted by
   `map_year_matches_…`; coupling a second constant into that test only makes it red for other
   people's reasons.

## The three declared deviations

**(a) I-1's hoist is in `export_full_return` — is there any path that writes a voucher without passing
through it?** No. `grep -n "write_payment_voucher(" crates/btctax-cli/src/cmd/admin.rs` finds exactly two
lines: the `fn write_payment_voucher(` definition (line 1042) and its **only** call site, at line 1565 —
inside `export_full_return` (which starts at line 1278), after the hoisted validation block (line 1344).
There is no second caller anywhere in the crate. **Confirmed sound.**

**(b) The I-2 mirror sits once above the dispatch — does it cover BOTH the full-return and crypto-slice
arms?** Yes. Read `export_irs_pdf_from_session` (admin.rs:642): the `f4868.pdf` guard is the first
statement in the function body (line 659), and the dispatch (`if crate::return_inputs::exists(…) {
export_full_return(…) } else { /* crypto-slice */ }`) starts afterward, at line 682. Both arms are
downstream of the one guard. Also confirmed behaviourally: the kill test exercises both pipelines in one
test (`owing_vault()` for the full-return arm, `make_vault(&real_events_2024())` for the crypto-slice
arm) and both assert the identical refusal and an untouched directory; both passed at baseline and both
paths are exercised by the same guard site — there is only one `if out_dir.join("f4868.pdf").exists()`
in the whole file. **Confirmed sound.**

**(c) M-3's pointer is on the dual report's AMOUNT OWED line — does a crypto-slice-only owing year (no
dual report) still get any pointer, and does the spec's amended T6 sentence describe what the code
does?**

First half: **no**, a crypto-slice-only year gets no pointer from this fold — `dual_report` in
`cmd/tax.rs::report_tax_year` (the `btctax report` handler; confirmed via `main.rs:158`) is `Some` only
when `provenance == Provenance::ReturnInputs` (i.e. `ReturnInputs` is stored for that year, `line 534`),
so a year with no full-return inputs never reaches `render_dual_report` and never sees the two new
pointer lines. But this is not a gap: I traced both instruments the pointer names and both require the
identical precondition. `extension_from_session` calls `screen_full_return` first (admin.rs:1213), which
refuses with `"no return_inputs stored for {y}"` if `ReturnInputs` is absent (line 1230) — so `btctax
extension` cannot run on a crypto-slice-only year at all. `export-irs-pdf --pay-by-check` on such a year
is separately refused by I-7 ("no full-return inputs, so there is no Form 1040 line 37 for box 3 to
carry" — confirmed live via the M-1 kill's own fixture and message). So there is no year in which a filer
could actually invoke either instrument the pointer names but not see the pointer: the precondition for
"the pointer would help" and the precondition for "the pointer appears" are the same one
(`ReturnInputs` on file), because a crypto-slice-only year has no Form 1040 line 37 to owe against in the
first place. **Confirmed sound — a real gap would exist only if either instrument worked without
`ReturnInputs`; neither does.**

Second half: **yes**, the amended spec sentence — *"report's AMOUNT OWED line points at both commands by
name"* (`design/SPEC_form_4868_1040v.md`, confirmed via `git show 7eb93c27 -- design/SPEC_form_4868_1040v.md`)
— describes exactly what `render_dual_report` does: the two `writeln!` lines sit directly under `→
AMOUNT OWED (L37)`, inside the `else` arm of `if f.line34 > Usd::ZERO { REFUND } else { AMOUNT OWED
+ pointer }` (render.rs:1648-1660), and `render_dual_report` is reached exclusively through
`report_tax_year`, the `btctax report` command's own handler. **Confirmed sound.**

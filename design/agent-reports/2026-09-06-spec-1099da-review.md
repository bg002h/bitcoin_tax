## Lens answers

**1 — Form text.** Every i8949 box-definition quote and the code-B (f)/(g) rule are *exact*; R3's
Schedule D claim is *true* (verified line by line against `f1040sd--2025.txt`). One wrong box number:
the 1099-DA basis box is **1g**, not 1e (S3) — 1e is "Date Sold or Disposed". The sentence naming 1g
sits at `i8949--2025.txt:1052-1055`, **outside** the spec's own cited span `:999-1030`, which is
plausibly how the error entered. Two cite ranges omit the lines they claim to cover (M1).

**2 — The rule's shape. Per-provider is the wrong grain, and it is wrong for the owner's own profile.**
`26CFR_1.6045-1(a)(15)(i)(J)`: a digital asset is a **covered security** only if acquired *in that
customer's account at that broker* on or after 2026-01-01. `(a)(15)(i)(G)`: an asset **transferred in**
is covered only if the broker received a §6045A transfer statement. `(a)(16)`: everything else is
noncovered. Form 1099-DA box 9 ("Check if Digital Asset Is a Noncovered Security") is **per form, i.e.
per transaction**, and `Instructions_1099-DA.txt:597-600` says a box-9 form need not complete boxes 1g
or 2. So one exchange, one customer, one year yields **both** kinds: box 2 checked for units bought
there in 2026+, box 2 unchecked for units bought there earlier or transferred in from self-custody.
A single `Basis` answer for `coinbase` routes the noncovered rows to G/J — a wrong box. Worse,
`Instructions_1099-DA.txt:548-551` lets a broker report basis for a noncovered asset *voluntarily*, so
covered-status is not even derivable: only the form says. This is Critical S4.

**3 — Fail-closed.** Defaults the spec leaves standing:
(a) **regime not live** (TY2017/2024) → C/F silently. *Correct* — no 1099-DA existed.
(b) **no exchange disposition** → not asked. *Correct* — nothing to box.
(c) **non-exchange disposal** (`box_needs_review = matches!(leg.wallet, Exchange{..})`) → I/L, never
asked. Acceptable today (locked-door intake), and open question 2 names it.
(d) **the crypto-slice `export-irs-pdf` arm** → I/L with no refusal at all. **Not acceptable** — S2.
(e) **R4's `0` in column (g)** on a `Basis` row → a fabricated adjustment the filer never gave. **Not
acceptable** — S1; wrong outcome is strictly worse than telling the user nothing, because the printed
`0` reads as testimony that the broker's figure was checked and matched.
(f) **TY2025** — the 2025 regime is `proceeds = true`, so R1's liveness makes the question live on a
paused year with shipped maps and goldens; the spec is silent. I3.

**4 — R4 is not defensible; it asserts three things at once, two of them false.** With box G/J checked,
`i8949--2025.txt:1018-1027` *and the Note printed on the form itself* say: put the **broker's** basis in
(e) and the correction in (g). R4 prints the **engine's** basis in (e), code **B** in (f) — which
declares "the basis on the 1099-DA is incorrect", a fact the tool has never seen — and `0` in (g),
which declares "the correction is zero", i.e. asserts the two bases are equal. The spec's own Legal
grounding bullet quotes the rule correctly three paragraphs earlier. **Honest minimum:** collect one
more answer per lot-group — *"does the 1099-DA's box 1g basis match btctax's for every lot from this
provider?"* — and then (i) **yes** → box G/J, (e) = engine basis, **(f) and (g) BLANK** (`i8949:1000`:
"For most transactions, you don't need to complete columns (f) and (g) and can leave them blank");
(ii) **no / unanswered** → **REFUSE**, naming the 1099-DA import as the exit. Never emit a code B the
filer did not assert. If a first cut must ship without the extra question, the minimum is box G/J with
**(f)/(g) blank** plus the advisory — that omits an adjustment (visible, correctable) instead of
asserting a false one.

**5 — Answered-ness.** The intent is right (absent key ⇒ refuse) but the stated mechanism does not fit
the classifier. `Census::declaration(&mut self, _leaf: &Option<bool>, id: QuestionId)` and
`FormQuestion { get: fn(&ReturnInputs) -> Option<bool>, set: fn(&mut ReturnInputs, bool),
unanswered: RefuseReason, neutral: bool }` are **boolean and singular**; a `BTreeMap<String,
BrokerReported>` with per-provider cardinality and a three-valued answer fits none of the four fields,
and `RefuseReason::BrokerReportingUnanswered { provider: String, year }` cannot appear in the `const
FORM_QUESTIONS` slice (no const `String`). And the thing that *could* silently answer for the filer is
already in the tree: `testonly::answer_all_live_declarations` fills every live unanswered question with
`q.neutral` — there is no neutral answer to "what did your broker report", so a force-fit would have
every fixture and golden silently assert "no 1099-DA received" and green the I/L default. I1.
Structurally sound parts: the map key set carries answered-ness rather than a sentinel value; the
`ReturnInputs` destructure with no `..` reds on the new field; T1's third kill (an answer for a
provider with no dispositions ⇒ refuse) closes the fabricated-declaration direction.

**6 — Build plan.** Order T1→T7 is right (declaration → routing → emitter → Schedule D → (f)/(g) →
surfaces → owner action). Gaps: **(i)** there is no `crates/btctax-forms/forms/2026/` — `for_year` is
generated by globbing that directory (`build.rs:183-195`), so `YearRecord::for_year(2026)` is `None`
and T1/T2's TY2026 kills cannot run (I2). **(ii)** `fill8949.rs` cannot paginate per (part, box)
today: `split_parts` splits by part only, `place_part` writes exactly one `part.box_field`, and
`lib.rs:119-135` computes `n_pages = max(⌈st/cap⌉, ⌈lt/cap⌉)` while pairing ST chunk *k* with LT chunk
*k* on one copy. It is *feasible* — one copy is a 2-page form (Part I p.1 / Part II p.2), and
`place_part` already no-ops an empty part — but the per-part group page-run and the cross-part pairing
rule are unspecified (M6). **(iii)** T3's risk is de-risked already: `pdf.rs:351-368` rejects an
on-state the widget does not declare, so a wrong `box_g/h/i` FQN↔on-state pairing fails closed rather
than printing a blank box. **(iv)** `ScheduleDLines` has no `line1b`, `line2`, `line8b` or `line9` at
all — T4 creates four line-sets, it does not split three (M3). **(v)** T5's kill hard-codes the wrong
box number (S3) and the wrong (f)/(g) behaviour (S1).

**7 — Scope.** Stays inside the rulings on the big things: TY2026 target, no 1099-DA import (out-of-scope
list is explicit and matches S3's "larger item"), T7 is the owner act S3 named, and the spec **corrects**
S3's own slip ("Box A/D with (f)=B" → correctly G/J). Two scope questions it does not answer: it makes
the question **live on TY2025** without saying so (I3 — a paused year), and R5 edits only the *2025* map
while the spec is for TY2026, with no statement that the 2026 map inherits at port time. Nothing here
should be *added*; S1's fix (one more question) is inside S3's "one input field per disposition source"
budget, and S4's fix is a re-grain, not a new feature.

## Findings

### S1 — CRITICAL — R4 prints a code B with a `0` adjustment, asserting two things the tool cannot know and the form forbids

**Where:** spec R4 (`SPEC_1099da_broker_reporting.md:84-91`) and T5 (`:128-129`).

**What is wrong:** With box G/J checked, the *form itself* prints — `f8949--2025.txt:54-55`,
identically on `f8949--2026-DRAFT.txt:92-93` — *"If you checked Box A or Box G above but the basis
reported to the IRS was incorrect, enter in column (e) the basis as reported to the IRS, and enter an
adjustment in column (g) to correct the basis."* `i8949--2025.txt:1018-1027` says the same. R4 does
the opposite: engine basis in (e), code **B** in (f), `0` in (g). That row asserts (1) a 1099-DA
basis was reported, (2) it was **incorrect** — a claim about a document the tool has never seen — and
(3) the correction is **zero**, i.e. that (e) equals the broker's figure. (2) and (3) are mutually
inconsistent, and (3) is precisely the repo's fabricated-`0`-is-testimony class: the filer never
answered it. The spec quotes the correct rule in its own Legal grounding bullet (`:27-30`) and then
violates it. Note the advisory does not cure this — the advisory is on stderr, the assertion is on the
mailed page.

**Minimal change:** Add one collected answer per provider (or per lot-group): *"Does the 1099-DA's box
1g basis match btctax's basis for every lot from this provider?"* — **yes** → box G/J, (e) = engine
basis, **(f) and (g) left blank** (`i8949--2025.txt:1000`: for most transactions leave them blank);
**no or unanswered** → **REFUSE**, naming the 1099-DA import as the exit. Delete the automatic code B
and the automatic `0` entirely. If a first cut must ship without the extra question, emit box G/J with
**(f)/(g) blank** — an omitted adjustment is visible and correctable; a fabricated one is neither.

### S2 — CRITICAL — the refusal cannot reach `export-irs-pdf`'s crypto-slice arm, which is the path that writes a mailable `f8949.pdf`

**Where:** spec R1 (`:65-70`), T1 (`:114-118`); code
`crates/btctax-cli/src/cmd/admin.rs:573-600` (the dispatch) and `:631, :716`.

**What is wrong:** R1 puts the refusal on the **full return** (`ReturnHeader::build`,
`packet.rs:386-390`, which iterates `FORM_QUESTIONS` over a `ReturnInputs`).
`export_irs_pdf_from_session` dispatches on `return_inputs::exists(session.conn(), tax_year)`; when
**no** `ReturnInputs` is stored for the year it runs the **crypto slice**, which calls
`btctax_core::form_8949(state, tax_year)` and `fill_form_8949` directly — no `ReturnInputs`, no
`FORM_QUESTIONS`, no refusal. A TY2026 `btctax export-irs-pdf` on a vault with no stored return inputs
therefore writes `f8949.pdf` with **every exchange row boxed I/L**, guarded only by the [I5] stderr
advisory. That is exactly the outcome the spec's own "Why this exists" calls Critical, and it violates
`TY2026_PORT_REPORT.md` §6 rule 18 verbatim ("**Do NOT ship a TY2026 Form 8949 whose box was chosen
without a Form 1099-DA answer**"), which carries no full-return qualifier. This is the B3 shape: the
spec covers the path it was thinking about and not its sibling.

**Minimal change:** Name the slice arm in R1 and give it a refusal of its own — for a year whose
`YEAR.toml` declares `f1099da.proceeds` and which has ≥1 exchange disposition, the slice arm must
refuse to fill Form 8949 unless a stored `ReturnInputs` answers every disposing provider. Add the kill
to T1: *`export-irs-pdf` on TY2026, one exchange disposition, no stored `ReturnInputs` → refusal, no
bytes written* (the existing `promote_export_gate` refusal-before-any-byte pattern at `admin.rs:620`
is the model).

### S3 — CRITICAL — "box 1e of the 1099-DA" is the wrong box; the basis box is **1g**

**Where:** spec R4 advisory text (`:89`); T5's kill (`:129`). Inherited from `FOLLOWUPS.md:6164` and
`fable-strategy-review.md` §S3, both of which carry the same error.

**What is wrong:** `Instructions_1099-DA.txt:498` — "**Box 1g. Cost or Other Basis**"; `:453` —
"**Box 1e. Date Sold or Disposed**"; `:539` — "Report the $600 gross proceeds from the sale in box 1f,
$1,000 basis in box 1g". And `i8949--2025.txt:1052-1055` spells out the distinction the spec collapsed:
"the basis shown in **box 1e on Form 1099-B** or **box 1g on Form 1099-DA** is incorrect". 1e is the
1099-B basis box. The spec's advisory tells the filer to compare a dollar figure in column (e) against
a **date**. This is user-facing instruction text on the one action the advisory exists to prompt, and
T5's kill pins the wrong string.

**Minimal change:** Replace every "box 1e" with "**box 1g**" in R4, T5 and the advisory text; correct
`FOLLOWUPS.md` FR-46's last sentence and T7's owner-action wording the same way. Widen the spec's
`i8949` code-B cite from `:999-1030` to include `:1052-1055`, the row that names the box.

### S4 — CRITICAL — a per-provider answer produces a wrong box for a real filer profile (covered vs noncovered within one broker)

**Where:** spec R1 (`:44-53`) — `by_provider: BTreeMap<String, BrokerReported>`, keyed by
`Source::tag()`.

**What is wrong:** Basis reporting is per **digital asset**, not per broker.
`26CFR_1.6045-1(a)(15)(i)(J)` makes a digital asset covered only if *"acquired in a customer's account
by a broker providing custodial services … on or after January 1, 2026"*; `(a)(15)(i)(G)` covers a
transferred-in asset only if the broker received a §6045A transfer statement; `(a)(16)` makes
everything else noncovered. TD 10000 (`:2999-3006`) is explicit that basis reporting reaches only
assets *"previously acquired, held until sale, and then sold by a custodial broker"*. Form 1099-DA box
9 is a **per-form** checkbox, and `Instructions_1099-DA.txt:597-600` says a box-9 form need not
complete box 1g or box 2. So Coinbase will, in the same year for the same customer, issue 1099-DAs
with box 2 checked (bought there in 2026) **and** with box 2 unchecked (bought there in 2025 or
earlier, or transferred in from self-custody) — which is precisely the owner's profile (long-held BTC,
a `TRANSITION_DATE`, self-transfers). A single `Basis` answer routes the noncovered rows to G/J; a
single `Proceeds` answer routes the covered rows to H/K. Either is a wrong box on a signed return.
The tool cannot derive the split either: `Instructions_1099-DA.txt:548-551` lets a broker report basis
for a noncovered asset *voluntarily*.

**Minimal change:** Re-grain the answer so one provider can carry more than one. The cheapest shape
that is not wrong: key by `(provider, covered_class)` where `covered_class` is a **collected**
partition the filer reads off their forms — e.g. `BrokerReported` answered per provider *per
acquisition cohort* (units acquired in that account on/after 2026-01-01 vs. all others), with the
engine supplying the cohort of each lot from `leg.acquired_at` + acquiring wallet and **refusing** any
lot whose cohort it cannot determine. State in R1 that a provider answer covers a *set of rows*, name
how a row is assigned to a set, and add the kill: *one provider, two cohorts, two different answers →
two Part I page-sets with different boxes.* Cite `26CFR_1.6045-1(a)(15)(i)(J)`/`(G)`/`(16)` (the
committed CFR XML) rather than the mangled TD 10000 pin cites.

### I1 — IMPORTANT — the answer cannot be a `FORM_QUESTIONS` entry as the registry stands, and force-fitting it makes `testonly` answer for the filer

**Where:** spec R1 (`:65-70`), T1 (`:114-116`); code `questions.rs:43-71`, `classifier.rs:71-74`,
`testonly.rs:34-40`, `return_refuse.rs:35-36`.

**What is wrong:** `FormQuestion` is boolean and singular in all four relevant fields —
`get: fn(&ReturnInputs) -> Option<bool>`, `set: fn(&mut ReturnInputs, bool)`, `neutral: bool`, and
`unanswered: RefuseReason` inside a `const` slice. A three-valued answer with per-provider cardinality
fits none of them, and `RefuseReason::BrokerReportingUnanswered { provider: String, year: i32 }`
cannot be constructed in a `const` (`RefuseReason` derives `Debug, Clone, PartialEq, Eq` — no `Copy`,
no const `String`). `Census::declaration` likewise takes `&Option<bool>`. Worse, if it *is* force-fit:
`testonly::answer_all_live_declarations` fills every live unanswered question with `q.neutral`, and
there is no neutral answer to "what did your broker report" — every fixture and golden would silently
assert "no 1099-DA received", greening the I/L default across the suite. That is the
green-and-blind-instrument shape.

**Minimal change:** Say in R1 which of the two the spec means: (a) generalise the registry (a
`QuestionKind`/`Answer` enum plus a per-question `unanswered_for(ri) -> RefuseReason` fn, and a
`Census::declaration` that takes the answer type), or (b) keep `FORM_QUESTIONS` boolean and screen
`BrokerReporting` in `screen_inputs`/`screen_absolute` alongside `DonationRestrictionsUnresolved`,
recording it in the classifier as its own class rather than as a class-A declaration. Either way T1
must state explicitly that `testonly` **must not** auto-answer it, with a kill that reds if it does.

### I2 — IMPORTANT — there is no `forms/2026/` package, so T1 and T2's TY2026 kills cannot run

**Where:** spec Legal grounding (`:39-40`) — "2026 `{true,true}`"; T1 (`:116-117`), T2 (`:120-121`).

**What is wrong:** `crates/btctax-forms/forms/` contains **2017, 2024, 2025 only**.
`YearRecord::for_year` (`year_record.rs:113-119`) reads `bundled::year_record_text`, which `build.rs`

2017/2024/2025 and stops. The spec states the 2026 `{true, true}` regime as a declared fact; it is a
plan, and R1's liveness predicate reads it. T1's kill ("TY2026 + one exchange disposition + no answer
→ refuse") and T2's kill (a `Basis` answer for TY2025 → refusal, which needs both regimes present) have
nothing to read.

**Minimal change:** Add a T0 to the plan: create `crates/btctax-forms/forms/2026/YEAR.toml` with
`information_returns.f1099da = { proceeds = true, basis = true }` and extend
`the_information_return_regime_is_declared_per_year` to assert it — or, if a 2026 package cannot land
before the finals, say in R1 which year the kills actually run against and how. Also state whether the
2026 `f8949.map.toml` inherits R5's six-box table at port time (R5 mentions only 2025 and 2024).

### I3 — IMPORTANT — the question goes live on TY2025, a paused year with shipped maps and goldens, and the spec never says so

**Where:** spec R1 (`:66-70`), R2 (`:72-74`), R5 (`:93-95`); `forms/2025/YEAR.toml:39-41`
(`proceeds = true`).

**What is wrong:** R1's liveness is *"≥1 exchange disposition AND `YEAR.toml` says `f1099da.proceeds`"*.
That is **true for TY2025**. So a TY2025 return with an exchange disposition — today an ordinary,
shipping export — begins to REFUSE, and TY2025 rows can now be boxed H/K rather than I/L. That is a
behaviour change on the year `ROADMAP_STATUS.md` §0a explicitly paused, touching the ten TY2025 maps,
the 2025 golden packets and the crypto-slice path. It may well be the right change (a proceeds-only
1099-DA does belong in H/K), but the spec neither states it nor bounds it, and the reader is left to
discover it from a TOML value. R1's closing sentence ("When not live … the box is I/L (TY2025+)") reads
as though TY2025 is unaffected, which it is not.

**Minimal change:** One paragraph in R1 stating what TY2025 does: either (a) the question is live for
TY2025 too and TY2025 exports may now refuse — with the golden-packet impact named and a kill; or (b)
liveness is gated to `f1099da.basis` (TY2026+) and TY2025 keeps I/L unchanged, with the reason. Say
which, and say it before T1 is built.

## `filing-path`

**VERDICT:** CONVERGING on the machine, not yet on the filer: the CSV→PDF path genuinely works end-to-end for a TY2024 common-W-2 household — I ran it and got a filled, signable 14-form packet — but it serves roughly 1 in 4 plausible US crypto filers for TY2024 and exactly 0% of the current filing season (TY2025), and the last month of work has been rigour on the TY2024 surface rather than the two things that change either number.

**WHAT I READ:** Read: design/direction/BRIEF-strategic.md; CLAUDE.md; crates/btctax-core/src/tax/return_refuse.rs (full RefuseReason enum L33-200, screen_inputs L547-881, registry loop L571-575); return_1040.rs screen_compute_dependent L660-757 and screen_absolute L1576-1719; crates/btctax-cli/src/cmd/admin.rs (export_irs_pdf L361, export_full_return L741-791 — screens run fail-closed before any byte), tax.rs (report_tax_year L272, write_back_carryover L485), answer.rs (live_questions L52), resolve.rs structure; crates/btctax-cli/LIMITATIONS.md (all 342 lines); crates/btctax-cli/src/testonly.rs (journey fixtures); docs/examples/examples.md (J1-J10); crates/btctax-adapters/src/tax_tables.rs L85-115 + the ty2025-must-stay-fail-closed guard test L790-815; crates/btctax-input-form/src/lib.rs; CONTINUITY.md; FOLLOWUPS.md headings; git log -40 on main. Ran: rebuilt target/release/btctax from main (12.5s); executed J1 end-to-end (init→import→tax-profile→report→export-irs-pdf, got f8949+schedule_d PDFs); executed J6 end-to-end (2 CSVs + reclassify-income + reclassify-outflow + set-donation-details + income import TOML → 14-form packet, exit 0); verified the 1040 AcroForm is really filled via qpdf (/V (290000), (254876), (47148), names, SSNs); ran report --tax-year 2024 (full absolute-return summary + 10 advisories); ran a live refusal experiment (added W-2 box-12 code C → whole return refused).

**STATE OF MY SLICE:** WORKS, verified by running it: the whole J6 pipeline — exchange CSVs → import → reconcile verbs (reclassify-income/outflow, set-donation-details, promote-tranche) → income import (TOML, unknown keys rejected) → three fail-closed screens → a 14-form filled AcroForm packet in IRS stapling order with manifest.txt, all-or-nothing (a refusal writes zero bytes, admin.rs:772-791), plus honest advisories and a NOT-AUTHORISED notice. The refusal UX is genuinely good for the question class: every unanswered-declaration refusal has a one-keystroke exit via `income answer` (answer.rs derives prompts from the same FORM_QUESTIONS registry that refuses, so prompt scope == refusal scope by construction). SCAFFOLDING: docs/examples/examples.md is generated from real binary runs and regen-gated, so the journeys cannot rot. ABSENT — and this is the number the brief asked for: I estimate ~20-30% of plausible US crypto filers could get a signable TY2024 federal packet, and ~0% can file the CURRENT season. Mechanism: (1) TY2024 only — BundledFullReturnTables::load inserts exactly one year (tax_tables.rs:100-102) and a guard test asserts TY2025 stays fail-closed until complete; today is Aug 2026, so the season in progress (TY2025, extensions to Oct 15) is unservable — the dominant term. (2) UNREPRESENTABLE income excludes big slices: any 1099-R event (including the rollover every job-changer has), SSA-1099, Schedule E/K-1, Form 1095-A/APTC, non-crypto Schedule C, second SE earner (LIMITATIONS §iii) — maybe 25-35% of the demographic combined. (3) Refusal census (44 RefuseReason variants): ~30 are class (a) legally-necessary or one-keystroke integrity/declaration gates — well calibrated; ~13 are class (b) closable gaps, led by HsaActivityUnsupported + box-12 W (HSA is very common in this demographic; Form 8889 unmodeled), IraDeductionClaimed, UnrecapturedOrSpecialRateGain (1099-DIV box 2b appears on ordinary REIT-fund statements), QbiAboveThreshold, ScheduleCLoss, ForeignTaxOverCeiling, and AmtScreenTriggered — which is the strangest one: Form 6251 is COMPUTED for every return and double-oracle-validated over 30 vectors, the blank f6251.pdf is already bundled in crates/btctax-forms/forms/2024/, and the refusal exists only because there is no f6251.map.toml to fill it; (4) one class (c) over-broad refusal I confirmed live: W-2 box-12 code C (employer group-term life >$50k — purely informational, already inside boxes 1/3/5, present on tens of millions of W-2s) refuses the entire return with no remedy named (return_refuse.rs:26, INERT_BOX12_CODES omits C, V, Y, P). (5) Not a refusal but blocking-in-practice: CTC/Schedule 8812 is advisory-only, so every parent's packet overstates tax by up to $2,000/child — a signable wrong-in-their-disfavor return; ~a third of filers. Multiply the independent-ish terms and ~1 in 4 gets a signable TY2024 packet; fewer get one they should actually sign.

**THE BOTTLENECK:** THE CALENDAR. The single thing most preventing a real filer from finishing is that btctax supports only TY2024 while the filing season that exists is TY2025 — a filer with a Coinbase CSV and a W-2 today gets exactly as far as `income import --year 2025` and dies at the year gate (resolve/full_return_for returns None, fail-closed, tax_tables.rs:107). Everything else — refusal calibration, §G-11, the census — is refinement of a year no one can any longer timely file. Second, inside the supported year: the highest-frequency stoppers are all in the same demographic cluster (HSA code W/8889, box-12 C over-refusal, 1099-R rollover, CTC-not-computed), so the marginal common-W-2-techie filer hits one of them with high probability even though each individual gate is defensible.

**WEB-UI READINESS:** Better than the crate sizes suggest. The seam already exists and is real: btctax-core takes ReturnInputs + LedgerState → screens → AbsoluteReturn/Refusal/advisories with no terminal dependency; btctax-input-form is explicitly "UI-agnostic... rendered by the TUI now and a web app later" (lib.rs:1-3), depends on core only, and the FORM_QUESTIONS/SKIPPABLE_QUESTIONS registries (live/get/set/neutral per question) are exactly the shape a web wizard is generated from — the 46k-line btctax-tui-edit is a renderer over that engine and correctly disposable for web. The coupling that should NOT be there: refusal and advisory REMEDIES are prose strings baked into btctax-core that name CLI commands — "re-run `btctax income import`" (return_refuse.rs:653, 680), "run `btctax income answer`" (screen_absolute detail, return_1040.rs:1654) — so a web front end would print terminal instructions at its users. Refusal.reason is machine-readable but the remedy is not addressable; the fix is a structured remedy field (QuestionId / field-path / verb) with each front end choosing its own words. Vault/passphrase session handling is terminal-flavored but thin. Net: a web UI is a rendering project, not a re-architecture — provided the remedy channel is structured first.

**WHAT I WOULD DO NEXT:**
1. **Fill and attach Form 6251, deleting the AmtScreenTriggered refusal** (days) — The form is already computed for every return and validated against both oracles; the blank f6251.pdf is already bundled — only the map.toml + packet entry are missing. This is the cheapest refusal-to-filer conversion in the codebase and unblocks exactly the high-income filers most likely to actually use a crypto tax tool.
2. **Calibrate the box-12 allowlist: add the purely-informational codes (C, V, Y, P at minimum), each with a one-line citation and a test** (hours) — Code C alone is on a huge fraction of W-2s and moves no 1040 line; today it hard-refuses the whole return with no remedy named (verified live). The allowlist design is right; its population is miscalibrated. Hours of work for perhaps the single largest unblocked-filer count per line changed.
3. **Ship TY2025: FullReturnParams + OBBBA SALT worksheet + Form 6251 re-transcription + 1040 reshape + Schedule 1-A (track A, T2-T7)** (weeks) — This is the critical path, full stop. The spec exists (design/ty2025/), track A is 1/7 built, and the guard test enumerates exactly what must land. Until it does, the product addresses 0% of the current filing season, and TY2026 arrives in five months — the year lag is compounding.
4. **Form 8889 common case (code W + contributions/distributions), un-refusing HsaActivityUnsupported** (days-week) — HSA activity is likely the most common class-(b) refusal in the target demographic, and the common case (contribution ≤ limit, qualified distributions) is a short transcribable form.
5. **Schedule 8812 (CTC/ODC), converting the largest advisory into a computed line 19** (days) — Every parent's packet currently overstates tax by up to $2,000/child; 'file Schedule 8812 yourself' defeats the product's whole premise for a third of filers. The worksheet is transcribable and the dependent data is already collected.
6. **Structure the refusal remedy channel (QuestionId/field-path instead of CLI prose in core)** (days) — Small now, expensive later: it is the one seam change web-UI readiness actually needs, and every new refusal added before it deepens the coupling.

**WHAT I WOULD STOP DOING:** Three things, all currently in flight. (1) STOP the §G-11 type migration (the two-types/'no testimony' emitter rework) beyond what has landed — the coverage checker exists, it already found the real defects (G-24: 1040 L34/L37 print a zero where the form says blank; fix those two lines directly), and the full 179-line migration is architectural purity on a surface that serves a past tax year; resume it after TY2025 ships. (2) STOP extending the form-authority pipeline and harness doctrine (label reader §5, further census instrumentation, B-series additions) — these are instruments about instruments; the census is complete (15/15 forms, zero unaccounted) and has delivered its gap list; work the gap list, not the instrument. (3) STOP adding refusing questions to the TY2024 surface — the owner already issued this correction mid-branch ('a lot of items on a tax return don't need to be answered, or asked'), and the refusal census above confirms it: the unanswered-question class is well calibrated now, and each new mandatory question subtracts filers. The general pattern across all three: the last ~60 commits are 0C/0I-grade rigour on a year the calendar has closed, while the two numbers that matter (supported-season filers: 0%; TY2024 filers served: ~25%) were movable the whole time with smaller, less glamorous work.

**WHAT WOULD MAKE THIS WRONG:** The assumption I could not verify: that the owner wants a CURRENT-season filer soon, rather than deliberately hardening the method on a frozen year (TY2024) so that each subsequent year becomes a table-entry-plus-transcription exercise — the question registry, census, and coverage checker DO transfer across years, and if that is the strategy, my 'stop doing' list is partly wrong and the year lag is a planned cost, not drift. Second-order unverified items: my frequency estimates (HSA prevalence, box-12 C prevalence, 1099-R events, dependents) are demographic reasoning, not measured data — the ~1-in-4 figure could be 1-in-3 or 1-in-6, though the dominant terms (TY2025=0%, code C over-refusal, CTC advisory) do not depend on the exact percentages. I also did not run the TUI-edit authoring path (LIMITATIONS calls it the primary authoring surface; if it is materially broken my 'the E2E path works' claim weakens), and I sized the 6251-attach move as days without confirming the form-geometry pipeline (G-6b Tier-2 criteria E4/E5/E6 still open) does not gate adding a new map.toml.

## `tax-engine`

**VERDICT:** Converging on correctness but not yet on coverage: the engine genuinely produces a validated, cross-footing, 15-form TY2024 packet end-to-end, but its supported archetype — a childless W-2 household with no brokerage account, no employer HSA, no retirement income, filing a year whose deadline has passed — is narrow enough that most real filers hit a refusal or a multi-thousand-dollar deliberate overstatement, and the shortest honest path is 4–6 mechanical form transcriptions plus TY2025 params, not more rigor on the already-validated core.

**WHAT I READ:** Files: design/direction/BRIEF-strategic.md; CLAUDE.md (project doctrine); crates/btctax-core/src/tax/return_inputs.rs (all 794 lines — the entire input surface); compute.rs (all 672 — the frozen crypto-delta engine); return_1040.rs (outline of all 67 pub items + lines 914–1150, the AbsoluteReturn struct and assemble_absolute entry); return_refuse.rs lines 33–190 (the RefuseReason taxonomy); advisories.rs (AdvisoryKind list + message()); questions.rs outline (the QuestionId registry, lines 43–430); tables.rs (year coverage, SaltLimitation enum, FullReturnParams); types.rs (FilingStatus); crates/btctax-adapters/src/tax_tables.rs (ty2024_full_return at :115, the TY2025-not-bundled comment at :793–801); crates/btctax-cli/LIMITATIONS.md in full; docs/examples/examples.md journey list + J6 in full (lines 393–774). Commands: `make check` (2544 tests, all green, 16s); greps confirming no 1099-B/1099-R/SSA-1099 input exists anywhere under src/tax/.

**STATE OF MY SLICE:** WHAT WORKS END-TO-END: the full-return path is real, not scaffolding. J6 (docs/examples/examples.md:393–774) is the actual binary producing a complete MFJ TY2024 return — W-2s x2, 1099-INT/DIV/G, crypto mining Schedule C + SE, Schedule A with §170(b)-limited charitable including ledger crypto donations, Schedules B/D + 8949, Forms 8959/8960/8995/8283/8275 — 15 official AcroForm PDFs in attachment-sequence order, byte-reproducible (golden_packet test), whole-dollar cross-footing (printed.rs, 2,991 lines), two-oracle validated. assemble_absolute (return_1040.rs:1135) is a genuine line-by-line 1040 constellation; Form 6251 is computed in full for every return (form6251.rs, 1,384 lines). The refusal taxonomy (return_refuse.rs, ~45 typed reasons) and the questions registry (questions.rs:100–112, 12 interview questions with liveness predicates and skippability classes) are principled and machine-readable. The suite is green and fast.

WHAT IS DELIBERATELY HOLLOW: 1040 line 19 CTC/ODC is pinned $0 (return_1040.rs:1018–1020) — dependents are captured (return_inputs.rs:151–157, name/SSN/relationship/DOB all present) but the credit is never computed, so every household with a child overpays up to $2,000/child and the printed packet is not correct as-printed for them (fixing L19 by hand changes L22/L24/L33–37 too). Same class: EIC, education, dependent-care, saver's credits (advisories.rs:46–125).

WHAT IS ABSENT (no input exists — LIMITATIONS.md:210–226): non-crypto capital gains — there is no 1099-B struct anywhere in src/tax/ (grep confirmed), so a filer who sold one share of stock cannot file; retirement/pension/IRA/Social Security income (1040 lines 4a–6b); Form 1095-A/APTC reconciliation (mandatory for anyone on marketplace insurance); Schedule E/F; any non-crypto Schedule C; a second SE earner. WHAT REFUSES on very common facts: W-2 box 12 code W — any employer HSA contribution — kills the whole return (UnsupportedBox12Code, LIMITATIONS.md:188); hsa_activity Some(true) refuses (return_refuse.rs:141–144); IRA deduction claimed refuses; a Schedule C loss refuses; Form 6251 must-attach refuses even though the form is fully computed, purely because the emitter cannot attach it (return_refuse.rs:184). AND: only TY2024 has FullReturnParams bundled (adapters/tax_tables.rs:115; the :793–801 comment shows TY2025 is researched but not wired) — in August 2026 the filable-on-extension year is TY2025, so the product currently supports only late/amended returns.

**THE BOTTLENECK:** Population coverage of the input surface, not engine correctness. Concretely: a filer with a Coinbase CSV and a W-2 gets a flawless packet — until they have a child (L19 pinned $0, return_1040.rs:1018), or a Schwab account (no 1099-B input exists, so the return is unrepresentable), or an employer HSA (box 12 W refuses at screen_inputs), or a parent's 1099-R (unrepresentable), or they simply want to file the current year (no TY2025 FullReturnParams). Each of these alone covers a large fraction of ordinary households; together they exclude well over half of them, and the CTC one specifically excludes nearly every family. Every one of these walls is a mechanical worksheet transcription by the project's own doctrine ('the answer is in the manual'; 'adding a form is a table entry plus a transcription') — the engine's architecture (typed inputs → assemble → screen → printed chain → AcroForm) makes each addition routine. The bottleneck is that recent investment has gone to hardening the already-modelled core (G-11 answered-ness migration, AMT form-authority pipeline, harness meta-instruments) rather than widening the set of people the tool can serve at all.

**WEB-UI READINESS:** Good — this slice is the most web-ready part of the codebase. The engine is a pure function pipeline: ReturnInputs (plain serde JSON, demonstrated by `income show` round-trip) → screen_inputs/screen_compute_dependent → assemble_absolute → screen_absolute → printed chain → AcroForm fill, with no terminal, clock, or filesystem dependency inside the computation. Refusals are a typed enum (RefuseReason), advisories a typed enum with structured payloads, and questions.rs is already a machine-readable interview spec — id, liveness predicate over ReturnInputs, skippability class, prompt text — which is exactly what a web form generator consumes. Two seams need work: (1) remedy prose is baked into core strings — RefuseReason details and Advisory::message() say 'run `btctax income answer`' (return_refuse.rs:652, :680) — a web front end needs reason-keyed remedies, so the prose should move behind the enum, not travel with it; (2) the interview state machine (ordering, per-field validation, draft autosave) lives inside btctax-tui-edit (46k lines, the largest crate) rather than as a front-end-agnostic service over the questions registry — that logic, not the tax engine, is what a web UI would otherwise have to rewrite. The vault (file-based, passphrase) is an orthogonal server-side question outside this slice.

**WHAT I WOULD DO NEXT:**
1. **Bundle TY2025 FullReturnParams and finish the in-flight TY2025/Schedule 1-A track (design/ty2025 B3, already spec-green with T1 built)** (days-week) — Without a filable current year there is no possible first user: TY2024's deadline passed in April 2025; TY2025 is filable on extension until Oct 2026. The constants are already researched (adapters/tax_tables.rs:793-801 comment) and the SaltLimitation::Worksheet2025 machinery exists in tables.rs.
2. **Transcribe Schedule 8812 (CTC/ODC) and unpin 1040 line 19** (days) — Dependents are already fully captured (name/SSN/relationship/DOB); at v1's supported income shapes the credit is a short mechanical worksheet with a simple $200k/$400k phase-out. This single form converts every family with children from 'overpays $2,000/child, packet unusable as printed' to filable — the largest coverage gain per line of code available.
3. **Add an aggregate 1099-B input feeding Schedule D lines 1a/8a (covered, basis-reported totals; no per-lot 8949 rows needed per the Schedule D instructions' Exception 1)** (days) — No non-crypto capital-gains input exists at all, so any filer with a brokerage account is unrepresentable. Two ST/LT proceeds+basis totals flow directly into the existing net_1222/capital_gain_line7 machinery (compute.rs:137, return_1040.rs:583); the full Box A-F 8949 machinery can come later.
4. **Allow W-2 box 12 code W with a Form 8889 Part I contribution-only path (distributions still refuse)** (days) — Any employer HSA contribution currently refuses the entire return (UnsupportedBox12Code), and HDHP+HSA is one of the most common W-2 facts there is. 8889 Part I for the employer-contribution-only case is a short transcription; the refusal stays for the genuinely hard cases (distributions, testing-period).
5. **Attach Form 6251 to the packet (it is already computed in full for every return)** (days) — The Form6251MustAttach refusal (return_refuse.rs:184) is now purely an emitter gap — the numbers exist and are two-oracle validated. Filling one more AcroForm is a field-mapping job by the project's own design ('the PDF emitter becomes trivial'), and it removes an artificial wall for exactly the high-income filers most likely to have real crypto volume.
6. **Add 1099-R/SSA-1099 inputs and 1040 lines 4a-6b with the Social Security taxability worksheet** (1-2 weeks) — Retirement income is the largest remaining unrepresentable class (roughly a third of all returns carry lines 4/5/6). The SS worksheet is an 18-line mechanical transcription; simple 1099-R cases (code 7, taxable amount determined) are direct box-to-line. Both oracles compute SS taxability, so validation is free.

**WHAT I WOULD STOP DOING:** Stop treating the §G-11 structural type migration (179 money lines across 14 forms) and further AMT form-authority pipeline rounds as the next tranche of work. The G-11 coverage checker that landed is the valuable part — it made the gap enumerable and testable; the full migration is weeks of churn on lines that are already two-oracle-validated and green, closing a defect class (silent fabricated blanks) whose known instances are already individually pinned, while every real filer is stopped by coverage, not by answered-ness. Migrate types opportunistically as each NEW form lands (8812, 8889, Schedule D 1a/8a — where the doctrine applies at zero marginal cost) rather than as a standalone pass over the existing surface. Similarly, pause growth of the harness's meta-instruments (checkers that check checkers, B1 kill-tests for instruments not on the coverage path): the observed failure modes they guard are real, but their marginal yield is now far below one transcribed schedule. The doctrine itself — transcribe, blank-is-normal, testimony — should keep governing new work; what should stop is applying it retroactively as a program while the product cannot serve a household with a child.

**WHAT WOULD MAKE THIS WRONG:** I did not verify the owner's intended first user. If the target is precisely the archetype LIMITATIONS.md names — a crypto-heavy filer whose non-crypto life is simple, filing late or amended TY2024 returns — then CTC/brokerage/HSA/retirement coverage is deliberately out-of-market, the conservative-omission posture is the product, and the rigor track is correctly prioritized. My population-coverage claims (over half of ordinary households hit one of the four walls) rest on general SOI-shaped knowledge, not verified against data or against the owner's actual user pipeline. I also did not run the TUI interview or the oracle sweep myself (I relied on the generated examples golden and the green suite), and I did not read the §G-11 spec's own cost estimate — if the migration is genuinely days rather than weeks, the stop-doing tradeoff softens. Finally, if the owner plans the first real filing for TY2026 in spring 2027, the TY2025-params urgency drops and the coverage moves rank even higher relative to it.

ABSENT. **THE BOTTLENECK:** The strongest instrument in the repo points at the middle of the pipeline, and both ends are dark. A filer with a Coinbase CSV and a W-2 traverses: sources/coinbase.rs (225 lines, no inline tests) → the lot engine (self-authored KATs only, structurally bypassed by build_golden_return's single synthetic leg at testonly.rs:651) → 1040 L11-L24 (genuinely double-oracle-validated, compute and paper) → L25-L37, the refund-or-owe the filer actually reads (compared against nothing, and already wrong once — G-24). The two-oracle agreement is the product's whole trust claim, but the numbers a real filer is most likely to get wrong — the ST/LT aggregates the oracles take as INPUT (the known §G-9-class limit, here at its largest scale), a refund figure, or any HoH/MFS return — are exactly the ones that agreement never touches. The bottleneck is corridor WIDTH, not instrument quality: 13 lines x 2 statuses x credit/AMT/withholding-free is not yet "a filer should trust a signed return," and every recent unit of rigour (grammar productions, coverage ratchets, more packet review) deepened the already-covered middle instead of widening the corridor.

**WEB-UI READINESS:** For this slice: good, nearly free. The confidence machinery is already front-end-independent — the oracle harness is a stdin/stdout JSON binary over core APIs (GoldenInputs in, per-line verdicts out); the golden/paper differentials live against btctax-core/btctax-forms; verify.rs operates on PDF bytes. Nothing in the correctness surface imports CLI or TUI code. The seam to respect: the harness validates GoldenInputs→packet via build_golden_return, while any front end will marshal user input→ReturnInputs through NEW code that sits outside the oracle loop — precisely where the tenforty precedent (#278: engine right, wrapper wrong) says wrong numbers enter oracle-validated systems. Concretely: a web layer should ship on day one with an end-to-end test that drives the HTTP/input boundary to a filled packet and compares figures against baked expectations; the harness's DEFAULT mode (whole-packet flattened read-back, main.rs run_default) is already the right instrument to point at that boundary, unchanged.
